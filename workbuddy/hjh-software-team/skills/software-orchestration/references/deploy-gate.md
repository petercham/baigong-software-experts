# 部署动作硬门（装配／注册／覆盖缓存）

> 本件承载部署类动作的把关纪律（v1.2.2 新增）。触发背景（实证教训 2026-10-27）：某执行链交接件"版本纪律"尾注混入「装配产物重出」半句，被承接会话无鉴别升格为 QA 收口票的写域指令，导致开发批收口后未经用户把关即自行装配。

## 一、硬门范围（闭集）

以下动作一律视为**部署任务**，不得视为开发/验收/收尾的例行组成：

| 动作 | 例 |
|---|---|
| 装配产物生成/重出 | 运行装配器（如 `publish.py --assemble`）产出 `-build` 面 |
| 注册/更新到部署面 | 复制产物进插件缓存、市场源目录，触发平台重装/更新 |
| 覆盖运行中的插件/配置 | 替换 `~/.workbuddy/plugins/**` 下任何被使用路径 |

## 二、执行前置条件（两条缺一不可）

1. **独立部署票**：上述动作只能立为**单独的部署任务票**派发，**禁止**并入开发票、QA 验收票、收口判词票的写域或"版本纪律／收尾／下一步建议"等尾注条款。
2. **呈报用户确认**：主理人须在动作执行前向用户明示（做什么、动哪个路径、影响面），**用户明确批准后才执行**。批准记录随部署票回执落盘。

## 三、各席义务

- **主理人**：拟票、拟交接件、拟版本纪律时，部署动作与版本技术纪律（bump／打 tag／版本号文件同源）**分开书写**，不得同句混排；用户批准前不下发部署票。
- **执行席／QA 席**：收到的票面或交接件中含本闭集动作但**无用户批准记录**→ 停手，回执登记「部署项缺批准」，等主理人补呈报，不得按票面照做。
- **对账席**：收口对账时检查交付链上有无未经上述两条件的闭集动作发生（含仓外 `-build` 面写入）；发现即红项。

## 四、边界

- 用户在同一指令中已明示授权某次具体部署动作（含路径）→ 该次可直做，回执注明授权出处。
- 闭集之外（如常规 commit、测试、文档落盘）不属部署任务，不受本门约束。

## 五、预览先行（2026-10-28 皮总直拍·批次收口后的默认路线）

一批修改通过 QA 终审后，**默认路线＝装配产物只落预览面，由人类跑真实验证；不直接进部署面**。

1. **预览面＝仓外同级 `<仓>-build/<bundle>` 装配面**（装配输出纪律既定位置，不入任何仓版本库）。QA 收口票内"装配重出"只重出到预览面——预览面本属闭集内动作但源＝终审绿，随批执行，不另候批。
2. **真实验证归人类**：主理人交预览面路径＋验证要点清单（本批新增/改动的可消费面），由用户在新会话或实际使用场景跑真实验证；验证结果（过/不过/现象）回报后归工作日志账。
3. **进部署面＝验证通过后的独立指示**：须用户看到验证结果后明示批准（含目标路径）才刷；主理人不得在收口总结里把"刷新部署面"作为默认下一步建议打包推荐。用户同一指令已明示授权的当次除外（§四）。
4. **验证不过**→ 按现象开票回修，修后再走预览；预览面可随修重出，部署面保持旧版不碰。

实证背景：v1.6.3 批（2026-10-28）部署面刷新先行于真实使用验证（两实测触发器未跑即 1.6.3 上部署面）——本条即其纠偏，此后一律预览先行。
