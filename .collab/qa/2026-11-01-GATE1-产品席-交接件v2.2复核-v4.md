## 三、固定必做块②：§12「修单审定」条款产品面直判

被核条款（V5 L187）：「修单审定：审计开出的必改修单由生成方径直执行、无需审定；权威审定仅适用于缺席类与范围类事项——修单审定权属设计权威」。

产品面直判：**成立**。理由三条——

1. **与我方盘上真源同构**：`skills/software-orchestration/references/handoff-discipline.md` §十一已把我方修单分两档——「执行层错误」类直修免审定、「保留闸类」（席位权力拓扑改动）须裁。v2.2 的「必改修单径直执行 / 缺席类与范围类须权威审定」是同一分档结构：免审的是**已被上轮独立闸判定为必改**的条目（审定已发生在开单方），须审的是**扩大解释权**的条目。分档边界清晰，无「生成方自选哪些免审」的滑动空间。
2. **不违背外部最佳实践**：S4「Version agent instructions in source control…review and rollback path as code」——径直执行仍在 git 链上、可回滚；S9 rubber-stamp 反模式针对的是"未经验证的批准"，修单执行不是批准行为。
3. **一个必要约束（非新必改，属机制既有）**：径直执行的修单**必须受下一轮独立闸闭合核**覆盖（v2.2 §18 终检/独立闸已含此面）。若该覆盖在实施中缺席，本条即退化为「生成方自改自证」——届时应回判不成立。此约束登记在此供架构签字面确认机制锚。
