## 〇、假说拆解（先立靶）

委托假说含四个可分离命题，分别核证：
- P1：Agent 框架对「席位（role/agent）与流程节点/产出物绑定」没有统一标准。
- P2：存在「席位绑定节点/产出物」的机制先例（MetaGPT SOP 等）。
- P3：WorkBuddy「专家即节点」是该谱系的一种机制选择。（内部系统主张，外部文献无从证伪，本件只登记不判定。）
- P4：因为「ADR＝对架构的决策」，所以 ADR 应从架构设计节点出口、写权归架构师席位。

**预断风险提示**：P1–P3 即便全部成立，P4 也不构成有效推论——「绑定机制的存在」推不出「该绑到哪个席位」；后者须由 ADR 自身范式（上轮 R1–R13）＋Agent 框架中 ADR 类产物的实际归属（本轮 Q5）独立支撑。

## 二、Q4 证据：席位-节点绑定机制盘点（逐框架）

### 2.1 MetaGPT（R14）——「席位绑定产出物」最强先例

- 机制原文："MetaGPT encodes Standardized Operating Procedures (SOPs) into prompt sequences… allowing agents with human-like domain expertise to verify intermediate results"（Abstract）；"SOPs outline the responsibilities of each team member, while establishing standards for intermediate outputs."（Sec.1）
- 角色闭集原文："We define five roles in our software company: Product Manager, Architect, Project Manager, Engineer, and QA Engineer"（Sec.3.1）。
- 产出物绑定原文：Product Manager → "formulating a detailed PRD that includes User Stories and Requirement Pool"；**"The structured PRD is then passed to the Architect, who translates the requirements into system design components, such as File Lists, Data Structures, and Interface Definitions"**；Architect → "the Architect agent generates two outputs: the system interface design and a sequence flow diagram"（Sec.3.2）；Engineer → 代码＋executable feedback；QA Engineer → 单测。
- 结构化强制品质："MetaGPT requires agents to generate structured outputs, such as high-quality requirements documents, design artifacts, flowcharts, and interface specifications."（Sec.1）Table 2 能力列含 "PRD generation / Technical design generation / API interface generation"（MetaGPT 全 ✓，对照框架多 ✗）。
- 判定：**「专家席位＝流程节点、且每个席位绑定标准化产出物」在 MetaGPT 中是显式设计核心**——P2 成立，且是文献内最强先例。

### 2.2 ChatDev（R15）——角色绑阶段子任务（instructor/assistant 对）

- "ChatDev segments the software development process into three sequential phases: design, coding, and testing."（Sec.3.1）
- "We divided software development into 5 subtasks within 3 phases, assigning specific roles like CEO, CTO, programmer, reviewer, and tester."（Sec.4 Implementation Details）
- 每子任务＝instructor＋assistant 双席对话："In every subtask, two agents… perform the functions of an instructor and an assistant."（Sec.3.1）
- 注意：论文未逐字给出「CEO→design、CTO→架构」的完整映射表（role→phase 为语境推断）；且后续研究记载其存在 role overstepping/行为漂移（综述级旁证，不承重）。

### 2.3 CrewAI（R16）——任务级绑定（agent↔task↔output 三元组）

- Agent 三要素："Role… Goal… Backstory"（Concepts: Agents）；Task 属性："The agent responsible for executing the task."（agent 字段）＋ "File path for storing the task output."（output_file）＋ "A detailed description of what the task's completion looks like."（expected_output）。
- 即绑定单元＝Task（步骤），不是角色自带节点；"Tasks are assigned to agents based on their roles and expertise"。产出物落点由 output_file/output_pydantic 显式声明。

### 2.4 LangGraph（R17）——节点＝函数，agent 与节点解耦

- "Nodes: Functions that encode the logic of your agents… Nodes and Edges are nothing more than functions they can contain an LLM or just good ol' code. In short: nodes do the work, edges tell what to do next."
- 即**节点是步骤不是席位**；agent 只是节点内可选实现物——与「专家即节点」正交的另一种谱系（席位可脱离节点）。

### 2.5 AutoGen（R18）——对话制，发言序行动态选择

- GroupChat 发言选择："We support several strategies to select the next agent: round_robin, random, manual (human selection), and auto (Default, using an LLM to decide)."（Conversation Patterns）
- 即角色不预绑节点；流程由对话池＋选择器驱动（辅证级）。

### 2.6 OpenAI Swarm（R19）——Agent＋handoffs 原语，无节点概念

- "It accomplishes this through two primitive abstractions: Agents and handoffs. An Agent encompasses instructions and tools, and can at any point choose to hand off a conversation to another Agent."
- 无产出物绑定、无流程节点概念；官方自述教育实验件。

### Q4 结论

**无统一标准（P1 成立），但「席位绑定产出物」有强先例（P2 成立）。** 如实分账：谱系至少三档——①席位绑标准产出物（MetaGPT SOP：PM→PRD、Architect→系统组件/接口定义；ChatDev 角色绑阶段子任务）；②任务级绑定（CrewAI：agent↔task↔output_file）；③席位与节点解耦（LangGraph 节点＝函数；AutoGen 动态发言序；Swarm 无节点概念）。各家自定义、互不兼容，不存在跨框架的绑定规范。

## 三、Q5 证据：ADR/决策记录类产物在 Agent 框架里绑谁

### 3.1 主流软件开发 Agent 框架：无 ADR 类产物定义

- MetaGPT（R14）产出面闭集＝PRD / 系统组件（File Lists, Data Structures, Interface Definitions）/ 接口设计与时序图 / 任务列表 / 代码 / 单测。**通篇无 "architecture decision record"、无 decision log 类产物**——Architect 席位绑定的是「设计文档」，不是「决策记录」。
- ChatDev（R15）design 阶段产物＝自然语言设计规格（"target user, data management, and user interface"，Sec.4.3），无 ADR 类产物。
- CrewAI/LangGraph/AutoGen/Swarm：通用编排框架，无领域产物闭集，更无 ADR 规定（R17/R18/R19 检索面内零出处）。

### 3.2 显式处理 ADR 的 Agent 系统（全部非主流框架，均不采「架构设计席直出 ADR」）

- **MArc（R20，一手承重个例）**：五席团队中 ADR 由**专职第五席**产出——"ADR & Documentation Generation Agent (ADGA): Documents the approved designs and decisions, creating ADRs and filling out the arc42 template"；而架构设计归 ADA（"Architecture Design Agent: Creates the architecture design"）、评审归 ARA。即在该系统内，**ADR 写权恰恰不绑架构设计席**，设计→评审→文档三席分立，且 ADR 落盘以 "approved designs" 为前置（先批准后记录）。
- **MAD-Arch（R21，概念件辅证）**：arbiter agent 汇编 ADR——"an arbiter consolidates the exchange into structured, version-controlled governance artifacts—Architecture Decision Records (ADRs)…"；而 "**A human architect remains the accountable decision-maker at a mandatory approval gate**"。即 ADR 汇编权归仲裁/记录席，架构师居**批准闸口**——与上轮人类业界范式结论（架构师常态在 decider 列）同构，而非作者列。
- 检索面内另有零散社区件（如 architecture-council skill：Architect-Prime 综合席位生成 ADR）——非权威、件套不全，仅登记不引用承重。

### Q5 结论

**主流 Agent 框架对 ADR 归属零规定；仅有的显式先例反而反证「写权归架构师席位」。** MetaGPT 虽把架构设计文档绑给 Architect 席位，但其产出面根本没有 ADR 这一产物；真正把 ADR 作为产物的 MArc 把它绑给专职文档席（ADGA）、以批准为前置，MAD-Arch 让架构师居批准闸口而非汇编席。

## 四、判定：对委托假说逐命题裁决

- **P1（无统一标准）＝成立**。六框架三种绑定谱系并存互斥（§二 Q4 结论），委托假说的「与 Agent 领域专家系统机制没有统一标准有关」作为归因解释**有事实基础**。
- **P2（存在席位绑节点/产出物的先例）＝成立**。MetaGPT 为文献内最强先例（SOP 定义角色闭集＋产出物闭集）；WorkBuddy「专家即节点」处于该谱系之内，机制上不孤立。
- **P3（WorkBuddy 机制定位）＝不可外部判定**。内部系统主张，外部文献无出处，本件只登记。
- **P4（故 ADR 应从架构设计节点出口、写权归架构师席位）＝不成立（推翻）**。三重证据链：
  1. 绑定机制本身不指定绑谁——P1 成立恰恰说明「因为专家即节点，所以要绑某席」无规范依据，选谁绑仍是开放设计；
  2. ADR 人类业界范式（上轮 R1–R13）：创建/拥有归 owner（任何成员），架构师常态在 decider/会签列非作者列；「ADR 本质＝对架构的决策」推不出「记录者＝决策者」——上轮已证记录与决策两权分离是常态；
  3. Agent 框架内 ADR 实证（本轮 R20/R21）：仅有的显式先例把 ADR 写权给专职文档/仲裁席、把架构师放批准闸口——**若真按「专家即节点」在本团队落 ADR 绑定，与业界最贴的绑法反而是「ADR 文档产物绑记录席＋架构师席任批准/会签节点」**，与委托假说的绑法相反。

**一句话总判定：委托假说的前提（无统一标准＋存在绑定先例）如实成立，但其结论方向与两层实证相反——「专家即节点」推不出「ADR 写权归架构师席位」；若采节点绑定，外部证据支持的绑法是「架构设计节点出口设计文档，ADR 记录产物另立文档席/记录席，架构师席位坐在批准位」。**
