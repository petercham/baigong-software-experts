## TL;DR（每问一行结论）

1. **monorepo vs polyrepo**：业界共识是「没有普适答案，判据＝耦合强度＋归属/发布节奏是否分裂＋访问边界」；且**仓结构与部署面是两回事**（Google 单仓照样数千个独立产物）——即「按消费面拆产物、按主题/团队拆仓」是被实证支持的组合。
2. **AI agent 生态分仓**：主流做法是**按「稳定性/变更频率」拆包、按「装配单元」合包**——LangChain 把抽象核（core）/通用编排（langchain）/长尾集成（community）/热门集成（partner 独立包）分层拆；Anthropic 把 skills 独立成仓、agent 应用只是 skills 的一个消费者；CrewAI/GPTs 把 persona/config 资产与代码分离。
3. **bundle＝装配产物**：Helm / Terraform / VSCode / npm 四条成熟链路的共同纪律＝**源仓与分发仓（registry）物理分离＋语义化版本＋Git tag 即版本锁＋产物不可手改＋发布前源一致性校验（clean worktree / digest 比对）**。
4. **persona/知识资产独立维护**：有明确先例——角色卡（TavernAI/SillyTavern V2 spec）就是「persona 作为可移植独立文件资产」的事实标准；RAG 生产实践明确要求「知识流水线与应用/代码流水线分离、索引层可重建、原始层为事实源」；OpenAI 官方把 instructions（行为）与 knowledge（参考材料）划为两类不同资产。

## 问 1：monorepo vs polyrepo 的判据与实证

### 结论

- 判据不是「规模」而是三件事：**共享代码的耦合强度、归属与发布节奏是否分离、访问/合规边界是否需要**。
- **仓结构 ≠ 发布面**：单仓可以产出多个独立版本化产物；多仓也可以统一发布节奏。把「消费面/部署面」和「仓边界」解耦，是业界实证的一致立场。
- 对小规模、紧耦合、单一维护者的资产集，实证立场偏向**先单仓**；只有当某块内容出现「真正独立的发布周期 / 独立归属方 / 独立访问边界」时才拆。

### 证据

|---|---|---|

### 对本案含义

- 本案资产（4 个协作纪律 skill、2 个专家 bundle、门禁脚本、治理记录）目前是**单一维护者＋紧耦合演进＋无独立发布节奏**——按上述判据，「为拆而拆」的多仓化没有实证支撑。
- 但决策者的诉求（专家归专家、技能归技能、图归图、知识归知识、persona 归 persona）本质是**内容主题维度分仓**，而业界对「主题维度分仓」的直接实证立场**未找到先例**；业界实证只支持三类拆仓理由：独立发布节奏 / 独立归属方 / 独立访问边界。→ 架构席需要把「主题分仓」诉求翻译成这三类理由之一才站得住（例如「将来图能被别的装配方复用」＝独立消费面；「经验知识由不同人维护、不同节奏更新」＝独立归属＋独立节奏）。
- 「消费面/部署面」的正确落点应是**装配步与产物版本**，而不是仓边界（Google 单仓多产物、Helm 源仓 vs 发布 repo 都是这个形状）。

## 问 2：AI agent 生态如何分仓维护 agent 定义 / 技能 / 编排 / 知识

### 结论

- 拆包维度普遍是**「稳定性与变更频率」＋「谁维护」**，不是「内容主题」：稳定抽象核沉底、易变集成上浮、热门集成单独成包以获得专属支持。
- **技能（skills）在头部生态里确实是独立仓/独立分发单元**，agent 应用只是它的消费者之一——这与决策者「技能维护技能」的直觉一致。
- **编排（图）与角色（agents）当前普遍与装配单元同仓**，未见「编排图独立成仓」的先例；OpenAI 的做法是把 instructions（行为）与 knowledge（参考材料）明确分成两类资产，间接支持「知识资产与行为资产分离」。

### 对本案含义

- 「技能独立仓」在 Anthropic / Claude Code 生态有直接先例与原生机制（marketplace.json 的 `source` 可跨仓），不需要自研装配器。
- 「编排图独立仓」**未找到先例**。最接近的是 Claude Code marketplace.json（图/清单与组件分离但仍在同一 Git 仓内）与 LangChain partner 包（按维护方拆）。若本案要拆图，等于自创一条业界尚无先例的路径——需要架构席明确其收益来源。
- WorkBuddy 专家包（plugin.json＋agents/＋skills/）与 Claude Code plugin 结构几乎同构；本案若要「维度分仓＋装配」，最省力的先例是 **marketplace 清单指向多仓**，而不是「源仓 → 编译 → 产物仓」。

## 问 3：「bundle＝装配产物、源码按维度分仓、打包步装配」的先例与坑

### 结论

- 该模式在基础设施/编辑器/前端生态是**成熟主流**，四条链路形状一致：**源仓（可编辑、按维度组织）→ 打包步（版本注入＋校验）→ 分发面（registry / 静态 index / marketplace 清单）→ 消费者按版本引用**。
- 关键纪律五条：① 语义化版本＋每次变更必 bump；② **不可变 tag**（发布后 tag 不得移动/删除）；③ 消费者必须**锁版本**（pin tag / version）；④ **禁止手改产物**（产物含签名/清单，篡改即失效）；⑤ **发布前源一致性校验**（clean worktree、HEAD==GITHUB_SHA、二次打包 digest 比对）。

### 对本案含义

- 本案 WorkBuddy 专家包＝可安装 bundle，与 chart / module / vsix 同型；「源按维度分仓＋打包装配」有充分先例，**但先例全部附带五条纪律**，缺任何一条都会退化成业界记录在案的事故（版本漂移、陈旧产物被分发、产物与源不一致）。
- 先例同时给出**拆仓成本**：Terraform 明确列出「跨模块变更要多 PR、依赖管理复杂、更多仓要维护」；monorepo.tools 列出「共享笨重、重复、跨仓改昂贵、工具链不一致」。本案资产量级远小于「50+ 模块」，成本侧权重应更高。
- 最贴合本案的先例其实是 **Claude Code marketplace.json**（清单指向多仓，无编译步）与 **Helm 源/分发分离**（有打包步）。二者取舍点＝本案是否需要「产物不可手改＋版本锁」这一层。

## 问 4：persona / 知识资产独立维护的先例

### 结论

- **persona 独立维护有强先例**：角色卡（character card）就是「persona 作为可移植、独立于任何应用/代码的资产文件」的事实标准（TavernAI 2022 → SillyTavern V2 spec，20+ 应用直接消费）。
- **知识资产与代码/应用分离有强先例**：RAG 生产实践一致要求「离线知识流水线与在线应用流水线分离、原始层为事实源、索引层可重建、知识带 owner/版本/复审日期元数据」。
- 但「persona 仓 / 知识库仓」作为 **git 仓拓扑层面的先例**：未找到直接先例（先例都在「资产文件格式与流水线」层面，不在「git 仓划分」层面）。

### 对本案含义

- 决策者「经验知识（情绪/审美/品味）与 persona/思想框架应解耦独立维护」的直觉，在**资产层**有强先例支撑（角色卡可移植、知识按域归属＋独立复审节律、不可变身份与情境上下文分离）。
- 但先例支持的是「**独立资产＋独立维护节律＋可被多个装配方引用**」，不必然等于「独立 git 仓」。本案最小可验证形态可能是：同仓内独立目录＋独立 owner＋独立版本标注；是否升格为独立仓，取决于是否出现「被别的仓/别的装配方引用」这一消费面事实。

## 对本仓拓扑决策的启示清单（不替架构席做决定）

1. **把「主题分仓」翻译成业界可验证的三条理由之一**（独立发布节奏 / 独立归属方 / 独立访问边界）。翻译不了的维度，先以同仓目录＋owner 标注承载，不升格为仓。（依据：reveneau 决策规则、Terraform 拆仓适用条件「50+ 模块/多团队/合规」、monorepo.tools 自治=隔离）
2. **仓边界与消费面解耦**：想让「图」被别的装配方复用，正确落点是装配清单/产物版本，不是先拆仓。（依据：Google 单仓多产物、Helm 源/分发分离）
3. **依赖方向必须单向**：装配层（专家包/图）→ 能力层（技能）→ 抽象/纪律层；能力层禁止反向引用装配层，否则拆仓后立刻断链。（依据：LangChain 0.2 解除 langchain→community 依赖）
4. **优先借用原生装配机制而非自研打包器**：Claude Code marketplace.json 的 `source` 原生支持跨仓指向（github repo / git URL / npm），WorkBuddy plugin.json 与之同构。这是本案成本最低、先例最直接的「维度分仓＋装配」路径。（依据：SpecWeave、Red Hat Developer）
5. **若引入打包步，五条纪律必须同时到位**（缺一即事故）：semver＋每次变更必 bump；不可变 tag；消费者 pin 版本；产物不入库、不可手改；发布前源一致性校验（clean worktree / HEAD==CI SHA / 二次打包 digest 比对）。（依据：Helm、Terraform、VSIX packaging contract、zhengruan）
6. **版本意图要显式化**：借 Changesets 思路——每次改动附一条「本次要 bump 哪个资产、bump 多少」的意图记录，由工具汇总生成版本，而不是靠人记得改版本号。（依据：javascriptcodex monorepo 篇）
7. **警惕拆仓后的两类已记录失效**：版本漂移（Segment 140 服务）、每仓 CI/门禁/规范重复且各自漂移。本案已有 `tools/` 门禁脚本，拆仓后必须保证门禁在每仓同源生效（复制或引用同一源），否则门禁本身会漂移。（依据：dev.to Segment 案例、codekeep）
8. **persona/知识资产先做「资产级解耦」再谈「仓级解耦」**：按角色卡先例把「不可变身份 / 情境上下文 / lore 知识」分字段分层；按 RAG 先例给知识加 owner／review_date／version／approved_source 元数据；索引/装配产物一律视为可重建派生物，事实源在源 md。（依据：promtable、digitalthoughtdisruption、CSDN 三层、CorpRAG）
9. **决策记录（`.collab/decisions`）与调研（`.collab/research`）本身即知识资产**，业界先例支持其独立于代码演进；但先例同样要求「元数据贴近被描述对象」（Backstage），故不宜把治理记录从被治理的仓里搬走。
10. **未找到先例处需自证收益**：「编排图独立仓」在 LangChain / Anthropic / Claude Code / CrewAI / AutoGen / OpenAI 生态均未见对应做法（AutoGen 未检索到仓拓扑级先例）。若架构席选择拆图，应显式标注为本案自创，并补一条可验证的消费面证据（谁会在不装专家的情况下复用这张图）。
