## TL;DR（皮总四点认知，各一行结论）

1. **persona 与专家耦合维护** → **部分符合**。主流通用 Agent 平台确实把 persona 与角色定义写在**同一文件/同一配置**内（Claude Code subagent 正文、CrewAI role+goal+backstory、Coze「人设与回复逻辑」、GPTs instructions、AutoGen system_message）；但「persona 独立于角色维护」**有明确先例且强度高于本席初判**——① 学术先例：《Persona-Execution Separation》（arXiv:2608.27427，锚点核验 A07 已证实存在）明确提出 persona（instructions/tone/self-presentation）可自由演化漂移、execution 须无面可审计的**架构模式**；② 产品先例：OpenClaw 的 SOUL.md/IDENTITY.md 与 AGENTS.md 是分离文件、Hermes Agent 的 SOUL.md 独立于 AGENTS.md/Skills、GPTs 三分离（instructions/knowledge/capabilities 独立配置项，A10 已核验）、角色卡生态（前序#33-36）。「无拆分实践」这半句不成立。
2. **图与专家耦合是平台差异** → **符合（且 WorkBuddy 属耦合派）**。耦合派：LangGraph（图＝代码，agent 节点内联）、WorkBuddy/Claude Code plugin（bundle 绑定图＋角色）、AutoGen Studio（team JSON 内联 participants）；分离派：Coze（工作流/Bot 是空间资源库独立资源，可被多方引用、联动更新）、Dify（agent 应用可作 agent 节点嵌入工作流，知识库独立）、CrewAI（agents.yaml/tasks.yaml 与 crew 装配代码分离但同仓）。「专门主理人席位控图」的形态未在其他平台找到同构先例（最接近＝CrewAI hierarchical manager / AutoGen GroupChatManager，均为运行时机制而非资产席位）。
3. **经验类知识资产很少落在 Agent 平台** → **部分符合**。平台内知识库（Coze/Dify）普遍是**平台托管运行时资源**而非版本化资产；但「经验知识以版本化资产形态维护并被 Agent 消费」已有两条成型路径：Agent Skills 开放格式（SKILL.md＋references/ 把品味/规范类知识打包成版本控制文件夹，跨 46 个平台/产品消费——采纳面读数经锚点核验 A11，见末节）与 Letta MemFS（git-backed Markdown 记忆仓，带版本历史）。情绪/审美/品味类知识仍以 prompt 内联为主，独立资产化确无主流先例。
4. **维度分仓＋部署期装配编译＝一次开发多平台部署** → **部分可行，无完整先例**。已可移植维度：能力层（MCP，事实标准）、技能/程序性知识（SKILL.md 开放格式被 Claude Code/Codex/Copilot/Gemini CLI/Cursor/OpenClaw 采纳）、项目指令（AGENTS.md，60k+ 项目，Linux Foundation 托管）。平台锁定维度：编排图（Dify DSL 仅 Dify 内闭环，Dify↔Flowise 无转换器）、persona（GPTs instructions 可迁为 skill 但 Actions 丢失；PortSmith 等第三方转换器存在但平台专属功能不迁移）。**「按维度分仓→编译→多平台产物」的装配编译器：未找到先例**；实况是「同一源＋各平台各自目录/包装」（.agents/skills 约定＋symlink），即前序#6「技能内容不变，只有包装变」。

## 问 1：persona 与专家（角色）是否耦合维护

### 结论

- **主流＝耦合**：在「一个角色＝一个定义单元」的平台上，persona 就是角色定义文件的正文/字段，不与角色分离维护。
- **拆分先例存在且成型（v1.1 补强）**：在「一个常驻 agent＝一个 workspace」的平台上（OpenClaw、Hermes），persona（SOUL.md/IDENTITY.md）与操作指令（AGENTS.md）、技能（skills/）、记忆（MEMORY.md/USER.md）是**同目录下的分离文件**，各司其职，且有社区最佳实践明确反对把项目/工作流内容塞进 persona 文件。
- **学术先例（v1.1 新增，出处＝锚点核验 A07）**：《Persona-Execution Separation: An Architecture Pattern for Evolving LLM Agents under Execution Audit》（arXiv:2608.27427，2026-08 提交，含 5 模型/4 供应商受控复现）把「persona 与执行分离」上升为命名架构模式——persona 单主可漂移、execution 无面须审计。这把问 1 的判定从「产品实践有拆分」补强为「产品实践＋学术架构模式双轨有拆分」。注意其分离轴＝**persona vs execution**（信任域分离），与本案「persona vs 角色职责」的分离轴相邻不同构，引用时不得混同。
- 对皮总认知的判别：**「各平台都支持耦合」大体成立；「无拆分实践」不成立**（产品层 OpenClaw/Hermes/GPTs 三分离＋学术层 A07 双重否定）。拆分先例的拆分粒度是「同 workspace 内分文件」或「同配置内分字段」，不是「跨仓/跨资产库分离」——后者（persona 独立仓）仍如前序启示#8 所述：未找到仓拓扑级先例。
- **禁用标注**：外部讨论中流传的 "agentic-workflow 三层模型（Persona/Skill/Codebase）"（含「最小 persona 约 3KB」「五条分离理由」等细节）经锚点核验 A01 **查无实源**（6+ 组检索无匹配），**不得作本节任何判定的依据**；三层分离的方向本身可作「社区设计约定」采纳，但不得引该具名来源。

### 对本案仓拓扑决策的含义

- 皮总「persona 应与 experts 一起维护」在**耦合派平台**（Claude Code/CrewAI/Coze/GPTs——与 WorkBuddy 专家包同构）得到支持：WorkBuddy 席位 MD 里 persona 与角色职责同文件，是业界主流形状，拆成独立 persona 文件反而偏离同构先例。
- 但 OpenClaw/Hermes 给出**另一条被验证的形状**：persona 独立成文件、与操作指令/技能/记忆分层，且社区实践显示混写会导致 token 膨胀与「多重人格」混乱（Hermes 经验帖的翻车案例）。若本案席位 MD 同时承载「身份/语气」与「流程纪律」，该先例支持在**文件内部分层**（分节或分文件），而非必须捆绑成一段。
- 「跨仓维护 persona」仍无先例（前序启示#8 维持）。本案可验证的最小形态＝席位 MD 内 persona 段与流程段分节＋独立复审标注；是否升格为独立资产，取决于是否出现「同一 persona 被多个专家包引用」的消费面事实。

## 问 2：图（编排）与专家的耦合——平台差异矩阵

### 结论

- 编排与角色的关系呈**三档谱系**：① 图＝代码/配置内联（LangGraph、AutoGen team JSON、WorkBuddy/Claude Code bundle）；② 角色与编排**配置分离但同仓**（CrewAI）；③ 图与角色都是**平台内独立资源、互相引用**（Coze、Dify）。
- WorkBuddy「图＋专家捆在一个 bundle、主理人席位控图」＝①档耦合，与 Claude Code plugin 同构（前序#5）；**「专门主理人席位作为资产控图」未找到同构先例**——其他平台的「控图者」都是运行时机制（CrewAI manager agent、AutoGen GroupChatManager、Coze 多 Agent 画布的路由节点），不是可独立维护的资产席位。

### 对本案仓拓扑决策的含义

- 皮总「WorkBuddy 把图和专家耦合在一个 bundle」的判断准确，且这不是孤立设计——Claude Code plugin、LangGraph、AutoGen team JSON 同档。
- 若想让「图」成为可独立维护/复用的维度，**Coze 是最直接的对照**：图（工作流/画布）与角色（Bot）都是空间资源库独立资源、靠引用装配、改一处全联动——证明「图与角色分离维护」在产品平台层面可行，但其代价是平台内闭环（资源不出平台）。
- 「主理人席位控图」在资产层无先例；架构席若保留该设计，应标注为本案自创，或说明其等价物（Coze 路由节点＝图内配置；CrewAI manager＝运行时生成）。
- **图形态的补充对照（v1.1 新增，出处＝`reference-2026-10-24/.discussion/20261024-002.txt` :206，GLM 调研摘要）**：多智能体编排的**状态传递**在 2025 年成熟实践中已收敛为同一形态——LangGraph 共享状态/Checkpointer、AutoGen 黑板模式、Claude Code subagents 的 workspace＋文件引用，共同点＝**大产出落盘为工件（artifact），消息只传引用＋摘要**，由显式状态层承载；纯消息中转大文件被公认为反模式。这与本节「图与角色关系」三档谱系互补：无论图是代码内联还是资源引用，**席间交接的业界共识形态＝artifact 落盘＋传引用**——本案 `.collab/` 落盘交接件与该共识同构，架构席无需自创传参机制。

## 问 3：经验类知识资产落在 Agent 平台的实践

### 结论

- **平台内知识库＝托管运行时资源，非版本化资产**：Coze 知识库/数据库/插件归「空间资源库」，可被同空间智能体/应用引用、独享资源可转移复制到空间库复用——但它们是平台数据库对象，无 git 式版本化/可移植性。Dify 知识库同理（知识流水线独立于应用，但 DSL 导出**不含知识数据本身**）。
- **「版本化知识资产被 Agent 消费」已有两条成型路径**：① Agent Skills 开放格式——官方定位即「把程序性知识与团队/公司特定上下文打包成可移植、版本控制的文件夹」，references/ 放长文档，跨 46 个平台/产品消费（A11 已核验读数）；② Letta MemFS——git-backed Markdown 记忆仓，system/ 下文件常驻提示、其余按需读取，**版本历史可见**。Mem0 亦称每条记忆 timestamped/versioned/exportable。
- **情绪/审美/品味类经验**：现状仍以 persona prompt 内联（Coze 人设面板、Hermes SOUL.md）或外挂文档（Hermes 经验帖用飞书文档做「爆款选题库」知识库）承载；**把此类知识做成独立版本化资产被多 Agent 消费——未找到先例**。皮总「很少落在 Agent 平台上」大体成立，但缺口正在被 Skills/MemFS 形态收窄。

## 问 4：「维度分仓＋部署期装配编译＝一次开发多平台部署」的先例与可行性

### 结论

- **没有任何平台或工具实现「按维度分仓→编译→多平台产物」**。该完整形态：未找到先例。
- 但**分维度的可移植性已有实证**，程度不一：
  - **能力/工具层＝已平台中立**：MCP（Linux Foundation 托管，官方口号 build once and integrate everywhere，2026-07 月下载近 5 亿）。
  - **技能/程序性知识层＝开放格式跨平台采纳**：SKILL.md 开放标准（2025-12-18 发布，锚点核验 A11）被 Claude Code、OpenAI Codex、GitHub Copilot、Gemini CLI、Cursor、OpenClaw 等采纳——agentskills.io Client Showcase 去重实列 **46 个平台/产品**（A11 已核验读数；本席初稿写「30+」为旧读数，已更正）；「写一次、处处可用」成立但有装配摩擦——各工具目录不同（.claude/skills vs .codex/skills vs .agents/skills），靠共享源目录＋symlink/复制对齐；frontmatter 判据经 2026-10-22 调研 v2.1 细化＝**spec 六字段闭集 {name, description, license, compatibility, metadata, allowed-tools}**，跨工具打包/上传路径（claude.ai 上传、Skills API、package_skill.py）含非 spec 字段＝**hard error**（不是静默忽略），本地加载则「ignores a field it doesn't recognize」；故跨平台安全子集＝六字段，name/description 为全场景安全底线。
  - **项目指令层＝跨平台约定**：AGENTS.md（60k+ 开源项目；OpenAI Codex/Amp/Jules/Cursor/Factory 共建；现由 Linux Foundation Agentic AI Foundation 托管；OpenClaw/Hermes 亦读）。
  - **persona/行为层＝部分可移植**：GPTs 退役迁移官方映射＝instructions→skill、knowledge→reference files、**Actions 与所选模型不迁移**；第三方转换器（PortSmith/GPT Migrator/Kit Migration）在 ChatGPT/Claude/Gemini 间搬 instructions＋知识文件，但「GPT Actions、图像生成等平台专属工具无法复制」。
  - **编排图/运行时层＝平台锁定**：Dify DSL（YAML）仅 Dify 自身导入，Dify↔Flowise「没有找到两种格式之间的转换器」，需逐节点重建；LangGraph 代码在 LangGraph 自家四种部署选项间可移植（低-中锁定），但迁往别的框架＝「genuine re-architecture, not a port」（CrewAI 对照语同理反向成立）。
  - **agent 间互操作＝协议层补偿**：A2A（Linux Foundation，Agent Card 能力发现＋任务生命周期）解决「agent 之间怎么协作」，不解决「同一 agent 定义部署到多平台」。
- 最接近「装配编译」的实况＝**「单一事实源目录＋每平台各自包装/目录」**（.agents/skills 约定＋symlink 编排；Red Hat「技能内容不变，只有包装变」，前序#6）＋ Claude Code marketplace.json 跨仓指向（前序#5）。即：**装配靠清单指向与目录映射，不靠编译转换**。

- 皮总的「一次开发多平台部署」目标，**当下可落地的子集**＝技能/程序性知识维度（SKILL.md）＋能力维度（MCP）＋指令维度（AGENTS.md）——这三类源文件本身已是跨平台资产，无需自研编译器；本案 4 个协作纪律 skill 已天然在此列。
- **不可落地的子集**＝编排图与平台专属运行时绑定（WorkBuddy plugin.json 编排图、主理人机制、Coze/Dify 图）——迁平台＝重建，无转换器先例。图维度分仓的收益只能来自「同平台内复用」，不能以「跨平台编译」为卖点。
- 若仍要「装配编译」形态，先例支持的最小版本＝**清单指向＋目录映射**（marketplace.json source 跨仓＋`.agents/skills/` 约定），而非「源仓→编译→产物仓」；后者仅在单一目标平台内成立（Helm 型，前序问3）。

## 对架构设计 v1 的修订建议清单（不替架构席/决策者做决定）

1. **席位 MD 内部分层，而非拆 persona 仓**：按 OpenClaw/Hermes 先例把「身份·语气（persona）」与「操作纪律·流程」在席位 MD 内分节（或席位目录内分文件），并给 persona 段单独复审标注；不升格为独立仓（无先例，前序启示#8）。——回应皮总认知 1：耦合维护照做，但「同文件内分层」是已被验证的改良点。
2. **图维度分仓的论证口径修正**：跨平台「编译图」无先例（问4#5/#6/#8），图分仓的收益论证应限定为「同平台内多装配方复用」（Coze 资源库模式为对照），删除/降级「一次开发多平台部署」中对图维度的期待。
3. **把「多平台部署」目标收窄为三维度**：技能（SKILL.md）、能力（MCP）、指令（AGENTS.md）三类源文件按开放格式写（frontmatter 只用 spec 六字段闭集 {name, description, license, compatibility, metadata, allowed-tools}，跨工具打包路径含非 spec 字段＝hard error；细节下沉 references/），即免费获得跨平台可移植性（采纳面＝46 个平台/产品，A11）；persona/图明确标注平台锁定。
4. **经验/品味知识资产二选一路由**：仅本仓消费 → 版本化 md 目录＋owner/review_date/version 元数据（Letta MemFS/CorpRAG/前序#5 形态）；要跨平台消费 → 打包成 skill 的 references/（Agent Skills spec 形态）。索引/装配产物一律可重建，事实源在源 md（前序#6）。
5. **主理人席位自创标注**：资产级「控图席位」无先例（问2 结论），保留则在架构文档显式标注为本案自创，并给出与运行时机制（CrewAI manager/Coze 路由节点）的差异说明。
6. **装配机制沿用前序启示#4**：优先清单指向（marketplace.json 型 `source` 跨仓）＋目录映射，不自研打包编译器；若引入打包步，前序启示#5 五条纪律同时到位。
7. **检索缺口备案**：OpenClaw/Hermes 为较新项目，本报告以其官方文档镜像＋社区长文交叉比对取证（多源一致）；扣子低代码平台对新注册用户已停开（docs.coze.cn 公告），其资源模型描述以现存官方文档为准，后续版本可能变动。
