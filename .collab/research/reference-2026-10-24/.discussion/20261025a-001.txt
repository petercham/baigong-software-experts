# 两个问题的回答：都对，但都有关键前提

**先给结论**：

1. **方法论沉淀为与专家绑定的 Skills 包——应该做，且这是 2026 年 Agent 工程的主流最佳实践。但"绑定"的粒度要区分：方法论进 Skill，角色身份和红线留在 Agent 定义里。把方法论写进人设正文是"重人设、轻技能"，正好和当前最佳实践相反。** 

2. **审美/品味用 RAG 案例库辅助——应该做，但 RAG 只解决"看过什么"，不解决"为什么好"。Ontology 负责后者。两者是互补关系，不是替代关系。** 只用 RAG 会得到一个"见过很多好作品但说不出为什么好"的 Agent；只用 Ontology 会得到一个"能说清规则但没见过好作品"的 Agent。

## 一、方法论沉淀为 Skills 包：最佳实践已经很明确

### 1.1 Skills 的定位正好是"方法论"

Anthropic 对 Skills 的定义说得很直白：**Skills 是"岗位操作手册"，把专业经验、工作流程和偏好设置持久化沉淀下来**，解决的是"专业流程无法被结构化地沉淀和复用"的问题，不是模型智能不足的问题。Skills 给出的答案是：用一个带 `SKILL.md` 的文件夹，把流程、代码、模板和示例打包成可按需调用的能力单元。

对比 System Prompt：System Prompt 是全量加载、埋在对话历史里、无法审计回滚、依赖措辞且天然漂移；Skills 是按需加载、文件可 Git 版本控制、团队共享、结构固定可回归测试。**方法论属于"这类任务临时打开的操作手册"，不是"每轮对话都该生效的规矩"，所以它应该进 Skill，不应该进人设正文。** 

### 1.2 当前方案的问题：方法论写在人设里，而不是 Skill 里

回到你们的 `aigc-screenwriter.md`。里面写了"钩子理论、每 15 秒小钩子、口语化、时长精确"——这些是方法论，但它们**硬编码在系统提示词正文里**。后果是：

- 每轮对话都加载，不管当前任务是写剧本还是润色台词
- 无法独立版本控制，改一处方法论要动整个 agent 文件
- 无法跨专家复用（美术指导也需要"参考片例分析"的方法，但现在各自写各自的）
- 无法做回归测试（改完不知道行为有没有漂移）

**最佳实践的做法**：把编剧的方法论抽成 `screenwriting-method/SKILL.md`，人设正文只保留"我是编剧、我负责故事结构、我不做分镜"这类身份和边界。Skill 的 `description` 写清楚"什么时候该触发"，正文写"具体怎么做"。

### 1.3 绑定的正确粒度：Agent 持有 Skill 的"引用"，不是"内容"

平凯 Loop 的做法值得直接参照：**角色、技能、记忆三层解耦**——角色管权责边界（系统提示词、知识库访问权限、工具授权），技能管标准化 SOP（一次定义、多处调用），记忆管持续上下文。技能和智能体角色要匹配——代码评审角色配代码审查技能，技术负责人角色配需求拆解和风险跟踪技能，**不要把所有技能都给每个智能体，分配过宽反而看不出专业分工**。

映射到 WorkBuddy：

| 层 | 放什么 | WorkBuddy 对应 |
|---|---|---|
| 角色层（Agent frontmatter + 人设正文） | 身份、边界、"不做什么"、红线 | `name`/`description`/`profession`/三栏表 |
| 技能层（Skills 包） | 方法论、SOP、检查清单、模板、脚本 | `skills` 字段引用的技能名列表 |
| 记忆层（项目圣经 + 案例库） | 项目级风格规约、历史决策、品味案例 | 圣经 SSOT + 资产库 + 待建的品味库 |

**关键设计决策**：Agent 的 `skills` 字段只放**技能名引用**，技能本体放在包内 `skills/` 目录，通过渐进式披露按需加载。这样角色文件保持轻薄，方法论可以独立演进。

### 1.4 一个容易踩的坑：Skill 不是"把方法论写长"

Google ADK 总结了 5 种 Skill 设计模式，其中和创意团队最相关的是 **Reviewer 模式**（按 checklist 打分审查）和 **Pipeline 模式**（多步骤串行 + checkpoint）。编剧的方法论如果写成"你要有钩子、节奏要好"就是废话；写成 Reviewer 模式才可执行——"逐场检查：前 3 秒有无冲突/悬念/利益点？第 15 秒有无新钩子？台词是否口语化（读一遍，卡顿处标记）？"。

**Skill 的核心价值是"可检查的反馈回路"，不是"更长的提示词"。**

## 二、审美/品味用 RAG + Ontology：两者分工，不能只做一个

### 2.1 RAG 解决"看过什么"，Ontology 解决"为什么好"

2026 年 6 月的一篇对比文章说得很清楚：**RAG 按相似度检索文本；Ontology 给 Agent 结构化的实体、关系和受治理的动作。会行动的 Agent 两者都需要——而且你应该拥有这一层，而不是租用供应商的索引。** 另一篇中文文章同样指出：**RAG 是 Agent 的资料检索层，Ontology 才是 Agent 的业务世界。RAG 解决"模型应该看到哪些上下文"，Ontology 解决"业务逻辑是什么、什么算对、什么算好"。** 

映射到短视频团队：

| 问题 | RAG 能回答 | Ontology 能回答 |
|---|---|---|
| "这个画面风格像什么？" | ✅ 检索相似参考图 | ❌ 不擅长 |
| "为什么这个风格在这个平台有效？" | ❌ 检索不到因果 | ✅ 平台-受众-风格关系 |
| "这个剪辑节奏对不对？" | ✅ 找相似节奏案例 | ✅ 节奏规则 + 案例对照 |
| "这个选题值不值得做？" | ❌ 只能找到类似选题 | ✅ 选题-受众-生成可行性关系 |

**审美不只是"见过好东西"，还包括"知道什么场合该用什么、为什么用、什么时候不该用"。** 前者 RAG 擅长，后者需要 Ontology（或至少结构化的规则体系）。

### 2.2 已有的落地参考

**Creative RAG（tdmcp）** 把自己定位为"创意曲目库，不是政策"：本地、版本化、开放授权的作品/艺术家/技术卡片库，索引后可搜索灵感，每个结果携带 `sourceUrl`、`license`、`rightsNotes`。**它刻意做窄——只提供创意上下文（情绪、色板、运动语言、技术名称），不做决策，不决定什么安全。** 这个边界划定值得学习：**品味库负责"给灵感"，不负责"下结论"**。

**dsh-palate** 做得更进一步：它维护一个**会积累的品味语料库**，流程是"观察 → 暂存 → 确认 → 评审 → 校正"。关键在于**暂存不等于入库**——只有明确的接纳/拒绝决定才会改变语料库，被拒绝的想法保留但不污染品味；评审后记录哪些建议真有用，**只强化被确认有效的原则，品味才会复利滚起来**。这解决了一个关键问题：如果所有案例都无差别入库，品味库会变成垃圾场。

**creative-eye Skill** 提供了可执行的品味训练框架：STUDY → COMPARE → CREATE → EVALUATE，每一步都不许跳。STUDY 阶段要求"具体到 200-tracking on uppercase Didot creates editorial authority 这种程度，不是 it looks good"；COMPARE 阶段先找 3-5 个参考再动手；EVALUATE 阶段用 5 分制打分 + 10 项发布前检查清单。

**Taste-Bench** 则给了一个冷静的基准：微软研究团队量化 Agent 品味，前沿模型最好成绩只有 **59.7%**，且"决定性证据滞后出现的分叉更难，加大推理预算几乎无增益"。这意味着**不要指望 RAG 案例库能把品味拉到人类水平，目标是"比没有案例库好"，不是"达到人类专家"**。

### 2.3 Ontology 在 AIGC 视频团队里长什么样

不需要建一个庞大的全领域本体。**从圣经的风格规约节衍生一个轻量 Ontology 就够了**：

```
实体：风格 / 情绪 / 色板 / 节奏 / 平台 / 受众 / 镜头类型 / 资产类别
关系：
  - 风格 --适用于--> 平台
  - 风格 --引发--> 情绪
  - 情绪 --匹配--> 节奏
  - 镜头类型 --适合表达--> 情绪
  - 资产类别 --属于--> 风格（一致性约束）
规则：
  - 平台 X 的黄金时长区间是 Y（来源：用户提供的平台文档）
  - 风格 A 与风格 B 不得混用（来源：圣经纪忌节）
  - 角色图跨镜头一致性优先级高于单镜头画面质量（来源：圣经验收标准）
```

这个 Ontology 的作用不是"替 Agent 做审美判断"，而是**给 RAG 检索结果提供结构化锚点**——检索到"类似风格"的案例后，Agent 能通过 Ontology 知道"这个风格在目标平台上通常配什么节奏、什么色板、什么镜头语言"，而不是只拿到一堆相似图片然后自己猜。

学术侧的支持：iCARE 把 Ontology 和 Case-Based Reasoning 结合，ontology 负责意图消歧和路由，CBR 负责案例回退，在路由准确率上相对提升 20%。AILMIR 提出 Non-Parametric Case-Based Memory，把成功推理轨迹沉淀为案例记忆，实现领域增量学习且不破坏已有能力。**这两个方向都指向同一个结论：Ontology 管结构，案例管经验，两者叠加才稳。**

### 2.4 落地建议：分层建，不要一次建全

| 阶段 | 建什么 | 怎么建 |
|---|---|---|
| **第一阶段（现在）** | 品味案例库（RAG） | 从已交付项目中筛选"好/坏"案例，按 dsh-palate 的"观察-暂存-确认"流程入库；每个案例带标签（风格/平台/情绪/问题类型）和"为什么好/坏"的一句话判断 |
| **第二阶段（3–5 个项目后）** | 轻量 Ontology | 从圣经风格规约 + 案例标签中提炼实体和关系；先用 YAML/JSON 手工维护，不急着上图数据库 |
| **第三阶段（跨项目复用需求出现后）** | 案例库 + Ontology 联动 | RAG 检索案例 → Ontology 解释关系 → Agent 基于"案例 + 规则"做判断；参考 iCARE 的 CBR fallback 模式 |

**关键纪律**：品味库的写入必须有人工确认闸（和圣经/G1–G5 同理）。**不确认不入库**，否则 Agent 会把偶然一次"用户没反对"当成"用户喜欢"，品味库会漂移。

## 三、回到"是否符合最新最佳实践"：逐条对照

## 四、一句话总结

**方法论应该沉淀为 Skills 包，这是 2026 年已经标准化的最佳实践——但"绑定"是 Agent 引用 Skill，不是 Skill 写进 Agent 正文。审美/品味应该用 RAG + Ontology 双层，RAG 给"看过什么"，Ontology 给"为什么好"；只做 RAG 会得到"见过世面但说不出所以然"的 Agent，只做 Ontology 会得到"满嘴规则但没见过好东西"的 Agent。两件事都可以增量落地，不需要推翻现有的圣经/G1–G5/有界回路结构。**

已按 A-15 出处纪律做了一轮取证（公开来源可核实，个别细节语境在文末标注）。两个问题分开答，先给结论：

①方法论沉淀为 skills 包——对，且这正是当前业界已收敛的标准做法；②直觉/审美/品味用 Ontology/RAG/案例库——方向对，但三者各管一段记忆，别当成一个方案；把它们拼起来恰好是学界共识的「记忆分层」架构，且你们的体系里已经有它的雏形。

一、方法论 → Skills 包：对，按「程序性记忆」定位
业界现状（可核实）：Agent Skills 开放标准（SKILL.md）由 Anthropic 于 2025 年 10 月首发、12 月开放为跨平台标准（agentskills.io），2026 年中已被 30–40+ 平台采用（Claude Code、Codex CLI、Gemini CLI、Copilot、Cursor 等），成为事实标准。标准形态：SKILL.md（元数据+核心指令）＋scripts/（确定性脚本）＋references/（按需加载）＋assets/；三层渐进加载（发现约 100 tokens→激活按需→执行），专治大专家包的上下文膨胀。

对本体系的落点判断：

绑定对象是「席位」不是「拟人名字」——这恰好回答了你上一问：岗位制与 skill 包是天然一对。技能跟着职责走（判据脚本归质检、模板归美术指导），换名字不换技能，技能版本化、可机检、可跨团队复用。A-14「判据脚本随判据 skill 交付」就是这个方向，只是还没做完——v1.3.0「零 skill 绑定、零确定性脚本」的弱点，正解就是把整个方法论层 skill 化。
四起计数失真的根治在 skill 化：我们刚经历的九/十条、九目录、5/6 行、两句/三句，全部是「清单靠人记、清点靠印象」的病。方法论进了 skills 包（检查单=可执行校验脚本、schema=ajv 类机验、回归矩阵=测试用例），这类错误从「靠顾问抓」变成「跑不过去」。
一条安全警戒线（可核实）：有大规模实证研究（4.2 万技能样本）发现约 26% 的 skill 包存在安全漏洞，捆绑可执行脚本的技能风险显著更高。所以 skill 化时「scripts/ 只放确定性脚本、权限最小化、进包前安全审查」应与 A-04 质检执行权的沙箱化纪律（只写 qc/、无生成、无外发）合并成一条统一的脚本治理规约——我们已有的三分册（生产/检验/感知）注册表直接升级为 skill 权限表即可。
二、直觉/审美/品味 → 案例库/Ontology/RAG：对，但要按记忆类型拆开
学界共识框架（CoALA 认知架构，被 2025–26 多篇综述沿用）把智能体记忆分四类，你的两个问题恰好各归其位：

记忆类型	装什么	对应本体系	载体
程序性（怎么做事）	方法论、判据、流程	席位 JD、SOP、检查单	Skills 包（问题①）
语义性（共识与规则）	术语、分类学、平台规则、风格词汇	圣经风格规约体系、market facts、platform-rules-index	Ontology/RAG
情景性（发生过什么）	决策案例、接受/否决记录	样张转正/作废、G5 退回理由、变更记录	案例库
工作记忆	当前项目上下文	暂存区＋suspend.json	已解决（A-01）
三点关键判断：

品味的本质是案例类比，不是规则——「符合调性」「有感觉」没法写成判据，但可以写成「上次类似的需求方接受了什么、否决了什么、为什么」。案例推理（CBR）＋ LLM 的结合在 2026 年已有学术实现（如 ontology 引导的 CBR 多智能体框架），形态是：决策时检索相似案例→给推荐＋依据→人来拍。这正是上一轮我说的「专家性缺口」的补法：AI 不凭空有品味，但可以「像持有案例库的人类组织」——老编辑带新编辑靠的就是案例库，只不过他们的案例库在脑子里。
你们的体系已经有案例库的雏形，缺的只是「理由结构化」：gate-log.jsonl（闸道记录）、变更记录、样张沉没登记、G5 退回项对应圣经条款——这些就是情景记忆的原材料。缺的一步：给每次人类确认/否决补一个结构化理由字段（选了菜单哪个、为什么退、改了什么），攒几百条后就是可检索的品味资产。不需要新建系统，需要新建字段和检索入口。
RAG/Ontology 的规模法则（业界经验）：<50 件资料直接塞上下文（context stuffing），50–10k 件用标准 RAG，更复杂的关系才上 Graph RAG/重 Ontology。别一上来建大本体——ontology 的维护成本极高，从轻量词表＋关系开始（风格关键词分类学、资产类别、平台规则索引三样先行）就够。RAG 装规范性知识时必须挂出处（我们已有的「未经核实仅供参考」纪律原样适用——检索来的规则同样可能过时）。
三、是否符合最新最佳实践：符合，且证据链完整
Skills 包：✅ 与 SKILL.md 开放标准（2025-12 开放、2026 年中成事实标准）完全同构，目录结构、渐进加载、脚本确定性三要素都在业界标准里；
案例库/Ontology 辅助决策：✅ 对应 CoALA 记忆分层＋CBR 复兴＋episodic memory 实践（结构化决策日志 + 检索），是 2025–26 的共识方向，非试验性做法；
「更像持有知识库的人类组织」：✅ 这个措辞本身就很准——业界结论恰恰是「决策质量的提升来自可访问的记忆结构，而非模型本身变聪明」。
出处状态标注（A-15 自律）：agentskills.io 标准沿革、目录结构、CoALA 四记忆、检索规模法则——均有可核实公开来源；个别数字（漏洞比例 26%、任务通过率 25%→95% 等）出自单一研究/厂商语境，是量级参考而非定论，入呈报依据前须补锚点。

一句话收束：方法论 skill 化＝把「怎么做事」做成可执行、可版本化、可机检的程序性记忆，绑定席位而非拟人名——这与 SKILL.md 事实标准同构；品味与直觉靠案例库（情景记忆）＋轻量 Ontology（语义记忆）让 AI 在决策时有据可类比——这与 CoALA 记忆分层共识同构。两者合起来，就是上一轮「受控专家性」的工程形态：skills 管确定性、案例管品味、Ontology 管共识，而人类确认闸一个不撤。若皮总认可这个方向，可作为 v1.4.x 之后的「记忆层」扩展项立项——第一步最小：给闸道记录加结构化理由字段，把已有的四起计数教训和样张决策攒成第一批案例。

# 对皮总两问的应询意见（方法论沉淀与案例库架构·设计哲学层）
> **轮次戳**：应皮总垂询的专项咨询答复，非确认轮签字件。此问属 v1.4.0 之后的架构演进议题，不属已冻结的 v1.2 条款范围；本意见不改 R2 任何已签条款，结论若采纳走立项候选，呈皮总拍定。已先行检索 2025–2026 主线实践与最新研究再作答。
---
## 一、总判断
**两问方向都对，符合当前最佳实践主线，但不能按二分法一刀切——正确的切法是四分**：程序性知识→Skills 包（Q1 成立）、关系性知识→Ontology/知识图谱、情境性判断→案例库（CBR 而非泛 RAG）、品味与审美→**人策展的示范检索，不是本体规则**。且一个重要事实：**R2 方案已无意识地把案例库的采集层建完了**（八目录＋manifest 对账＋append-only＋闸道记录＋沉没登记），缺的只是索引与检索层——这两问实际上是在问"要不要把已经埋好的地基接上楼"。
## 二、Q1：方法论是否沉淀为与专家绑定的 Skills 包——**成立，且你们已经在做，只需校正绑定方式**
**方向与最新实践完全同轨。** Anthropic 2025 年 10 月发布 Agent Skills、12 月将其发布为开放标准（agentskills.io，已被 OpenAI Codex、Gemini CLI、Cursor 等 20+ 平台采纳）——形式正是"文件夹化的方法论包"：SKILL.md（指令）＋脚本＋资源，按需渐进加载。这和 v1.4.0 落包的形态（各席 MD＋判据脚本＋工具注册表）是同构的。实践界对此的分工共识很清晰：**Skills 是"可执行、可版本化的操作手册"，适合 SOP、模板化产出、确定性流程**——判据脚本、闸语义、写权归属、SendMessage 契约全部属于此类。
三项已有设计暗合最佳实践，无需改：①A-16 的 MD ≤2500 token 上限＝官方"渐进式披露、context 是公共财"纪律；②append-only＋30 天归档＝Skills 即代码（version＋review＋audit trail）的治理要求；③判据脚本的输入输出契约＝研究实证的 skill 可封装判据——"只有编码了程序性知识且具有清晰输入输出契约的技能包才适合独立执行"。
**需要校正的一点**：绑定单位应是**能力而非人设**。研究明确指出人设化、判断密集的内容打包效果差（现有 curated skills 不总具备契约性质）——所以正确的做法是"编剧席的**剧本结构判据**是一个 skill"，而不是"编剧专家是一个 skill"。这与上一轮我的意见一致：专家性住在判断权里，skill 包住的是可复现的工序；两者分开沉淀，恰是「岗位＋专家」名实问题的技术解法。
## 三、Q2：灵活/审美/品味部分是否用 Ontology 或 RAG 案例库——**方向成立，但技术选型要分开落位，且有三个已知失败模式必须设防**
**框架选择上，你们要的其实是 CBR（基于案例的推理），不是泛 RAG。** "积累案例库、解新问题时参照过往经验、从而更像人类专家"——这正是 CBR 的教科书定义（Retrieve→Reuse→Revise→Retain 四环），2025 年的系统综述表明 CBR 增强的 LLM 代理在推理透明度、领域适应、可问责性上优于 vanilla RAG 和纯 CoT——尤其擅长**定义不良问题**（审美判断正属此类）和提供**基于先例的可解释决策**。
**Ontology/知识图谱的适用面比"品味"窄，用在它真正赢的地方。** GraphRAG 的实证优势在**多跳关系与可追溯性**（事实准确率可翻倍、答案可溯源）——适合：平台规则索引（EU AI Art.50→各平台标识规则的推理链）、资产-实体关系、bible 规约间的依赖图。但品味不是关系推理问题，用本体规则表达审美（"高级感＝低饱和＋大留白"）恰是反面教材——**示范优于描述**：少样本实例对风格一致性的效果显著优于抽象指令（"给 AI 看一篇完美的商务邮件"胜过"写得专业一点"）。你们 G1 风格板＋样张机制在无意识中已经站在了正确的一边。
**三个已知失败模式与对策（案例库方案的必要护栏）**：
| 失败模式 | 机理 | 对策（与现有条款的接口） |
|---|---|---|
| 均值回归 | 检索"最相似案例"→输出趋同→风格漂平 | 多样性感知检索；保留**反例**——你们 A-12 作废样张沉没登记天然就是负案例库，这是很多团队没有的资产 |
| 自我强化闭环 | AI 检索到自己的历史产出→循环固化 | 案例入库须**人策展门槛**——品味把关权在人类手里，这正是上一轮"专业判断通道"的必要性论证：没有人类判断权，案例库只是风格化石的挖掘机 |
| 检索噪声 | 研究发现随机抽样有时竟优于相似度检索 | 案例须带**结构化标注**（场景类型/风格锚点/需求方偏好/成败原因），裸向量库对品味问题信噪比不足 |
## 四、与现有体系的映射：地基已建成，缺的是中间层
这是最值得皮总注意的结论——**R2 的基础设施恰好是 CBR 的 Retain 环节**：八目录（案例采集）＋manifest 对账（案例-产出绑定）＋闸道记录（决策上下文）＋沉没登记（负案例）＋A-18 复盘回流（Revise 环节）。缺的只有三件事：①**案例 schema**（什么算一个案例：需求→约束→选择→结果→人类评语，全部可从现有暂存区组装）；②**索引与检索层**（结构化标注＋混合检索）；③**入库策展判据**（谁批准入库、按什么标准——即上一轮判断权的制度化）。换句话说，这两问的落地成本远低于通常情况，因为采集管道已在八轮纪律中顺带建成。
## 五、建议的目标架构与程序登记
四层分工一句话版：**Skills 管工序（怎么干），Ontology/Graph 管关系（什么和什么相关），案例库管情境（这种情况下上次怎么干的），人类闸管品味（什么是好的）**——四者互相供血：案例库的成功案例提炼成 skill（个别到一般），skill 的执行记录沉淀为案例（一般到个别），本体提供两边的公共词表。
**程序登记（不阻塞 R2→v1.4.0 落包，与上轮两项并档）**：①「方法论 Skills 化」——v1.4.0 落包本身就是第一步，无需立项，建议仅补一条：skill 以能力为单位组织、人设文件只做引用；②「专业判断案例库」（CBR 层）——建议与上轮"专业判断通道"合并为一个立项（通道是出口、案例库是弹药，缺一不可），若立项走一轮三方定向讨论；③本体/GraphRAG——建议缓行至平台规则索引的实际规模超出文档检索能力时再评估，避免为图而图。均入后评估清单，与数字句时间戳复核同列。R2 签字维持有效。
