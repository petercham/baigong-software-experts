# 第二轮意见：先认领歧义，再逐条回答皮总六问

## 〇、对主持人汇总件的歧义认领

汇总件对 DS 立场的归纳**整体准确**，有一处需要精化：

主持人将 DS 的 Q1 立场归纳为「应该做，且这是 2026 年 Agent 工程的主流最佳实践」。这句话本身没错，但**漏掉了限定条件**：DS 第一轮同时说了「绑定＝引用不是内容」，而这一条的实质是——**如果现有架构里专家文件已经写满了方法论，正确动作不是“再加一个 skill 层”，而是“把方法论从专家文件里搬出去”**。这是一个**迁移**问题，不是**新增**问题。皮总在第六问里说「对接必须建立在方向、架构正确清晰的基础上」，这个区分直接影响对接策略：先搬后加，不是先加后搬。这一点在下面的 Q1 和 Q6 里会展开。

其余三方立场与汇总件一致，无其他歧义。

## 一、Q1 专家层与 Skill 层的边界如何界定

**先给可操作的分界线，再给依据。**

边界不在“专家管判断、skill 管执行”这种模糊表述上。2026 年已经收敛出一个更硬的分法，来自 agentic-workflow 的三层模型：**Persona 管「是谁、在乎什么、以什么顺序工作」；Skill 管「具体怎么做」；Codebase/项目上下文管「这里什么算好」**。

把这个分法落到 WorkBuddy 的语境里：

| 层 | 放什么 | 判断标准 | 不应该放什么 |
|---|---|---|---|
| **专家层（Persona）** | 身份、红线、工作顺序、对什么“生理性不适” | **“换一个人来做，这句话也必须一模一样”** | 具体步骤、检查清单、模板、脚本 |
| **Skill 层** | 可复用的流程、判据、模板、schema、回归用例 | **“换一个专家来做同一类任务，也应该用同一套”** | 角色身份、价值观、边界声明 |

agentic-workflow 给出的五条分离理由里，有两条直接命中皮总的问题：

- **Persona 可以很小**：「最小的 persona 约 3KB，本质上就是‘你是一个资深前端工程师，加载这五个 skill，这是你的护栏’。」
- **Skill 可以很大而不膨胀上下文**：「QA backend persona 很小，引用大的 skill；agent 只在真正需要时才加载重文件。」

另一条来自生产级架构的直接证据：**Thin Soul, Fat Skill** 的实测结果是——soul 文件 30 行 YAML 声明身份，skill 插件作为子进程确定性执行，**skill 代码永不进入 LLM**，token 效率提升 83%，且“天然抗注入”。这从工程上证明了：**专家层应该瘦到只够定义“这个人是谁”，方法论和执行逻辑越早搬出上下文越好。**

**一句话边界**：专家层写“我是谁、我不做什么、我以什么顺序看问题”；Skill 层写“这件事按什么步骤做、做到什么算对、用什么工具验证”。

## 二、Q2 Skill 层具体承载哪些东西

按“可执行性”排序，**只放能产生确定性输出的东西**。这不是理论推演，是 MiMo 第一轮说的「四起计数失真的根治在 skill 化」的直接延伸——如果 skill 里放的东西仍然靠人记、靠模型自评，那只是把“人设里的软约束”换了个地方变成“skill 里的软约束”，问题没有解决。

**应该进 Skill 的四类**：

1. **可执行的检查清单**：不是“检查节奏是否合适”，而是“逐场检查：前 3 秒有无冲突/悬念/利益点？第 15 秒有无新钩子？台词读一遍，卡顿处标记”。能写成 if-then 的，不写成形容词。
2. **判据脚本**：S 轨和 V 轨里那些“能机器判的不让模型判”的判据，必须落在 `scripts/` 里，通过 Bash 执行，**源码不进上下文**。Progressive Disclosure 规范明确说「scripts 通过 Bash 执行，其源码永不进入上下文」。
3. **模板与 schema**：脚本表格模板、资产清单 schema、闸道记录的结构化理由字段。**schema 本身就是一种 skill**——它让“填得对不对”可机检。
4. **回归用例**：每次交付后确认“这套判据跑得过”的最小测试集。MiMo 说的“回归矩阵=测试用例”就是这个意思。

**不应该进 Skill 的**：

- 审美判断（“这个画面有高级感”）——这是案例库和人类闸的事，skill 表达不了
- 角色身份和红线（“我是编剧，我不做分镜”）——这是 persona 层的事
- 项目级风格规约（“本项目色板是 XX”）——这是圣经 SSOT 的事，skill 只引用不重复

## 三、Q3 Skill 层是否应该按第一轮讨论的维度做分层或横切

**不建议按“情感/审美/叙事”这类内容维度横切。** 横切维度会导致同一个 skill 被多个专家以不同语义调用，边界重新模糊——这正是岗位化设计试图避免的问题。

**建议按 CoALA 的三类记忆来分，但只取前两类进 Skill 层：**

| CoALA 记忆类型 | 是否进 Skill 层 | 理由 |
|---|---|---|
| **程序性记忆**（怎么干） | ✅ 进 Skill | 可复用、可版本控制、可回归测试 |
| **语义性记忆**（术语/分类/规则） | ✅ 进轻量 Skill 或 Ontology | 平台规则索引、风格关键词分类学、资产类别——MiMo 说的“三样先行”就在这一层 |
| **情景性记忆**（上次怎么干的/什么被接受了） | ❌ 不进 Skill | 进**案例库**，靠检索调用，不靠常驻加载 |

情景性记忆不进 Skill 的理由很硬：情景记忆的本质是**按情境检索**，不是**按流程执行**。GLM 第一轮说的「品味是案例类比，不是规则」，以及「案例库管情境」，指向的就是同一件事。如果把案例塞进 skill，skill 会变成“什么都装”的杂物间，渐进披露的索引也会失去意义。

**分层的正确形态是“两层三域”，不是“按内容横切”**：

```
专家层（Persona）→ 引用 → Skill 层（程序性 + 语义性）
                                ↓ 需要情境时
                          案例库（情景性，检索调用）
```

## 四、Q4 如何让专家在处理不同情感需求场景时具有个性化

**这里需要先把问题拆开：皮总说的“不同情感需求场景”，指的是两种不同的东西，解法完全不同。**

### 4.1 如果是“同一专家在不同情感语境下调整表达方式”

比如编剧在写温情片和悬疑片时语气不同——这是**persona 的调制**，不是 skill 的事。但调制不应该靠把 persona 写胖来实现。HumanPersonaBase 的做法值得参照：persona 有一个**内部状态层**（Inner Shell），通过“调制桥”映射到可观察行为，而 persona 的核心配置保持解耦。落到 WorkBuddy 的最小实现：**在专家文件里加一个“调制参数区”**（比如“本席在温情语境下倾向用短句、留白；在悬疑语境下倾向用断点、信息延迟释放”），这是 persona 的合法内容，不需要新层。

### 4.2 如果是“不同专家对同一情感场景做出不同专业判断”

比如编剧觉得“这里该收”，运营觉得“这里该放”——这不是个性化问题，是**专业视角差异**，应该通过第一轮已经讨论的“专业异议权”来解决，而不是靠给每个专家配不同的情感 skill。

### 4.3 真正需要“情感 skill”的场景

Agent Harness 的 ESC-Skills 实验提供了一个直接证据：**情感支持技能以 SKILL.md 形式加载，在多个 LLM backbone 上显著提升了策略预测准确率和对话级情感状态**，Qwen3.6-Plus 的策略准确率提升 12.06%，Claude-Haiku-4.5 的 BERTScore 从 69.13 提升到 84.03。这说明**“怎么在对话中提供情感支持”是可以 skill 化的**——但它是一个**独立的、按需加载的能力**，不是专家身份的替代品。

**给 WorkBuddy 的建议**：如果未来需要专门的“情感场景专家”（比如做情感类短视频），那个专家的 skill 包里应该包含**情感支持策略 skill**（按 ESC-Skills 的模式），但专家本身的人设仍然只写“我是谁、我关注什么”，不写“我有哪些情感策略”。

**一句话**：个性化靠**persona 的调制参数 + 独立的情感策略 skill** 来实现，不靠把 persona 写成“万能情感演员”。

## 五、Q5 以上核心疑问是否有最佳实践可参照

**有，而且不止一个来源在 2026 年收敛到同一组结论。** 按证据强度排列：

| 最佳实践 | 来源 | 对本仓的直接含义 |
|---|---|---|
| **Persona / Skill / Codebase 三层分离** | agentic-workflow（2026） | 专家层瘦到身份+红线+顺序；方法论进 skill |
| **Thin Soul, Fat Skill** | 生产级架构论文（2026-05），75 agents/16GB，token 省 83% | skill 代码不进 LLM，天然抗注入 |
| **Progressive Disclosure 三级加载** | Anthropic Skills 规范（2026） | 索引常驻、正文按需、scripts 不进上下文 |
| **Persona-Execution Separation** | arXiv 2608.27427（2026-08） | persona 可自由漂移，execution 必须可审计——正好对应“闸道记录保留在 execution 侧” |
| **CoALA 四记忆分层** | Sumers et al.（TMLR 2024，2026 年被广泛采用） | 程序性→Skill，情景性→案例库，语义性→轻量 Ontology |
| **情感支持技能化有效** | ESC-Skills 实验（2026） | 情感策略可 skill 化，但不替代 persona |

**需要诚实标注的一点**：Thin Soul, Fat Skill 的“83% token 节省”来自特定生产环境（75 agents/16GB），不是通用基准；ESC-Skills 的增益幅度因模型而异（弱模型增益更大）。**方向上共识明确，具体数值不可直接移植。**

## 六、Q6 最次要才是如何对接当前开发进度

按“先方向、后对接”的顺序，对接策略可以压缩成一条原则：

> **先做“减法迁移”，再做“加法扩展”；先治已发的病，再补未发的功能。**

**第一步（对接 v1.4.0，不新增架构层）**：把现有专家文件里**已经写成方法论的内容搬进 skill**——编剧的“钩子三段论/口语化规则”、美术的“世界观推导链”、导演的“生成可行性预判”。这不是新建，是**把写错地方的东西挪到对的地方**。MiMo 说的「v1.3.0 零 skill 绑定的弱点，正解就是把整个方法论层 skill 化」，对应的就是这一步。

**第二步（同一批次，零新增成本）**：给闸道记录**加结构化理由字段**。这是 MiMo 和 GLM 第一轮都指向的最小步——案例库的采集管道已经建好了，缺的只是一个字段。这不是“建案例库”，是“让已有记录变得可检索”。

**第三步（等第二步攒够样本再评估）**：轻量 Ontology（平台规则索引、风格关键词分类学、资产类别三样先行）和案例库检索层。GLM 说的「GraphRAG 缓行、本体只在多跳关系真正赢的地方用」，在对接节奏上应该被理解为：**不要在本轮对接里给 Ontology 分配工时**。

**一句话**：v1.4.0 的对接只做两件事——**方法论搬家 + 理由字段**。其余（Ontology、案例库检索层、情感策略 skill）等这两件事跑过 2–3 个项目、有了真实数据再评估。皮总说“对接必须建立在方向架构正确清晰的基础上”，这个方向现在可以拍：**专家层瘦身、Skill 层承载可执行内容、情景记忆留到案例库，分层按 CoALA 取前两类，个性化靠 persona 调制 + 独立情感 skill。** 方向清楚了，对接就是执行顺序问题，不是架构问题。

## 三、皮总六问作答（Q1–Q5 为重点）
### Q1 专家层与 skill 层的边界如何界定
**一条主判据＋三条辅助判据**。主判据来自官方对 skill 与常驻记忆的区分机制——**加载时机决定归属**：常驻每会话的身份/规则→专家层；按需加载、由模型匹配 description 触发的程序→skill 层。arXiv 2607.25032 给出了更精确的工程判据："**谁决定该机制运行、它提供什么保证**"——需要每次必然生效的保证（闸纪律、红线）不能写成概率触发的 skill；允许按场景触发的专业知识才适合 skill 化。
| 判据 | 归专家层（常驻） | 归 skill 层（按需） |
|---|---|---|
| 加载时机 | 每会话必载 | 匹配 description 才载 |
| 换模型/换项目 | 不成立（只在这个人格上成立） | 仍成立（可迁移的方法论） |
| 变更频率 | 稳定（身份定义性） | 持续迭代（可版本化演进） |
| 验证方式 | 无机检（人格评价） | 可机检/可行为评估（skill＝软件制品：单一职责、接口实现分离、低耦合） |
| token 经济 | 占常驻预算（严控篇幅） | 渐进披露三级：metadata→SKILL.md→bundled files |
**红线分层细则**：全局铁律（沉默不算、闸不可跳、不确认不流转、主理人零生产写盘）→专家层常驻——它们需要"每次必然生效"的保证；领域操作禁忌（如"判据脚本禁写生产册"）→随所属 skill 显式声明、随 skill 加载注入。**A-04 接口不动**：放行判定权永远在人类闸——专家层承载"呈证据不判行"的身份纪律，skill 只承载"怎么跑判据"。

### Q3 skill 层是否分层或横切
**横切为主、轻纵向、严禁按角色分层**。三条依据：
1. **横切**：官方 skill 库按能力域组织（文档处理/构建器/设计……），不按使用者角色组织——能力域是稳定边界，角色是问责安排，两者分离正是 Q1 的结论；
2. **轻纵向**：仅保留一层"core（跨域通用工序：判据执行、闸道纪律、暂存契约）vs domain（短视频生产域）"——用命名约定即可，不建硬层级；skill 内部的"分层"由渐进披露天然承担（metadata→正文→引用文件三级），无需另建；
3. **严禁按席位/角色分层**：那会把 skill 变回人设附件，重新耦合工序与人格——跨席位共享能力将被重复注册，MiMo 的"换名字不换技能"利益归零。第一轮三方"绑席位/能力、不绑拟人名"的共识（主持人件 C2）在结构问题上的推论就是：**skill 按能力横切，席位经引用消费**。
CoALA 的语义/情景记忆**不塞进 skill 层**——它们是独立记忆层，skill 层只承载程序性记忆，这是三方的实际共识边界。
### Q4 专家在情感需求场景的个性化
**分解为两个正交维度，各配已验证机制**：
**维度一：专家的稳定个性**（"这位编剧是谁"）——①**人设内核**：价值观/语气/审美倾向的简短声明，专家层常驻（低成本、成熟实践）；②**示例库**：代表作片段作 few-shot exemplars——"示范优于描述"（第一轮已证，官方 Examples pattern 同款：示例传达风格远比形容词有效）；③**自由度分级**：情感/创意场景按官方指引用 high freedom skill（"design, writing, brainstorming 用高自由度"），一致性攸关处才用低自由度——**个性化恰恰要靠 skill 内声明高自由度来获得空间**，这是第一轮"刚性是买来的"论断的技术解法。
**维度二：对需求方的适应**（"这位需求方吃哪套"）——④**偏好档案**：从闸道确认/否决历史提取结构化偏好（即 MiMo 结构化理由字段的直接复用）；⑤**跨会话记忆**：memory 机制已产品化，记"这位需求方上次否决了强反转"。CCS 2025 对用户自建情感支持 agent 的实证研究核心发现即此：个性化情感体验来自**persona 定制＋记忆积累＋关系状态跟踪**三件的组合，而非更强的单次生成。
**诚实校准（不迎合部分）**：个性化让输出"**合调**"，不保证"**动人**"——Taste-Bench 式上限（前沿模型 59.7%）同样压在情感判断上；persona 学术综述亦将情感深度归为 Architecture Layer 的记忆/状态问题，非提示词问题。程序底线不动：个性化建议仍是"呈意见不决断"（A-04），个性化选择发生在确认空间内——这正是上一轮"专业判断通道＋确认空间内裁量"两个通道的用武之地。

Q3 分层还是横切——横切建库，纵切用库
结论：skill 内部按能力域横切组织，不按第一轮讨论维度分层、不按档位分层。

第一轮的维度（程序/语义/情景）是记忆分类，不是 skill 结构——skill 是程序性知识的唯一居所；语义层（平台规则索引、风格词表）进 references/ 文档由 skill 引用；情景层（案例）进八目录数据区由 skill 检索。用 frontmatter 引用它们，不把它们装进 skill 目录；
档位/流程的「分层」发生在专家层（主理人五档路由组装调用顺序），skill 只被流程调用、不复制流程——这正是「横切建库（按能力，一份 skill 多席多档复用）、纵切用库（按流程，在主理人层）」；
批 3b 的五域容器已是横切形态，与业界单一职责、「一能力一 skill」实践一致——结构已对，无须重分层。
Q4 情感需求场景的个性化——四层位点＋一条铁律（全部落已验证机制）
