## 三、皮总六问逐问汇总（三方答案）

### Q1 专家层与 Skill 层的边界如何界定

| 顾问   | 核心答案（L1 原话要点）                                                                                                                                                                                                                                                                                                                                                               |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DS   | agentic-workflow 三层模型落地：「**Persona 管『是谁、在乎什么、以什么顺序工作』；Skill 管『具体怎么做』；Codebase/项目上下文管『这里什么算好』**」（:19）。可操作判据：「**换一个人来做，这句话也必须一模一样**」→专家层；「**换一个专家来做同一类任务，也应该用同一套**」→Skill 层（:25-26）。Thin Soul Fat Skill 实证：「skill 代码永不进入 LLM，token 效率提升 83%，且『天然抗注入』……**专家层应该瘦到只够定义『这个人是谁』，方法论和执行逻辑越早搬出上下文越好**」（:33）。一句话：「专家层写『我是谁、我不做什么、我以什么顺序看问题』；Skill 层写『这件事按什么步骤做、做到什么算对、用什么工具验证』。」（:35） |
| GLM  | 主判据＝**加载时机**：「常驻每会话的身份/规则→专家层；按需加载、由模型匹配 description 触发的程序→skill 层」（:161）。辅助判据三条：换模型/换项目是否仍成立、变更频率（稳定 vs 持续迭代）、验证方式（人格评价 vs 可机检）。**红线分层细则**：「全局铁律（沉默不算、闸不可跳、不确认不流转、主理人零生产写盘）→专家层常驻……领域操作禁忌→随所属 skill 显式声明」（:169）。「A-04 接口不动：放行判定权永远在人类闸——专家层承载『呈证据不判行』的身份纪律，skill 只承载『怎么跑判据』。」（:169）                                                                                        |
| MiMo | 「**边界三则**」：P1 常驻/按需（反向判据：「红线进了 skill＝错——skill 可能未加载、被替换、加载失败，常驻的必须是约束」）；P2 判定/执行（反向判据：「skill 里出现『你可以放行/你可以跳过』＝越界」）；P3 引用/实体（反向判据：「同一方法论人设正文与 skill 双写＝第二真源」）（:241-243）。**冲突裁决**：「专家层与 skill 冲突时专家层赢（红线＞方法论）；skill 加载失败时专家层按降级路径行动（能力声明+降级——延续既有纪律）。」（:244）                                                                                                                  |

**Q1 共识（L2）**：常驻/按需是三方共同主判据（GLM「加载时机」＝MiMo P1；DS「换人必须一模一样」是同一判据的正面表述）。红线与判定权永在专家层、skill 只产出证据与产出物——三方一致。DS「先搬后加」精化：对接动作是**迁移**不是新增。

### Q3 Skill 层是否按第一轮维度做分层或横切

| 顾问   | 结论（L1 要点）                                                                                                                                                                                                                                                                |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| DS   | 「**不建议按『情感/审美/叙事』这类内容维度横切**……横切维度会导致同一个 skill 被多个专家以不同语义调用，边界重新模糊——这正是岗位化设计试图避免的问题」（:60）。按 CoALA 三类记忆「只取前两类进 Skill 层」：程序性✅；语义性✅「进轻量 Skill 或 Ontology」（平台规则索引、风格关键词分类学、资产类别）；情景性❌「进**案例库**，靠检索调用，不靠常驻加载」（:62-70）。正确形态「**两层三域**」：专家层→引用→Skill 层（程序性+语义性）→需要情境时→案例库（:72-78） |
| GLM  | 「**横切为主、轻纵向、严禁按角色分层**」（:182）。横切＝「官方 skill 库按能力域组织……不按使用者角色组织——能力域是稳定边界，角色是问责安排」；轻纵向＝仅「core（跨域通用工序：判据执行、闸道纪律、暂存契约）vs domain（短视频生产域）」一层、**「用命名约定即可，不建硬层级」**；skill 内部「分层」由渐进披露天然承担，「无需另建」（:184）。「CoALA 的语义/情景记忆**不塞进 skill 层**——它们是独立记忆层，skill 层只承载程序性记忆」（:186）             |
| MiMo | 「**横切建库，纵切用库**」（:253）。「skill 内部按能力域横切组织，不按第一轮讨论维度分层、不按档位分层」；第一轮维度「是记忆分类，不是 skill 结构——skill 是程序性知识的唯一居所；语义层（平台规则索引、风格词表）进 references/ 文档由 skill 引用；情景层（案例）进八目录数据区由 skill 检索」（:256）；「批 3b 的五域容器已是横切形态，与业界单一职责、『一能力一 skill』实践一致——**结构已对，无须重分层**」（:258）                      |

**Q3 共识（L2）**：按能力域横切、严禁按角色/席位分层——三方一致（第一轮 C2 在结构问题上的推论）。skill 层只承载程序性记忆；语义/情景是独立层（references/、案例库）。小分歧 N2：语义性记忆的位置——DS「轻量 Skill 或 Ontology」（:67）vs GLM/MiMo「references/ 文档由 skill 引用」（:179/:256）。

### Q4 如何让专家在处理不同情感需求场景时具有个性化（第一轮未覆盖新题）

| 顾问   | 机制分解（L1 原话要点）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DS   | 先拆题：①「同一专家在不同情感语境下调整表达方式」＝**persona 的调制**——参照 HumanPersonaBase 的 Inner Shell＋「调制桥」，最小实现＝「在专家文件里加一个**调制参数区**」（如「温情语境下倾向用短句、留白；悬疑语境下倾向用断点、信息延迟释放」），「这是 persona 的合法内容，不需要新层」（:88）；②「不同专家对同一情感场景做出不同专业判断」＝专业视角差异，走第一轮「专业异议权」，「不是靠给每个专家配不同的情感 skill」（:92）；③真正需要「情感 skill」的场景＝ESC-Skills 实验证据：「**情感支持技能以 SKILL.md 形式加载**，在多个 LLM backbone 上显著提升了策略预测准确率和对话级情感状态，Qwen3.6-Plus 的策略准确率提升 12.06%，Claude-Haiku-4.5 的 BERTScore 从 69.13 提升到 84.03」——但是「一个**独立的、按需加载的能力**，不是专家身份的替代品」（:96-98）。一句话：「个性化靠 **persona 的调制参数＋独立的情感策略 skill**，不靠把 persona 写成『万能情感演员』。」（:100）             |
| GLM  | 两正交维度。**维度一（稳定个性）**：人设内核＋**示例库**（few-shot exemplars，「示范优于描述」，官方 Examples pattern 同款）＋**自由度分级**（「情感/创意场景按官方指引用 high freedom skill……**个性化恰恰要靠 skill 内声明高自由度来获得空间**，这是第一轮『刚性是买来的』论断的技术解法」）（:189）。**维度二（对需求方适应）**：偏好档案（从闸道确认/否决历史提取结构化偏好，即 MiMo 结构化理由字段的直接复用）＋跨会话记忆（:190）。CCS 2025 实证：「个性化情感体验来自 **persona 定制＋记忆积累＋关系状态跟踪**三件的组合，而非更强的单次生成」（:190）。诚实校准：「个性化让输出『**合调**』，不保证『**动人**』——Taste-Bench 式上限（前沿模型 59.7%）同样压在情感判断上……程序底线不动：个性化建议仍是『呈意见不决断』（A-04），个性化选择发生在确认空间内」（:191）                                                                                               |
| MiMo | 「**四层位点＋一条铁律**」（:259）。铁律：「情感个性化只作用于『怎么说、给什么选项、记什么偏好』，**永不作用于『过不过闸、入不入库』**。情绪是需求信号，不是确认的替代品——否则就是橡皮图章的亲和版」（:260）。四位点：①专家层语气区（energy matching：「着急→高效直接／沮丧→冷静结构化／困惑→耐心拆解」）②宿主用户记忆（lightweight user profile：称呼、长期偏好、敏感点）③项目调性层（圣经风格规约的受众/语气字段·「G1 已拍机制，零新增」）④偏好案例档案（按需求方索引的确认/否决理由·「与案例库合并立项」·最小步＝理由字段）（:262-266）。**反谄媚红线**（「本轮调研最硬的实证」）：「OpenAI 2025 年回滚 GPT-4o 更新——『过度迎合用户』是为留住对话而涌现的优化倾向，不是 feature。情感个性化若以『让用户满意』为目标函数，必然滑向讨好；本体系的闸、『不确认不入库』、退出码就是反谄媚的结构件——所以个性化优化的是可预期与被理解感……不是满意度表演」（:267）。诚实边界：「情感推理/共情判断的工程成熟度低（研究与回滚实证并存），不建议做『AI 判断用户情绪并自动调整交付物质量标准』这类承诺」（:269） |

**Q4 共识（L2）**：个性化＝persona 侧（语气/调制参数区/人设内核）＋记忆侧（宿主用户记忆/偏好档案/跨会话记忆）＋skill 侧（高自由度空间/独立情感策略 skill）三处合力，不是单点。铁律共识：只改「怎么说、给什么选项、记什么偏好」，永不碰闸与入库；反谄媚（GPT-4o 回滚实证）为本轮最硬新增风险锚点。三方实证互补：DS＝ESC-Skills（情感策略可 skill 化）、GLM＝CCS 2025（三件组合）、MiMo＝energy matching＋反谄媚（红线）。
