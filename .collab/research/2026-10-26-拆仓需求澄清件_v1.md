## 1. 动机链还原

皮总拆仓意愿的因果链（每条标发言要义＋日期；发言均为 2026-10-26 拍板三及其后续补充）：

### 1.1 现状痛点（为什么要拆）

| # | 痛点 | 发言要义（出处） |
|---|---|---|
| M-1 | **交付物与工具边界不清** | 「skills 怎么是治理工具呢？交付物中当前就是这点边界不清，我才有此一问的」——反对把交付物技能四域定性为"治理工具"；边界混浊是拆仓之问的起点。（拍板三后续补充·2026-10-26） |
| M-2 | **bundle 编译形态与源码维护形态错配** | 「workbuddy 的 experts 其实是图和专家角色和技能 3 维度绑定的设计，必须要在专家包里完成整体的打包编译。而作为开发者维护项目，应该拆开分别维护」——打包编译发生在 bundle（装配面），但维护应按维度（源码面），二者不应混在同一仓边界里。（维度分仓诉求·2026-10-26） |
| M-3 | **跨平台一次开发多平台部署的期待** | 「在图领域，比如 Workbuddy 就是把图和专家耦合在一起的……不同 Agent 平台在这点上差异很大」＋「经验类知识，现在也很少有实践落在 Agent 平台上吧？」——皮总自觉各平台耦合形态不一，期望用维度模块化＋部署期装配来对冲平台差异。（图认知/经验知识认知·2026-10-26） |

### 1.2 拆仓想达成什么（目标态）

| # | 目标 | 发言要义（出处） |
|---|---|---|
| G-1 | **分开维护**：「我的目标是专家专门负责维护专家、技能专门维护技能、将来如果图能解耦则单独维护图」。（维度分仓诉求·2026-10-26） |
| G-2 | **正交维度模块化**：经验知识类（情绪/审美/品味）与 persona/思想框架类即使仍以 skill 形态出现，也应解耦独立维护。（维度分仓诉求·2026-10-26；persona 部分后被本人修正，见 §3 R-5 演变链） |
| G-3 | **部署期装配**：「我之所以建议拆解不同仓，就是方便分开维护，然后在部署的时候通过一套专门的部署方式完成针对不同平台的专家、图、技能的部署前的不同正交维度模块的打包编译，实现一次开发快速兼容部署的目的。」——拆仓的 why 总纲＝「分开维护 × 正交维度 × 部署期打包编译」三段式。（总目标·2026-10-26） |

### 1.3 因果链一句话

边界不清（M-1）＋装配形态与维护形态错配（M-2）→ 按维度拆仓分开维护（G-1/G-2）→ 部署期用专门装配把维度模块重新编译成各平台可安装包（G-3）→ 实现一次开发快速兼容部署。其中 G-3 的「跨平台编译」环节已被【补证·Q4】判定无先例（见 §4 R-7），动机链的起点（分开维护）与中段（维度模块化）成立、终点（跨平台编译装配）需收窄。

### 调研对皮总认知的修正点（显式标出）

1. **装配编译器无先例**：皮总设想的「部署前对正交维度模块打包编译→多平台产物」这一完整形态，业界未找到任何先例；实况＝「同一源＋各平台各自目录/包装」（清单指向＋目录映射，无编译转换）（补证·Q4#8；调研·启示#4）。
2. **图跨平台锁定**：图维度不能以「跨平台编译」为卖点——Dify DSL 仅自家闭环、LangGraph 迁框架＝重构；图分仓的收益只能来自**同平台内多装配方复用**（补证·建议#2）。皮总「不同 Agent 平台在这点上差异很大」的认知本身准确（补证·Q2 三档谱系证实）。
3. **persona「无拆分实践」不成立，但拆分粒度是文件级**：拆分先例存在（OpenClaw/Hermes/GPTs 三分离/A07），粒度＝同 workspace 分文件或同配置分字段；跨仓维护 persona 仍无先例（补证·Q1 结论；调研·启示#8）。皮总 v2「随 experts 维护」的方向与主流同构平台一致，可保留；但「席位 MD 内 persona 段与流程段分节」是已被验证的改良点（补证·建议#1）。
4. **经验知识「很少落在 Agent 平台」大体成立**：平台内知识库多为托管运行时资源非版本化资产；但版本化资产化已有两条成型路径（Agent Skills references/、Letta MemFS）（补证·Q3）。
