## 二、产品定义

### 2.1 产品目标（3 个·正交）

1. **程序确定性**：把「主持人＋外部顾问」讨论轮机制固化为可重复执行的标准程序——轮次推进、三档表态、轮次戳、成稿规则、上报条件全部条款化，任何一次新讨论照此运行（实证基线：十轮零上报零否决，《收口登记》:38）。
2. **记录保真**：确保外部顾问意见从回执到成稿全程可回溯、无合成失真——汇总忠实原话、归属标注、机扫计数取证、append-only、指针只指不搬、引用治理降格规则（实证基线：GLM 对 §五总表签名链终检无失真，009.txt:139；四起计数观察的机扫整改范式，《消歧方案》:102-104）。
3. **决策边界清晰**：明确「顾问层可决」与「必须上报皮总」的边界——顾问一致即成稿、多轮充分讨论仍无法一致才上报；皮总两令类外部指令走「呈请→登记→落地」正规通道（实证基线：005.txt:9 程序基线三方确认；《收口修订呈报》:7 L1/L2/L3 分级）。

## 四、载体比选与建议（核心决策）

### 4.1 比选对象（仓内实物·L1）

- **选项 A：专门 skill**。仓内现存三枚：`deliverables/skills/` 下 `multi-collab`（协作纪律真源，SKILL.md＋references/ 六分件，frontmatter 带 name/description/agent_created/version＋spec-provenance 溯源块）、`object-audit`、`object-build`。
- **选项 B：单立「方案调研讨论主持人」专家（expert 包）**。仓内现存一枚：`deliverables/profiles/aigc-video-team`（plugin.json＋agents/ 七席 MD＋avatars＋settings.json，安装＝放专家目录＋register_expert.py 注册，README.md:37-47）。

### 4.2 四维比选表

| 维度 | 选项 A：专门 skill（如 external-advisor-collab） | 选项 B：单立「方案调研讨论主持人」专家包 |
|---|---|---|
| **载体对** | 机制主体＝流程纪律＋主持工作流（轮次戳/三档表态/C5/并集基准/机扫计数/append-only/L1L2L3/归属标注），与 skill 的提示词层方法论形态同构；multi-collab 先例证明仓内协作纪律类资产即 skill 形态（SKILL.md:24「本器＝协作纪律真源」） | 专家包适合承载**多席位团队**（aigc-video-team 七席先例）；单席专家包会把约八成纪律内容锁进一个角色身份，与机制本质「主持人＋外部顾问两侧共守同一套纪律」错位；且本机制的全部沉淀要点无一条是「角色专业能力」 |
| **用户场景** | 用户（皮总/主理人）需要的是「组织一场外部讨论」的操作手册＋回执模板＋纪律条款；skill 可被任意宿主会话加载，主持人（主理人）即加载者，零召唤成本 | 用户「召唤一个主持人专家」——但讨论的参与者是外部大模型（经皮总人工分发 .txt 回执，R2 稿:242），不是专家包内的 agents；专家包解决不了外部链路，只把主持人身份具象化 |
| **部署形态** | `deliverables/skills/` 体系：SKILL.md（≤2500 token 量级）＋references 平铺分件；有 validate＋回归矩阵＋publish.py 发布链现成基础设施（R2 稿:250-258 同族物料规范） | `deliverables/profiles/` 体系：plugin.json 字段闭集＋settings.json＋8 张头像（512×512 PNG ≤500KB）＋各席 MD ≤2500 token 计数表（R2 稿:250）——物料显著更重 |
| **维护成本** | 纪律条款引用 multi-collab 真源（引用复刻模式，SKILL.md:24），本 skill 只承载外部讨论轮特有条；单一真源、单轨版本 | 须自携全套纪律（＝与 multi-collab 双真源——正是本轮 GLM/MiMo 反复打击的反模式，011.txt:164）或引用 skill（多一层间接）；且专家包与 skill 双轨版本维护 |

### 4.3 建议：**选项 A**（L2，依据如下）

1. **机制本质是纪律不是角色**。十轮沉淀的机制要点（讨论轮机制/三档表态/轮次戳/C5/并集基准/机扫计数/append-only/L1L2L3/归属标注）全部是流程纪律，与 multi-collab 同族；skill 是仓内既定的纪律载体。皮总令本身也把「协作专家席位说明和组织讨论的相关技能」指向 skill 语义（《收口登记》:5）。
2. **外部链路是人工环节，两种载体都无法自动化**。顾问经皮总分发 .txt、轮次口径以皮总文件编号为准（R2 稿:242）——这决定了机制只能是提示词层资产；在此无差异的前提下，skill 加载成本为零，expert 召唤物料成本显著更高（头像/plugin.json/settings，R2 稿:250）。
3. **双真源风险是产品化第一步最该避开的坑**。本轮机制用四起计数问题换来的最重要教训＝「单方清单不闭合、验收物失真、双真源隐患」（011.txt:109、:164；《消歧方案》:35）。若以 expert 包平行承载同类纪律，等于在机制产品化的第一步复刻该反模式。
4. **仓内有形态误配的实证教训**。aigc-video-team 出身记载：「初版误以 skill 形态交付（定性见裁-37④·已撤包除名）」（README.md:27）——反向证明载体选择必须「载体对」优先；本机制的载体对在 skill 侧。
5. **主持人身份的处置**：skill 的 description 触发词即入口（对标 multi-collab SKILL.md:3 的触发词设计），宿主加载后按 skill 内「主持人工作流」执行——主持人职责由工作流条款承载，不需要一个独立 expert 席位。

### 4.4 选项 B 的适用条件（不堵死·L2）

若未来出现以下情形，应重启比选并优先考虑 B：①需要把「主持人」变成可被第三方直接召唤的独立服务（脱离 multi-collab 上下文独立运行）；②主持流程需要挂接专家包特有的工具/权限配置。且届时 B 应从本 skill 衍生（纪律仍归 multi-collab 真源），不做平行建设。

### 4.5 命名与边界建议（L2）

- 命名：`external-advisor-collab`（对齐 multi-collab 命名风格；「external-advisor」点明外部顾问链路，「collab」点明协作纪律属性）。
- 定位：**外部顾问讨论轮机制**——multi-collab 管仓内多席协作纪律（真源），本 skill 只写外部讨论轮特有程序：轮次戳/三档表态回执格式/并集基准/转签程序/皮总上报通道。
- 真源关系：引用复刻——本 skill 涉及内部协作纪律处一律指向 multi-collab，冲突时以 multi-collab 为准（模式对标 SKILL.md:24）。
