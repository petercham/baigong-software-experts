## 三、技术核查：三种常见解法全部无效（有实验）

我没有停在"又发生了一次"，而是去查这个窗口到底能不能堵住。三个实验都在仓外独立临时仓库做，各有对照。

| 方案 | 做法 | 实验结果 | 结论 |
|---|---|---|---|
| **A 钩子内检查** | pre-commit 里读 `git diff --cached --name-only` 比对声明 | 钩子看到 1 件（正确）→ 通过 → **最终 tree 2 件** | **无效**。检查与树构造非原子 |
| **B pathspec 提交** | `git commit -m ... -- <单文件>` | 钩子看到 1 件 → **最终 tree 仍 2 件** | **无效**（反直觉） |
| **C 提交段加锁** | 锁内做 add→check→commit，注入方在钩子内动手 | **最终 tree 仍 2 件** | **仅在全员遵守锁时有效**；任一方直接 `git add` 即失效 |

方案 C 的失效原因值得记下：锁只能约束"知道锁存在的进程"，而注入方是一次裸 `git add`，它不知道也不需要知道锁。

### 一个必须纠正的文档判断

`share/check-staged-declaration.py` 头注现写着：

> 探针定档（票面 §〇-2）：钩子环境内跑 `git diff --cached --name-only -z` 天然继承 GIT_INDEX_FILE——**pathspec 提交只见 next-index 子集视图（天然零误拦）**

这句话在"钩子视图"层面是对的，但它被当成了一项**优点**写下来。而实测的含义相反：钩子只看到子集，于是**它没有能力发现最终 tree 是超集**——这不是"天然零误拦"，是"天然零拦截能力"。

这个措辞偏差很可能是本族缺陷反复续存的认知来源：**大家以为闸能拦，所以每次卷入都被归因为"漏了一道"，而不是"这道在原理上拦不住"。**

## 四、所以真正的解是什么

在 git 的提交模型下（检查必然早于树构造），**没有"提交时拦截"这条路**。剩下的只有两条：

**解一（推荐·成本近乎零）· 把防线从"拦"改成"当场报"。**
加 post-commit 钩子：拿 `git show --name-only --format= HEAD` 与 `FX_COMMIT_DECLARE` 比对，不符则**立即在终端打醒目告警＋追加一行到仓内日志**。不阻止（已落地，阻不了），但让卷入从"事后偶然发现"变成"提交瞬间知道"。

价值点很具体：本会话两例都是我事后翻 `git log` 才发现的（第一例约 3 分钟后、第二例约 12 分钟后），而第二例正是"我还在查第一例的时候就又中了一次"。**当场报能把这段延迟压到零，也就掐掉了递归发生的窗口。**

约 25 行脚本 + 钩子加一行。不改任何纪律条文、不改任何席位的提交方式、零人工负担。

**解二（不建议·成本高且不彻底）· 提交段全局串行。**
包装脚本内加锁，所有人改用包装脚本提交。实验已证：**只要有一方绕过就失效**，而"所有 AI 实例每一次提交都走同一包装"这件事本身无法机检保证。等于用一个新的、需要自觉遵守的纪律去保护另一个需要自觉遵守的纪律。

**解三（可选·与解一叠加）· 收窄单笔声明粒度。**
不治本，但缩小命中面：把"一次提交多个无关件"从常态改成例外。这是纪律调整不是机制改动。

## 五、我的建议与理由

**建议取解一，暂不取解二。**

理由三条：

1. **收益/成本比悬殊**。解一 25 行、零纪律负担、零故障模式；解二要求全员改提交方式，且自带死锁/残留锁/绕行三个新故障面。
2. **它修的是认知偏差**。第三节那句"天然零误拦"是这族缺陷反复的根——每次卷入都被当成"执行不到位"，于是加一道会更严的检查，而检查在原理上无效。**把机制讲清楚，比再加一层更值。**
3. **它把"登记"从人工排查变成自动触发**。本会话两笔卷入登记都是我自己写的，靠翻日志发现。自动告警能让这件事不依赖"主理人今天有没有去查"。

**不同拍法的利害**：

- **取解一**：卷入仍会发生（数量不减），但每笔在提交瞬间暴露，登记成本从"排查 10 分钟"降到"看一行告警"。代价＝多一个钩子脚本要维护，且它只报不拦，**看起来像"没有解决问题"**——这点我要先说清，它确实不减少发生次数。
- **取解二**：理论上能把发生次数压到零，但只在全员遵守时成立；一旦有人绕过，会形成"以为有锁所以不查"的**更危险状态**（比现在更糟，因为现在至少知道没有防护）。
- **不取任何解（维持观察行）**：成本最低，本会话已证明"自愈"可行（两笔登记后内容零损）。但第三例、第四例会继续发生，且每次都要人工发现＋人工登记——**如果哪天没人去查 `git log`，一笔混合笔就会静默留在链上**，事后追溯归属的成本远高于现在。
