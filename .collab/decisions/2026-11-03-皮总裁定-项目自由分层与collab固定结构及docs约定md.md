# 皮总裁定 · 项目自由分层 × `.collab` 固定结构 × docs 约定 md（2026-11-03·裁定三·后生效）

- 开端 HEAD 实测读数＝`2ccc1ce`。
- 皮总原话（2026-11-03）：「也就是说专家团定义的只是每个项目里面 {project_id}/.collab 下面的固定结构，而 {project_id} 下面除了 .collab 以外的都是用户根据项目自由定义的项目分层目录方案，我的建议是让用户在 docs 里面通过一个约定好的 md 文档来描述自己的结构设置，这样我们的工程师席位和 QA 席位就可以根据用户的设计来严格遵循分层约束来写入和校验了，但是如果用户在该 md 里面写入了 .collab 的子目录规范，我们是不认的，只按自己的规范走」

## 一、裁定口径

1. **规范面（专家团定义的闭集）只有三件**：
   - ① `{project_id}/.collab` 下面的**固定结构**——由专家团规范统一定义，每个项目必有、结构不分叉；
   - ② **docs 内约定 md 机制**——用户在项目 `docs` 里通过一个**约定好的 md 文档**描述自己的项目分层目录方案（约定文件名属规范实施细节，由架构席在修正票中提方案、经双席审票确定）；
   - ③ **席位执行规范**——工程师席与 QA 席按该 md 描述的用户结构**严格遵循分层约束来写入和校验**。
2. **自由面**：项目根下除 `.collab` 以外的全部目录＝**用户按项目自由定义**的分层目录方案，专家团规范不预设、不干预其形态。
3. **`.collab` 不可被用户覆写**：用户约定 md 中若写入 `.collab` 子目录规范，**一律不认**，只按专家团自身规范走（执行面/机检面对 md 内 `.collab` 段落应忽略并可按违例处理）。

## 二、效力与承接关系

- **D9（仓重整呈拍件·统一治理结构最小集＋泛化/仓级实例边界）＝本裁定实质裁毕**：泛化规范最小集＝上述三件闭集；项目其余结构不入规范。呈拍简报中 D9 主理人倾向（「定义暂落本仓、是否升泛化待另裁」）被本裁定覆盖——泛化边界已由皮总直接划定。
- **裁定一.3 具象化**：「写域配置随项目走、docs 内专文定义成规范」的承载形态由本裁定明确＝**项目 docs 内的约定 md**。T08 修正票中「写域配置项目化承载缺面」候裁点就此关闭：承载面＝约定 md；门禁机件读该 md 取项目根/交付路径；engineer 可写面＝项目根∪交付（编译、部署）路径；deny＝项目根下 `.collab` 与 `docs` 唯二排除（裁定一.2 不变）。
- **席位权限数据面联动**：`seat-permissions` 类机件的写域判定数据源随项目走（源自约定 md），而 `.collab/**` deny 与 `.collab` 固定结构校验属规范固定，**不受用户 md 内容影响**。
- **对 D1/D2/D3 呈拍口径的影响**：项目子包内部结构＝「固定 `.collab` 结构＋用户自由分层」两段式；跨项目公共区归属（D3）本裁定未直接覆盖，继续候裁。D1 命名名录、D2 归属分组、D4–D8 各点继续候裁不变。

## 二点六、补充裁定 · 仓根物理结构（同日 18:0x·皮总原话要旨）

「"D:\multi-agent-collab-devkits" 就只是一个包含了多个属于开发工具项目的目录，下面除了每个项目名称就不应该再有其他什么公共区了，每个项目完全物理隔离……如果 tools 是所有项目的开发中必须的开发工具，那可以放在公共区域，除了它那就只有几个不同 Agent 分类目录，也可以有一个传统软件项目的分类，然后具体项目可以指定到下面，也就是说"百工软件团队"的实际工作目录应该在 `D:\multi-agent-collab-devkits\{project_type}\{project_id}` 下面，tools 是这个仓的唯一公共工具目录。仓下还可以有一个 README.md 来说明这个包的结构，如果还有其他公共目录的需要的话，再临时决定如何安置。」

口径：
1. **两级路径定形**：项目实际工作目录＝`{仓根}\{project_type}\{project_id}`——仓根下先按 Agent 分类（可含传统软件项目分类）分 `project_type` 目录，其下挂具体项目；**项目完全物理隔离**。
2. **仓根白名单闭集**：`project_type` 分类目录 + `tools/`（唯一公共工具目录，条件＝所有项目开发必需的通用工具）+ `README.md`（说明包结构）。此外不得预设任何其他仓根目录；将来如需其他公共目录＝**临时决定安置**（一事一裁，不预设）。
3. **主理人此前呈报的「公共区（标准工作空间）」方案作废**——皮总明示无「公共区」概念，主理人呈拍时误带概念（登记为呈拍措辞违例，属主理人侧）。
4. 承接影响：D4（tools 放哪）＝已裁（仓根 `tools/` 唯一公共）；D1（子包名单）转两级名录＝分类目录名＋各项目 id 待人类＋主理人定；D2（包分组）被 `{project_type}` 维度吸收（分组＝分类归属）；**D3（跨项目拍板史/研究底稿）原「留公共区」选项随公共区概念消灭而失效**——按白名单闭集＋物理隔离口径，治理记录须归各项目自己 `.collab`；主理人拟按「跨项目案卷按参与项目归档＋仓级 README 索引」处置，若有异议由皮总临时裁定（符合"其他公共需要临时决定"条款）。

## 二点七、补充裁定 · 分类目录命名与交接件两级分流（同日 19:1x·皮总原话要旨）

「software-team 不是正确分类，experts 才是 agents 的类型，所以我建议：agent-expers / agent-skills / softwares。而所谓票包属于开发哪个项目的交接件就放进哪个项目的包内 .collab，或者我觉得可以参考 Mattpocok 的定义，放进 .scratch/tickets 下面，专门服务源于 issues 和自己内部的迭代需求。因为更新会很频繁，虽然我们定义它是属于从架构设计到施工之间的关键节点的交接件，但不属于有必要持久保存或用于分发的交接件，而产品、架构文档都属于适合长期保存和用于分发的交接件，所以进 docs，而分票并不适合。」

口径：
1. **分类目录名录改定**＝`agent-experts`／`agent-skills`／`softwares` 三类（原主理人草案 software-team/agent-skills/collab-system 作废；原话 "agent-expers" 按拼写更正为 `agent-experts` 登记＝主理人引申注明）。experts 是 agents 的类型，不与项目类别混切。
2. **交接件两级分流（新纪律）**：
   - **持久/分发级**＝产品文档、架构文档 → 进项目 `docs/`（长期保存、可分发）；
   - **迭代过程级**＝分票票包（架构设计→施工之间的关键节点交接件）→ **归所属项目**（禁仓级混放），落位二选一待细裁：项目 `.collab/tickets`（现行）或 `.scratch/tickets`（参考 Matt Pocock 定义＝专服务源于 issues 与内部迭代需求的高频更新件）——更新频繁、非持久保存对象。
3. 连带：D3（跨项目案卷）进一步收窄——票包按"属于哪个项目进哪个项目"原则天然归位；跨项目 decisions/research 归属仍按 §二点六.4 口径处置。
