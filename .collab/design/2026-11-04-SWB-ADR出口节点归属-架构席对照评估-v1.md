## 一、三问速答（详证分节展开）

1. **出口映射现状**：SWB 基线里「架构设计」流程节点（节点 2·设计）的出口边校验＝**签字矩阵（表2-3）＋注入面机械定义（dispatch-spec）＋串行闸（B3）**三层，写侧另有 **B5 write-guard（租约＋deny_globs）＋ commit-audit ＋ git pre-commit run-gates 门禁链**。「出口边校验规范审计」在现实现里不是一个单机件，而是这族件的合取。`docs/adr/` 现挂在**架构席写域＋租约通道**下，**不挂在任何流程节点的出口边上**——租约四字段无节点维度（lease-issuer.py L20），节点校验只存在于签字矩阵/注入面层。两条路径当前**不是同一条校验路径**。
2. **「同一出口边校验」主张的机制映射**：已天然覆盖＝写权（seat-permissions architect 行含 `docs/adr/`）、租约签发链（lease-issuer 架构签注必填）、写侧拦截（hooks→write-guard）、席位卡纪律行。**缺位＝四处**：①票型八类无 ADR 类承载（ticket-types.json types 集）；②表2-3/dispatch-spec 节点 2 签字集合＝「架构交付签＋QA 质量属性审计签」两签，产品/QA 会签类职责**在节点 2 行无承载位**（会签形态仅存在于维护行）；③ADR 的变更/修订通道不在 §12 通道闭集任何一类的射程内（四通道＋施工票各有射程，ADR 无归道行）；④ADR 产出工序节点缺失＝已在册缺口（ES2 收口登记 §三之二 定性＝在位缺口·候皮总拍板，本评估不重复判决只指认）。
3. **「专家即节点」前提核**：本仓实现里**席位与节点是两个正交闭集，经「签字集合」间接绑定**——席位＝agents/{seat}.md＋seat-permissions seat_id＋hooks-map agent_type_to_seat＋派发 Agent ID 互验（身份链）；节点＝表2-3 七行＝签字集合行，其成员以**席位名**构成。所以「席位绑定节点」的确切形态＝节点出口边由席位签名把守＋注入面按席位机械装填，**不是**「席位＝节点」的直接同一。该前提在本仓语境下**方向一致、形态需精确化**：写权表（seat-permissions）＝席位可写面闭集，不是节点出口闭集；节点校验不落写侧机件。

## 五、张力清单（如实呈证·不表立场）

1. **出口语义的层级错位张力**：主张中「节点出口」在 SWB＝签字矩阵语义（治理层）；写权落点在 seat-permissions＝席位层语义。两者机器互查通道不存在（租约无节点字段）——「从节点出口」目前无法机检，只能以票面/签字程序体现。
