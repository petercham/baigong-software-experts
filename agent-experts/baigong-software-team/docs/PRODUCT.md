# 百工软件团队 · 产品设计说明书

> 文档性质：产品设计说明书（描述件）。被描述对象＝`baigong-software-team` 专家团包（Team 型多角色专家团）。
> 本件所述机制一律以包内相对路径指向真源（如 `skills/software-orchestration/references/dev-discipline.md`），条款细则以包内各卷为准，本文只做产品视角表述、不复述条文。

## 1. 产品定位

**一句话**：百工软件团队专家团：项目负责人统筹产品经理、架构工程师、开发工程师、质量审计师四席，按固定 SOP 把需求推到可验收交付，每步留证据与判定级别。

**类型**：Team 型（多角色协作团队）。主对话入口为主理人席位（项目负责人·包好用），其余四席由主理人按需编排，用户无需直连任何成员席。

**出身背景**：本包为市场包 fork 自维护——基线＝WorkBuddy 专家中心市场包 `software-company` v1.1.0，fork 后经历本地形态适配、改名与版本升迁，后与旧血脉做身份切割、版本号自 0.1.0 重新起算，版本态为 0.1.36 世代、具体版本以三同源（`plugin.json`、`.codebuddy-plugin/plugin.json`、`bundle.lock` 版本行）现读为准。版本账由仓侧维护、不随包分发；本件只载现行版本态。fork 的意义在于：市场版给协作骨架，本包在其上叠加了本地纪律层（写权边界、交接收口、部署硬门等），纪律卷皆在 `skills/software-orchestration/references/` 包内自包含。

## 2. 目标用户与使用场景

**谁在用**：需要在 WorkBuddy 内把"想法→可用软件"走完一段有质量关卡的交付过程的用户；需要有人替他把需求拆成可验收任务、把交付审出缺口的人。

**拿来干什么**（从席位定义与包门面路由表归纳）：

| 场景 | 典型请求 | 承接形态 |
|---|---|---|
| 需求拆解 | "把这个需求拆成可验收的开发任务，标出依赖、验收判据和预估改动面" | 产品席 PRD／架构席任务分解 |
| 中大型开发 | 多页面/多模块应用、前后端 combined | 🏗️ 标准 SOP 五席全链 |
| 小型开发 | 单页应用、小游戏、工具脚本 | ⚡ 快速模式（工程+QA 两席） |
| Bug 修复 | 明确 Bug 报告（非新功能） | 🔧 BugFix 快捷路径 |
| 审计验收 | "审这份交付或治理报告，按四态判定给结论，列出必须补的缺口" | QA 席独立核验出判词 |
| 市场调研 | 行业/竞品/定价分析 | 产品席研究模式出报告 |
| 讨论会主持 | 组织／主持／收口外部顾问讨论会、编制议题包与决议件 | 主理人席临时兼任主持人，加载 `external-advisor-collab` 技能按该技能程序执行 |

## 3. 能力地图（变更通道与席位派发的路由指针）

主理人收到请求后**首先做路由**：现行路由真源内置于主理人席位 MD（`agents/software-team-lead.md`），为两表——「变更通道路由」表（按变更对象分通道：C1／产品票／规则票／技能票／施工票／维护票）＋「席位派发路由」表（按阶段/动作派对应席位）。本件不复写两表内容，只指真源。

早期"五路工作流判定"形态已退役（口径见 `skills/software-orchestration/SKILL.md` 索引注），对应五个细则卷仍作为 references 细则卷在册、按需加载：

| 能力 | 一句话 | 细则卷 |
|---|---|---|
| ⚡ 快速模式技法 | 单页应用/小游戏/工具脚本等小需求的跳过 PRD/架构直入实现技法（轻工作量现行走维护票） | `skills/software-orchestration/references/quick-mode.md` |
| 🔧 BugFix 快捷路径技法 | 明确 Bug 的定位修复＋回归两步技法 | `skills/software-orchestration/references/bugfix-path.md` |
| 🏗️ 标准 SOP 技法 | 中大型需求的五席逐步派单细则（含分档与审法口径） | `skills/software-orchestration/references/standard-sop.md` |
| 📋 部分工作流技法 | 只取链条一段（仅 PRD／架构评审／代码实现／仅测试／市场调研等六子模式） | `skills/software-orchestration/references/partial-workflows.md` |

## 4. 五席价值主张

| 席位 | 职责一句话 | 对用户的核心价值 |
|---|---|---|
| 主理人（包好用·项目负责人） | 编排者而非执行者：建团队、按两表路由（变更通道＋席位派发，见 §3）、中转所有跨席信息、汇编交付；可临时兼任外部顾问讨论会主持人 | 用户只面对一个入口，换来的是"谁接、什么顺序、每步怎么验收"的持续在线统筹 |
| 产品经理（姜通透） | 把模糊需求写成可施工的 PRD（简单 PRD 默认／完整 PRD 含竞品象限分析），或以研究模式出市场调研报告 | 需求先被界定再被实现——目标、用户故事、P0/P1/P2 需求池、待澄清项一目了然 |
| 架构工程师（顾长远） | 基于 PRD 一次性输出系统设计（方案选型/文件列表/类图/时序图）＋按依赖排序的任务分解（≤5 任务硬上限、首任务必为项目基础设施） | 设计与排期一次成型：工程拿到的是可直接执行的任务列表，不是需要二次翻译的蓝图 |
| 开发工程师（柯会码） | 一票一新鲜实例、票间串行，在当票租约 path 闭集内写（现行工序真源＝lead 席位 MD 席位派发路由行＋`agents/software-team-engineer.md`），完工前做全局跨文件一致性自查（IS_PASS 判定），完工必出回流件 | 交付是完整可用的代码而非骨架；改动有回执清单可逐项对账 |
| 质量审计师（沈得严） | 编写并运行测试，每轮做智能路由判定（源码 Bug 回工程/测试 Bug 自修/全过收工），测试最多 2 轮、遗留问题如实入报告；对回执清单逐件核对交付面纯净性 | 质量结论出自独立判定方：不自己生产所以不给自己放行，2 轮上限换交付节奏、遗留问题不藏 |

## 5. 质量与可审计承诺

产品视角的四组承诺（条款细则以 `skills/software-orchestration/references/dev-discipline.md`、`skills/software-orchestration/references/handoff-discipline.md` 两卷为准）：

- **每步留证据**：SOP 每一步产出带验收判据与判定级别；关键输出要求结构化（表格/Mermaid/JSON），交接件按六字段骨架自包含成文——接手人只拿该件即可行动。
- **判定分级、禁糊账**：工程完工有 IS_PASS 二值判定；QA 每轮有路由判定；收口声明前须跑收口自检五件套（判据清单/逐条证据/三态计数/未绿项/移出项），任一缺项只能报"部分完成"；验收读数按三分账分列，不出"基本通过"式结论。
- **独立核验（fresh eyes）**：交付面纯净性由 QA 席逐件核验，生产方不兼判定方——工程师自证不算绿，QA 漏检才算 QA 未绿项；核验者以空会话接手人视角对终态复核，不沿用生产方的过程假设。
- **租约闸写权模型**：写权按租约闸形态运行——租约签发＋写侧事前阻断＋提交审计三机制（机制名只提名，细则真源＝`skills/software-orchestration/references/dev-discipline.md` 与五席位卡「权限」租约节）。工程师写入集＝当票租约路径闭集，完工回执逐项列出写入清单并与版本库实写面全等对账；非工程席受命向交付面写入时有权且应当拒绝并报主理人改派。

## 6. 非目标与边界

- **不做单代理全能模拟**：主理人严禁跳过正式团队流程、严禁代写任何成员席的专业产出；所有跨席信息流经主理人中转，席位间不得直连。
- **不自行动外部系统**：装配／注册／覆盖插件缓存三类动作一律属部署任务——须独立部署票＋用户明确批准，且走「装配→预览→人类闸→部署」四段闸口链，禁止跳段、禁止人类闸由代理代跑（`skills/software-orchestration/references/deploy-gate.md`）。开发收口不自动附带部署。
- **不设研究席**：调研是各席通用技能而非编制，取证按问题适配席位派执行（`skills/software-orchestration/references/dev-discipline.md` §一）。
- **装配组件闭集外不属本团**：本包装配的外部技能组件锁版本闭集现为六枚——`external-advisor-collab`、`deep-research`、`claim-commitment-governance`、`multi-collab`、`object-audit`、`devkit-tools`，锁引用与性质以 `bundle.lock` components 现读为准（本件只列名＋指向，不复写组件行细则）；六枚之外的技能包不属本包装配范围。
- **不越内容本体判断**：本包交付的是过程质量保障（拆解、设计、实现、质检、审计判定），不对业务内容本体作最终裁决；市场研究产出为带来源的分析建议，决策权保留给用户。

## 7. 交付形态

本包的产品形态＝一条"真源→装配→部署"链条加一条版本账纪律：

- **包面真源**：仓根相对的嵌套 bundle 层 agent-experts/baigong-software-team/ 目录是席位定义与流程域的唯一真源；改席位定义只改真源。
- **装配面派生**：`bundle.lock` 声明组件与版本锁，装配器把包本体＋锁定的外部组件拼成注册态 bundle；装配产物不入任何版本库，缺省输出为与源仓同级的 `<仓名>-build/<bundle名>` 预览面——派生产物，非第二真源。
- **部署四段闸**：装配→预览→人类闸→部署，段段须上游收口；预览态抓手＝本地市场注册挂预览卡，人类真实验证明示通过后部署面才转正（`skills/software-orchestration/references/deploy-gate.md` §五）。
- **版本账纪律**：包版本号在 `.codebuddy-plugin/plugin.json` 与 `bundle.lock` 同源镜像、每变必 bump；组件一律锁不可变 tag；历次变更的版本账由仓侧维护、不随包分发——版本号同时是宿主刷新运行缓存的载体。
