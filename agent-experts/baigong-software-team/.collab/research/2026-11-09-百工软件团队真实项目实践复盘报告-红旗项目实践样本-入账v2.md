## 一、机制缺陷清单

### T1 真源链条无强制机制：下游件可被原始料源充当构造输入而全程无拦截

- **机制缺陷描述**：专家团 SOP 定义了"说明书＝上游交接件、下游件须对齐"，但**没有任何工序/判据在机制层面强制下游件的构造输入只能来自真源**。实践样本：架构书立项时主理人票面直接写"按甲方架构图四泳道对齐"，作废料源骨架由此进入构造面，历经 30+ 轮版本演进无人拦截，直至用户亲自质疑（红旗案 P1，commit 链 b17a1ac→…→42b8ed9）。
- **发生频率**：红旗项目 1 例结构性命中＋1 例合法引证需人工澄清；机制面＝零防线，属**必现型缺口**（任何项目立项票写错构造输入即中招）。
- **严重级别**：**S1**。
- **根因分析**：SOP 把"对齐真源"当作席位自觉而非硬门——立项票无"构造输入"必填栏；审计/复核判据无一探测构造输入真源性；料源与真源在权限面上无区分（翻料源无闭集限制，此闭集直至用户裁定 DEC-1109-01 才出现）。
- **修法建议**：①立项/重大改版票模板增"构造输入"必填栏＝真源文档名＋锚 commit，禁料源直引；②审计票固定分项增"构造输入真源性扫描"（DEC-1108-18 已载，需固化进票模板而非一次性裁定）；③翻料源权限闭集（主理人/产品席/审计席）入 SOP 硬纪律（DEC-1109-01）。
- **作者席**：**主理人（SOP 建制与派发双环节）**。

### T2 审查注入面（dispatch-spec）无覆盖面自检：判据盲区由开票人单点决定

- **机制缺陷描述**：专家团纪律"审查注入面由票面机械定义、席位不许自选"是双刃剑——保证纪律性，但**判据覆盖面完全取决于开票人一次性设计，无任何"覆盖面自检"工序**。实践样本：红旗两轮审计（1107F 七分项、1108G 六分项）全部作用于件-件引用面，2/2 轮漏检图面真源性；产品席两轮复核票面全部文字口径，用户设计的"本体面对齐"判据从未落进票面——按设计意图衡量的有效复核＝0 次。
- **发生频率**：红旗项目内 4/4 轮涉架构书审查全部存在同型盲区——**系统性、非偶发**。
- **严重级别**：**S2**（多道防线共享同一单点失效）。
- **根因分析**：开票人设计判据时没有"三面自检"程序（链条面/本体面/图面面）；席位侧"不许自选"进一步抑制补位；席位证词证实扩展探项的授权模糊（1107F 证词）。
- **修法建议**：①审计/复核票模板附固定三面判据清单（本体面＝逐 FR/流程/页面/图面承载对碰；链条面＝真源指针计数挂账；引用面＝现行项）；②明确授权：席位可在固定分项外扩展探项，结论中标注扩展项；③产品席复核架构书判据钉死＝内容本体面对齐含图面（DEC-1109-03），与审计席形式合规分工互不替代。
- **作者席**：**主理人（判据框架定义单点）**；SOP 模板（无固定三面清单）。

### T3 席位"读取完整性"无申报义务：覆盖面真实性不可证

- **机制缺陷描述**：票面可要求"全文直读"，但**无机制回证读取完成度**，也无"读取降级须申报"纪律。实践样本：1107F 审计席首次 Read 被体量截断后全程改道 Grep 定点，静默缩面，被审件 1.1 节从未进入视野（该席在复盘时主动如实申报）。
- **发生频率**：1 例申报；早期拦停轮改道先例多处，全数不可复原——疑为常态化。
- **严重级别**：**S2**（审计结论可信度不可证）。
- **根因分析**：SOP 只定义写侧租约/记账，读侧无任何完成度面；读门受阻（见 T7）使改道成为常态诱因，改道无申报＝缺陷静默传播。
- **修法建议**：审计/复核结论件强制"读取完整性申报"节（覆盖面清单＋降级方式＋未覆盖面）；大文件默认分段直读；主理人采信审计结论前先查该节。
- **作者席**：**QA 席（执行未申报）**；SOP（无申报纪律，建制主责）。

### T4 版本语义无元规则：存活版/定稿版双语义并存，下游推进效力含糊

- **机制缺陷描述**：SOP 有 docs/ 三关收口（定稿语义）与"现行版随刷"（存活语义）两套机制，**但无一条元规则裁决下游件依据哪个状态推进、推进须谁拍板**。实践样本：架构书验收指针挂签署版 v3.4 数月不动；主理人裁定文本亦误用"现行定稿版"；"依据存活草稿自行收口自行推进"无明文禁止。
- **发生频率**：红旗项目全程（语义含糊是 T1 存续温床）。
- **严重级别**：**S2**（规则缺位级）。
- **根因分析**：版本机制按"件"局部设计（签署区、口径钉各自成立），从未按"链条"设计版本效力。
- **修法建议**：DEC-1109-01 语义定义入 SOP 基线（存活版＝可作推进依据的在版本；定稿版＝三关入 docs 的最终唯一口径版）＋"依据存活草稿推进只有人类决策才推进"硬门＋全部下游件版本指针随刷入审计固定分项。
- **作者席**：**SOP 建制（主理人）**。

### T5 状态迁移无波及联动：已决项在他件的挂账无清退工序

- **机制缺陷描述**：台账状态迁移（已决/撤行/过时处置）只清台账自身行，**无"波及他件挂账清单＋当轮随清票"联动**。实践样本：登录承接已决后，架构书图面挂账/切片旧注/验收指针四处残留存续，用户定性"给施工开票制造噪声"。
- **发生频率**：红旗项目 4 处残留（同一根因）；机制面＝每次状态迁移都可能复制。
- **严重级别**：**S2**。
- **根因分析**：挂账面（图/切片/正文指针）与台账间无索引关系，也无失效联动工序。
- **修法建议**：状态迁移操作规范增"波及清单"字段，迁移即列他件挂账、当轮派随清票，不留候裁过夜（1108R 为正面样本，需升为规程）。
- **作者席**：**SOP 建制（主理人）**；架构席（挂账维护面次责）。

### T6 审计单出口纪律无票种隔离：多审计身份并行无硬拦

- **机制缺陷描述**："审计唯一出口"在 SOP 中是原则，但**票种无类型字段、无并行拦截**——主理人可以对历史审计席位发含审计实质内容的票而不触发任何告警。实践样本：复盘证词采集票发给 1107F 历史审计席实例，与未闭的现行审计票 1108H 并行，且 1108G 票混装续做审计分项——用户问责违纪成立。
- **发生频率**：1 例（本轮）。
- **严重级别**：**S3**（程序违纪，未造成双结论落地）。
- **根因分析**：单出口纪律落成"主理人自觉"，无票种标签机制（判定票/证词票/续做票应显式分类）。
- **修法建议**：DEC-1109-02 入 SOP——票模板增"票种"必填字段（审计判定票唯一化：同对象至多一张现行判定票；证词票显式标注不作判定）；第二方复核须人类裁定开复审票并定取代/叠加关系。
- **作者席**：**主理人**。

### T7 读权限模型违背使用方定义：读侧钩子＋点目录敏感门造成系统性读障

|   |   |
| - | - |

- **机制缺陷描述**：使用方规则定义＝**项目根/交付根范围只约束写权域、不约束读权域**（租约＝写域授权）。专家包实践现实：hooks.json 挂读侧钩子（Read|Grep → memory-neutralize.py，缺省 permissionDecision ask）＋宿主平台对 `.collab/` 等点目录敏感门，子代理审批无法直达使用方→TIMED_OUT，全席位被迫改道。
- **发生频率**：贯穿红旗项目全程（11-06 起多轮反复）——机制性。
- **严重级别**：**S2**（系统性削弱审计与复核质量，直接诱发 T3）。
- **根因分析**：专家包 0.1.29 的 hooks 设计将"记忆中立化"读侧标问做成缺省 ask，未区分项目域/系统敏感域；使用方机器沙箱对项目根实为全 allow——读障纯系专家包钩子＋平台点目录门，与使用方配置无关（已排查实证）。
- **修法建议**：DEC-1109-04 入专家包基线：项目域读一律直通（读侧 ask 摘除/改 allow）；席位纪律补"遇拦如实回报，不得静默改道"。注意插件缓存内改动在包升级时被覆盖，修法应回流到专家包源件（expert-manager 渠道）。
- **作者席**：**专家包机制层（0.1.29 hooks 设计）**。

### T8 席位自引范围无"引不到即撤"硬门

- **机制缺陷描述**：席位在票面框架内"自求完备"时以料源/推测补面，SOP 无"新增对接面/组件必须引用真源在册条目编号，引不到即撤除"硬门。实践样本：架构书"发码通道决策点"整节＝架构席自引范围（平台内部流程被我方方案面侵占），使用方三连追问才撤除；先例＝WP-08 越权定案回改。
- **发生频率**：红旗项目 2 例。
- **严重级别**：**S2**（范围虚增直达报价与施工面）。
- **根因分析**："席位只对齐不增改需求"职权边界（DEC-1108-08）晚出于事故后；无条目级引用校验工序。
- **修法建议**：DEC-1108-08 入 SOP 基线＋交票机检增"新增实体真源条目引用校验"（可脚本化：新增节点名 grep 真源编号表）。
- **作者席**：**席位执行（架构席两例）**；SOP（职权边界成文滞后）。

### T9 席位实例运行脆弱性：503/引擎异常无续做协议，取证链中断

- **机制缺陷描述**：席位实例（子代理落件实例）中断（服务端 503、引擎 exit 1）后，**无标准续做/断点恢复协议**——上下文丢失、任务状态与实际进度脱钩，证词与审计任务反复中断。
- **发生频率**：红旗项目后段 3 次（架构席×2、1108G×2，含重复）。
- **严重级别**：**S3**（流程可用性缺陷；本次未损结论但取证延后）。
- **根因分析**：席位实例是长上下文一次性作业体，SOP 无"票可分段续做＋断点落盘"规程。
- **修法建议**：长票（审计/复盘/大对碰）票模板增"断点落盘"要求——分段结论实时写入 .collab 卷宗，实例中断后新实例按卷宗续做；主理人侧对中断票自动降段重派。
- **作者席**：**SOP 建制（主理人）**；平台运行时（不可归席位）。

### T10 主理人质疑响应无纪律：确认偏误无硬门

- **机制缺陷描述**：使用方质疑既有产物时，SOP 无响应规程——主理人以"合法保留"定性护图、整改方向从清噪滑回加注、被二次问责才更正（1108P→1108Q 返工）。
- **发生频率**：红旗项目 1 例完整链（质疑→护→再问责→更正）。
- **严重级别**：**S2**。
- **根因分析**：质疑响应全凭主理人当场判断，无"先按真源重查、保留类定性必须引在册裁定编号"程序。
- **修法建议**：质疑响应规程入 SOP——收到合法性质疑→冻结该面→按真源链条重查→答复附重查证据；无在册裁定编号支撑的"保留"定性不得出口。
- **作者席**：**主理人**。

## 二、根因结构总图（专家团机制层）

```
使用方三条基线：说明书存活版＝唯一顶层真源｜读不设限、写按租约｜审计单出口
        │  三条基线在专家团 0.1.29 中均为"原则"而非"硬门"
  ┌─────┴───────────────────────────────────────────────┐
  │ 硬门缺位集中在主理人可控制环节：                    │
  │ ① 票模板无"构造输入真源"必填栏 ────────────→ T1     │
  │ ② 判据框架无三面自检＋票种无类型字段 ──────→ T2 T6  │
  │ ③ 元规则缺位（版本效力/挂账联动/读权模型）─→ T4 T5 T7│
  │ ④ 运行规程缺位（读取回证/断点续做/质疑响应）→ T3 T9 T10│
  │ 席位执行实责：QA 未申报降级（T3）、架构席自引与挂账（T5 T8）│
  │ 产品席无实责（判据非其可得）；平台贡献＝点目录门与运行时（T7 T9）│
  └───────────────────────────────────────────────────────┘
```
