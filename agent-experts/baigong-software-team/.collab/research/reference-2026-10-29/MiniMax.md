二、核心工程范式：把蒸馏当编译来做

原始语料 ──[抽取]──> 中间表示 IR ──[编译]──> 规格卡 ──[执行]──> 产出 ──[评测]──> 回补 IR

关键在 IR 的设计，而不是提示词怎么写。三类对象要三种不同的 IR（混用必然失败）：

A. 风格卡（Style DNA）—— 只抓"怎么写"，不抓"信什么"
你知识库里那张 9 轴卡（句子节奏/段落/词汇/语气/论证/比喻/情绪/开头结尾/雷区）方向是对的。需要补的三点：

• 拆成 表达层（表层特征，可机械验证）vs 选择层（在相似场景下选 A 不选 B）

• 每条规则必须绑 锚点原句（正例 + 反例：他常写但此处不这么写的近似表达）。反例是防"AI 腔"的关键，你现有文档只强调正例

• 显式 禁用集（他绝不会做的事）单独成区

B. 技法卡（Craft Card）—— 你现在最缺的一层
风格卡能生成"像他"的句子，但生成不了他的决策。导演/作家的价值在技法层，必须显式建模：

场景类型 → 决策点 → 可选项(2-4个) → 他的选择 + 判据 + 放弃项的理由

这层不可能靠语料统计自动得到，只能靠两种办法：① 逆推成品（从他的成片/成稿反推每个节点的选择）② 结构化访谈/决策点追问（CDM 式）。这是整个方法论里最贵、也最不可替代的一段。

C. 框架卡（Theory Card）—— 一类著作的思想骨架
字段：核心问题 / 底层假设（可证伪的） / 论证链 / 核心概念表 / 适用条件 / 边界与失效场景 / 反例域 / 后续争论与反驳 / 作者自陈局限。

必须先做一个区分，否则做出来的东西两头不讨好：

目标	优化指标	方法倾向
忠实蒸馏（做 exegesis，还原作者本意）	覆盖度 + 忠实度	理性重建、阐释学、细读
可迁移蒸馏（做 transfer，能拿来用）	迁移成功率 + 边界安全	抽象掉案例、剥离作者特有部分

同一本书两张卡不一样。要先说清要哪张。

三、六条能直接抄的工程经验

1. 语料分层并标记来源：作品（可直接学）/ 访谈与创作谈（学意图，最有价值）/ 二手评论与影评（学的是别人的误读，必须打标，否则污染卡片）。

2. 留出集是及格线：N 篇用于蒸馏，M 篇完全留出做验证。没有留出集等于没验证。样本量阈值参考你现有文档的 6000 字门槛，但要加"跨场景 + 跨时期"覆盖维度。

3. 三级证据分级：① 原文可直接证实 ② 跨文本统计推断 ③ 模型补全。第三类必须显式标记，且允许写"证据不足"——这直接接你的"零事实性猜测"硬校验原则。

4. 拒答机制：任一维度证据不够时，卡片该维度写"证据不足/样本不足"，而不是补全。这是最容易被模型违反、也最需要外部硬约束的一条。

5. 语料主题配平：这是从图像领域借来的教训——InstantStyle 解决的核心问题是"content leakage"，做法是从 CLIP 全局特征里减去文本内容特征，只留风格残差。文本侧同理：语料若全是"战争题材"，卡片会长出主题偏好而非风格。主动补齐配平样本，或做减除式蒸馏。

6. 三层评测闭环：① 机械可查的硬指标（句长分布、禁用词命中、功能词分布 vs 原作）② LLM-judge rubric（分维度打分）③ 人工 A/B。发现问题后回补的是 IR 和语料，不是改提示词。

四、导演/视觉类别的特殊性

• 量化维度现成：Bordwell 的电影修辞学、mise-en-scène 分析、Kress & van Leeuwen 视觉语法。导演"品味"可测：平均镜头长度、轴线遵守率、色温/饱和度分布、明暗比、构图习惯（对称/三分/中心）、运动频率、景深偏好、剪辑点分布。

• 参数化路线：风格参考/LoRA（IP-Adapter、InstantStyle、ComfyUI）——但这是训练式，要训练数据和算力；文本式的"规格卡"是免训练路线，二者不冲突，可叠加。

• 别把技法和品味混成一句话："爱用长镜头"是技法；"偏爱疏离的观看距离"是品味（可学但不可照抄成规则）；"反类型片"是立场——立场不该进风格卡，你现有文档那条原则是对的。

三、三个真漏洞（这是"科学吗"的核心答案）

漏洞1：女娲的 30 分主项存在数据泄漏

漏洞2：女娲引用了 46.4% 的论文，却没对自己做元评估

但它的五维评分卡，五个维度全部由 LLM 打分。独立双 agent 只解决了"自证"（同一个 agent 既答题又打分），没解决"LLM judge 本身只有 46.4% 基线"。而且它把"结构完整度"（字段齐不齐、有无诚实边界、反模式清单）交给 LLM 静态检查——这是设计者定规则、设计者写产物、设计者自己检查规则，必然满分，零信息量（循环验证）。

再看发布数据：15 个官方 skill 全员 A 级，89–97 分。这个分布本身就是可疑信号——若测量工具有 46.4% 的准确率，"全 A"更可能反映宽松 rubric + 共同方法偏差，而非真实质量。

漏洞3：仓颉的判定仍是 LLM 单方执行

四、它们真正的盲区（两者共有）

SkillLens 那个75%/25% 的数字（25% 加 skill 比不加还差，negative transfer）恰恰说明这个对照是必要的，而两个项目都没做。

这两个技能合并成一个统一的蒸馏技能合适吗？

一、为什么单体合并一定会坏：三条硬约束

① 验证锚不可通约——这是最致命的一条

仓颉	女娲
锚是什么	原文（source_id + 章节/页码/chunk_id，逐项对应引用）	外部公开事实（该人物真实公开立场）
锚强度	强、可回查、可机械断言	弱、动态、依赖网络来源本身的可信度
门禁能否确定化	✅ 能（validate → gate --min B → 退出码 0/1/2）	❌ 不能，"像不像芒格"没有确定性判定

仓颉的 V2 演练能写 input / expected / observed 三段式并被 json_number(abs_tol) 机械判分；女娲的"立场一致性 30 分"只能靠 LLM judge 读答案再对照人脑里的真实立场。

合并后只有一个结果：门禁被统一到最弱那一档——仓颉辛苦建立的确定性门，被女娲的软判拉平；反过来若强行给女娲做机械断言，只能得到假阳性。

② 风险等级不同，合并后默认路径取高的那个

女娲靠 web 搜公开信息（涉人格权、名誉、"使人误认"）；仓颉靠用户提供的原文（风险主要是表达层著作权）。合成一个 skill 后，默认路径必然带着联网采集这一档风险——你原来可以把两者分开关，现在关不上了。

③ 语料合规性不同，采集方式不可共用

仓颉有硬规定："不要在没有文本的情况下凭记忆蒸馏——宁可停下来问用户要"；女娲是"纯网络搜索（默认）"。一个是"无文本即停"，一个是"无文本即搜"。这是两种相反的失败姿态，合并必然要挑一个当默认。

二、但合并是值得的：收益全在治理层，不在方法层

两边有大量语义同构、可以无损抽取的东西：

可共享项	来源	收益
证据三级标注	女娲「他说过的/别人说他的/我推断的」+ 仓颉 source_id/location	你已经拍定的最佳实践三级证据分层，可直接映射
逃逸/降级路径	两边 if-then 失败模式表（语料不足、上下文不足、成本失控、Agent 冲突、产出互斥）	语义几乎同构，抽出来纯赚
审计留档契约	candidates/+rejected/+coverage-audit.md ↔ references/+FIDELITY.md	统一后专家层/skill 层可一锅端检索治理
阶段骨架	全局理解→多路并行提取→三重验证→构造→关系→压力测试	调度器共用，adapter 填料

关键判断：如果你要的是"任何专家都能用同一条流水线生产"（你专家层正在重构的目标），那你要的是一套蒸馏协议，不是两个 skill。而协议层合并、IR 层分离，正好就是这个形态。

三、建议形态：L0 共享内核 + L1 adapter + L2 validator

distill/
├── SKILL.md                        # L0 协议内核：只做调度与门禁，不含领域判据
├── references/
│   ├── evidence-grading.md         # 证据三级（合并两边同构项）
│   ├── failure-modes.md            # 逃逸路径（合并）
│   └── artifact-contract.md        # 产物目录契约（统一）
├── adapters/
│   ├── person.md                   # 女娲侧：六路采集 / 心智模型 / 表达DNA
│   └── method.md                   # 仓颉侧：Adler / 五维提取 / RIA++
└── validators/
    ├── source-anchor.md            # 仓颉式：机械断言优先，可确定性 gate
    └── public-anchor.md            # 女娲式：LLM judge + 泄漏检查 + 人工卡

IR 保持分离：persona-IR（心智模型/决策启发式/表达DNA/反模式/诚实边界）≠ method-IR（RIA++：R/I/A1/A2/E/B）。验证器保持分离：source-anchor 走硬门，public-anchor 走软门+人工确认。

四、三个"合并已坏"的诊断信号（自查用）

1. IR 串味：persona 卡片开始写"步骤1/2/3"，或 method 卡片开始写"表达DNA/语气" → IR 混了

2. 锚被降级：仓颉的 verify.yaml 不再有 location 可回查位置 → source-anchor 失效

3. 门禁统一到最弱：gate --min B 变成"LLM judge 打了 B 就放行"，机械断言消失 → 确定性丢失

出现任一条，就是合并失败，该退回分层。

五、一个反直觉的补充判断

女娲有个仓颉没有的、不该被合并掉的独特资产：泄漏检查 + 边缘诚实度 + 独立双 agent。仓颉有留出集但没有"表达指纹"和"边缘诚实度"类评测；女娲有这两样但没有留出集。

所以理想形态不是"谁抄谁"，而是交叉嫁接：

• 仓颉的留出集 + 机械断言 → 补进 public-anchor

• 女娲的泄漏检查 + 边缘诚实度 → 补进 source-anchor

这才是"合并"真正能产生的新价值：两套验证器交叉加固后的产物，比各自单独强。而单合并成一体反而会丢掉这个增益。

要我把上面的分层形态落成实际目录 + 骨架文件吗？我建议按这个顺序：

1. 先抽 L0（evidence-grading + failure-modes + artifact-contract）——纯收益、零风险，两个现有 skill 可直接引用

2. 再写两个 adapter（person / method），各自把现有 SKILL.md 的判据迁入

3. 最后交叉加固 validator ——这步动的是验证逻辑，建议你先拍板再动

或者你更想先做最小验证：挑一本方法论书 + 一个人物，用同一套协议各跑一次，对比合并前后的产物差异，用实测决定要不要合并。这个更稳，但慢。
