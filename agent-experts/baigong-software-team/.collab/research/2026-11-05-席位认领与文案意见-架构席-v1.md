## ② 文案意见段（对 `2026-11-05-专家团队介绍卡片审查与改写提案-v1.md` §三）

### 2.1 §3.3 displayDescription（zh 候选）——方向正确，两处措辞建议

候选句把六节点（取证 `skills/sop/references/architecture-v2.9-copy.md` L60 实测「节点 1 需求→2 设计→3 拆票→4 执行→5 发布→6 灰度」）、账本为唯一真相、租约写侧、双席独立审（L147 独立闸词条「当前形态＝第一闸产品席＋QA 席独立复审合议」实测在账）全部上脸，替掉 fork 时代旧句——**准确，支持换代**。

两处措辞意见（以架构席实职能为准）：
1. **「租约写侧校验」是本席唯一生产权的落点，建议保留不删**。提案 L109 的删减预案是「删至『……独立复审。』截尾」——若真触长度上限，被删的恰是租约句。建议删减优先级反过来：**「租约写侧校验」优先于四段链句保留**。理由：四段链在 v2.9 基线已有过渡口径注记（`skills/software-orchestration/references/deploy-gate.md` L33「独立 deploy-gate 四段卷→发布硬门禁二＋灰度机械门禁＋转正代写（四段流程保留为装配运维面）」实测），它是装配运维面；而租约＋写侧拦截（`skills/sop/scripts/lease-issuer.py`＋`write-guard.py` 实测在盘，共 17 件脚本目录）是全队无外部先例的差异化机制，删它最亏。
2. **「机械门禁执法」对宿主读者偏术语**。可改「脚本化门禁」或保留——本席不坚持，属风格裁量，记录备案。

### 2.2 §3.4 tags 换代——一槽建议措辞微调

候选三槽中「软件交付（SOP）」「独立复审与审计」两条准确（后者回指 L147 独立闸＋`docs/PRODUCT.md` L59–61 判定分级/独立核验两行实测）。

「账本治理（写侧门禁）」一条：**机制上账本与写侧门禁是两套实体，不该挤一个括号**——账本面真源＝`state-transition.py`/`reconcile-daily.py` 等状态机脚本，写侧门禁真源＝`write-guard.py`＋租约路径集（`lease-issuer.py`）。括注合并易让读者以为是一件事。建议改「账本与写侧门禁」并列式，或「流程账本」＋把门禁留给 displayDescription。槽数不变，只改措辞。

### 2.3 §3.6 quickPrompts 候选（5＋1）——逐条

1. **第 1 条（标准流程）：「开发票」一词必改。** 在本体系内「开票」＝开任务票据（`agents/software-team-architect.md` L22 写域行「开发票四字段」），但在宿主公开卡片语境，读者第一读法是商业发票——这是本包对外文案最大的歧义雷。建议改「拆成可验收票据」「出任务票」之类。其余「拆任务、串行执行、独立验收、每步留判定证据」各句皆可在盘（串行闸 `serial-gate.py`、收口自检五件套 `skills/software-orchestration/references/handoff-discipline.md` L32），**保留**。
2. **第 2 条（独立复审·三态矩阵）：准确，支持。** 「三态矩阵（覆盖／部分／缺口）」回指 architecture copy L142 实测「产出一律三态覆盖矩阵（✅/⚠️/❌）」——比现行 README L18 旧句「四态判定」更贴盘上实态（四态标注另属交接件 §10 检查面，与复审矩阵不是一物）。
3. **第 3 条（讨论会）／第 4 条（调研）：与两技能 SKILL.md description 一致，保留。** 非本席职能面，无补充。
4. **第 5 条（四段链）：成立但语境要收窄。** 四段链（`deploy-gate.md` L32–37「装配→预览→人类闸→部署……禁止跳段」实测在账）适用装配/发版运维面；标准 SOP 的产品上线走节点 5 发布硬门禁＋节点 6 灰度（architecture copy L60）。候选句「这套改动按四段链上到预览」用于本包自身发版语境准确（提案 §四 传导链即此用法），但若宿主读者拿去指导任意产品上线，会与六节点面打架。**建议句首加限定**，如「本专家团自身的包/系统改动要上线时：按四段链……」。
