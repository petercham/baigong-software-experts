# R5 目录治理最佳实践（res-dir-structure）

## 结论
目录治理**有业界可参照实践，但没有统一的"目录结构总规范"**。业界事实分三层：
1. **硬规范（工具强制，违反即报错）**：只存在于"工具契约目录"——cargo 的 src/tests/benches、MkDocs 的 docs_dir、Sphinx 的 source dir＋conf.py、Turborepo 的包发现 glob。
2. **配置文件声明式**：docs-as-code 工具把"导航/索引"从目录里**抽出来放进配置文件**（mkdocs.yml nav、toctree、sidebars.js）——目录只管存放，展示顺序与层级由配置声明。这是"一级子包根只放 INDEX.md"最接近的业界同构物。
3. **纯惯例（官方明说"不强制"）**：GitHub 根文件（README/CONTRIBUTING 放 root/docs/.github 三处皆可，只是**查找优先级**是硬编码的）、Go 的 cmd/internal（官方称 convention/recommended）、JS 社区布局（原话"not an absolute requirement or enforced by the tools"）、ADR 目录（adr/ 或 docs/decisions/，编号 NNNN 是 MADR/adr-tools 惯例而非标准）。

对"造目录结构"技能：**可机检的判据集中在第 1、2 层＋GitHub 查找优先级这类硬编码规则**；第 3 层只能写成"推荐＋理由"。

## 逐条证据

### 1. GitHub 官方：根文件位置与 README
- A｜https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes
  - "README files typically include information on: What the project does / Why the project is useful / How users can get started / Where users can get help / Who maintains…"（what/why/how 五段论的官方版）
  - "If you put your README file in your repository's hidden `.github`, root, or `docs` directory, GitHub will recognize and automatically surface…"；多份 README 时按 `.github` → root → `docs` 顺序取第一份。**位置是软约定，查找优先级是硬规则。**
  - "A README should only contain information necessary for developers to get started… Longer documentation is best suited for wikis."——**README 只做入口、细节下沉**的官方成文依据。
- A｜https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/setting-guidelines-for-repository-contributors ：CONTRIBUTING 同样允许 root/docs/.github 三处，同样有硬编码优先级。
- A｜https://opensource.guide/how-to-contribute/ ："A project also has documentation. These files are usually listed in the top level of a repository."（只说"通常在顶层"，无 docs/ 硬性要求）
- A｜https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners ：CODEOWNERS 放 `.github/`、root 或 `docs/`，按此顺序取第一份；支持按目录路径声明所有权（`/docs/ @doctocat`）——**目录＝所有权边界**有官方机制。

### 2. src layout / cmd / cargo：规范主体各不同
- A｜https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/ ：src layout 理由是行为性的——"The src layout helps prevent accidental usage of the in-development copy of the code."全文用"helps/requires installation"描述利弊，**无 must**；属"官方建议＋可复现的失败模式"。
- A｜https://go.dev/doc/modules/layout ："it's recommended placing such packages into a directory named `internal`"（internal 的**不可导入性是 go 工具链强制**，目录名本身是惯例）；"A common convention is placing all commands… into a `cmd` directory; while this isn't strictly necessary…"——官方原话区分了 convention 与 necessary。
- A｜https://doc.rust-lang.org/cargo/guide/project-layout.html ："Cargo uses conventions for file placement…"——src/bin、tests、benches、examples 是 cargo 的**自动发现契约**：放对目录零配置，放错要手写 target 配置。规范主体=工具（软强制：违反不报错，但失去自动化）。

### 3. docs-as-code：目录存放与导航声明分离
- A｜https://www.mkdocs.org/user-guide/configuration/ ：`docs_dir` default `'docs'`；"All paths in the navigation configuration must be relative to the `docs_dir` configuration option."；nav 缺省时"alphanumerically sorted, nested list of all the Markdown files… Index files will always be listed first within a sub-section"——**目录自动成导航、INDEX 优先**是工具默认行为。
- A｜https://www.sphinx-doc.org/en/master/usage/quickstart.html ："the root of the 'table of contents tree' (or *toctree*)… a way to connect multiple files to a single hierarchy of documents."——层级由 toctree 声明，不由目录隐式决定。
- A｜https://docusaurus.io/docs/sidebar ："Docusaurus can create a sidebar automatically from your filesystem structure: each folder creates a sidebar category, and each file creates a doc link."（autogenerated 模式）；也可显式 sidebars.js。
- 这个模式的通称是 **docs-as-code**（文档进仓库、进评审、进 CI；导航即配置）。注：本次未找到"docs-as-code"一词的单一权威定义页（见查不到清单）。

### 4. ADR 目录
- A｜MADR 官方 https://adr.github.io/madr/ ："Create folder `docs/decisions` in your project."；"Copy `docs/decisions/adr-template.md` to `docs/decisions/NNNN-title-with-dashes.md`, where `NNNN` indicates the next number in sequence."；"Decisions are placed in the subfolder `decisions/` to keep them close to the documentation but also separate the decisions from other documentation."——**决策记录与文档同区不同子目录**，编号四位连续。
- B｜https://github.com/joelparkerhenderson/architecture-decision-record ：推荐 `adr/` 或 `decisions/` 目录＋**无编号动词短语命名**（choose-database.md）；"Some teams much prefer the name 'decisions' over the abbreviation 'ADRs'."——编号非唯一惯例。
- 注：Nygard 2011 原文（thinkrelevance.com/blog/2011-11-15/...）**现址 404**（thinkrelevance 与 cognitect 镜像均失效），本次仅获二手转述（B｜https://realpython.com/ref/software-engineering-glossary/architecture-decision-record/ ："The convention popularized by Michael Nygard's 2011 blog post and codified by Nat Pryce's adr-tools CLI is to keep each record in doc/adr/… 0001-record-architecture-decisions.md"）。原文引文未能一手核验，如实标注。

### 5. monorepo 布局
- A（论文）｜Potvin & Levenberg, "Why Google Stores Billions of Lines of Code in a Single Repository", CACM 2016, https://cacm.acm.org/magazines/2016/7/204032-why-google-stores- ："Each team has a directory structure within the main tree that effectively serves as a project's own namespace."——目录＝命名空间＋团队边界。
- A（书）｜Software Engineering at Google（O'Reilly, 2020）ch.2.1："Each subtree of the repository can have a file listing the user ids of the 'owners' of that subtree… Each subtree is required to have at least two owners."——**目录子树强制有 owner**。
- A｜Turborepo https://turborepo.com/docs/crafting-your-repository/structuring-a-repository ："We recommend starting with splitting your packages into `apps/`… and `packages/`…"（推荐）；但"Turborepo does not support nested packages… will result in an error."（嵌套包结构**工具报错**＝硬规范）。

### 6. 「目录结构」作为一等对象的规范文档
- 存在**项目级**规范（Turborepo 布局文档、Go module layout、cargo layout、MADR 目录约定），但**未发现跨语言、被广泛承认的"仓库目录总规范"**。最接近的社区件：
- B｜"Anatomy of a JavaScript/Node project"（gist.github.com/tracker1/59f2c13044315f88bee9）：原话自证等级——"While the following structure is not an absolute requirement or enforced by the tools, it is a recommendation based on what the JavaScript and in particular Node community at large have been following by convention."
- 12-Factor App 经查**不涉及目录布局**（其 I. 依赖/VI. 进程等讲构建-发布-运行，不讲 repo 目录）——本次未在 12factor.net 找到目录条款（未单独抓取，标注为未核）。

### 7. README 与索引分工
- 官方成文：见 §1 GitHub About READMEs 的"入口五段＋长文下沉 wiki"。
- B｜"Progressive Disclosure for Documentation"（gptme-contrib skill，claude-plugins.dev/skills/@gptme/gptme-contrib/progressive-disclosure）："Split monolithic docs into: Slim index (~20% of original) - Always included, provides overview + navigation; Detail directories - On-demand loading"；反模式"Deep nesting: Keep to 2 levels max (index + details)"、"Orphan content: Ensure all detail files linked from index"。**注意：这是 AI-agent 文档圈的一手实践（2024+），不是传统文档界标准**；与 Diátaxis（见 R1/R3 队友报告）互补——Diátaxis 管分类轴，progressive disclosure 管深度轴。

## 「规范主体」分类表（沉淀技能时决定判据强度）
| 类别 | 例子 | 违反后果 | 可机检？ |
|---|---|---|---|
| 工具硬强制 | internal/ 不可导入(go)；Turborepo 嵌套包；CODEOWNERS 三处优先级；README 三处优先级；MkDocs nav 路径必须相对 docs_dir | 报错/静默失效 | ✅ 完全可判 |

| 配置文件声明式 | mkdocs nav / toctree / sidebars.js：目录存放与导航分离 | 配置与磁盘不一致→构建告警或死链 | ✅ 可判（nav 路径↔磁盘对账） |

| 纯惯例 | cmd/ 命名；adr/ vs decisions/；apps/packages 命名；JS lib vs src | 无 | ❌ 只能写"推荐＋理由" |

## 对「沉淀成构建期技能」的可行性判断
**可行，且判据可分三档**：
1. **硬判据（机检）**：① 声明式导航与磁盘对账（INDEX/nav 里每个指针指向存在的文件，无孤儿文件——对应 Docusaurus/MkDocs 的构建检查）；② 有 owner 声明才允许新增一级目录（Google owners 文件＋GitHub CODEOWNERS 同构）；③ 工具契约目录名不得自造（若用了 docs-as-code 工具，docs_dir 不得乱改）。
2. **建议判据（有业界失败模式背书）**：④ 入口文件只做 what/why/how＋索引，长文下沉（GitHub 官方）；⑤ 决策记录独立子目录＋连续编号、与文档同区分离（MADR）；⑥ 目录深度 ≤2（progressive disclosure 反模式，B 级）。
3. **不可判（审美/团队习惯）**：目录叫什么名字（deliverables/ vs packages/ vs apps/）、按对象还是按工序分（R3 队友已证两派皆存）、ADR 编号位数。技能里应写成"选项＋各自背书"，不写"必须"。
