## 一、任务 A：五条论断逐条判定

### A1 `description` 触发词超载 —— **判定：不成立（命题所述约束不存在）**

**顾问原话**：规范常见约束是 <200 字符警告、<300 字符错误，且明确 "No list bloat (>3 commas)"。

**出处原文（L1）**

1. `agentskills.io/specification`（官方开放标准）frontmatter 字段表：
   > "`description` | Yes | **Max 1024 characters.** Non-empty. Describes what the skill does and when to use it."
   > "The required `description` field: — **Must be 1-1024 characters** — Should describe both what the skill does and when to use it — Should include specific keywords that help agents identify relevant tasks"
   同页正文另有一句反向证据："The Markdown body after the frontmatter contains the skill instructions. **There are no format restrictions.**"
   → 全文**无** 200／300 阈值，**无**任何逗号数量规则；且"include specific keywords"是**鼓励**而非限制。

2. `code.claude.com/docs/en/skills`（Claude Code 官方文档）：
   > "Put the key use case first: the combined `description` and `when_to_use` text is **truncated at 1,536 characters** in the skill listing to reduce context usage."
   > "`when_to_use` … Appended to `description` in the skill listing and **counts toward the 1,536-character cap**."
   → 真正存在的数字是 **1536 截断**，不是 200/300。

3. `anthropics/skills` 仓内 `skill-creator/SKILL.md`（官方仓一手）：
   > "Note: currently Claude has a tendency to 'undertrigger' skills … To combat this, please make the skill descriptions **a little bit 'pushy'**. So for instance, instead of 'How to build a simple fast dashboard…', you might write '…**Make sure to use this skill whenever the user mentions dashboards**, data visualization, internal metrics…'"
   → 官方取向是**加触发词**，与"关键词堆砌降低信噪比"方向相反。

**本机实测（L1）**

| 文件 | description 字符数 | UTF-8 字节 | 半角逗号 | 全角逗号 | 是否超 1024 |
|---|---|---|---|---|---|
| `C:\Users\peter\.workbuddy\skills\multi-collab\SKILL.md:3` | **236** | 632 | 0 | 0 | 否（余 788） |
| `C:\Users\peter\.workbuddy\skills\doc-governance\SKILL.md:3` | **249** | 613 | 0 | 0 | 否（余 775） |

量法：`python len(value)` 取 `description:` 后的实际值（不含字段名），字节数取 `encode('utf-8')`；两个口径都远低于 1024，**结论对口径不敏感**。

**"关键词堆砌降低信噪比"有没有可查依据？**

- **有，但不是顾问说的那个依据**（L1→L2）：官方只说"装得多 ⇒ 每条每轮常驻成本"（`code.claude.com/docs/en/skills`："**Every skill in the skill listing adds to your context on every turn, whether or not Claude ever uses it.**"）与"超 1536 截断"。由这两条可推出（L2）：**长 description 的真实风险是被截断，故尾部的触发词可能根本不进上下文**——这不是"信噪比"，是"尾部失效"。
- 推论（L2）：把最强的触发场景放**最前**，是可操作的改良；"限制逗号数"没有依据。

**对本包的实际影响**

1. **不要按顾问削 description**——削了会掉触发率，且违反官方"pushy"取向。
2. 真实可改的是**冗余**（L2，基于截断风险）：`multi-collab/SKILL.md:3` 先把席位枚举了一遍（"主理人/审计者/顾问/研究席/QA/子代理席"），末尾"触发词：…"又把同类场景词列了一遍，两段语义重叠。建议保留 Use when 段（前置），把"触发词："清单压到 8 个以内的最高频说法、并整体前置到 1536 窗口内。**这不是合规问题，是效果问题**，可延后。
3. `doc-governance` description 另有一个真问题（见 §3.1）：它把"何时用"绑死到项目名 `creative_skyline`。

### A2 交接件自包含 vs 引用纪律 —— **判定：部分成立（前句思想成立·引文非原文；后句查不到）**

**顾问引句 1**：「Treat the reader as having only the working tree and the plan file」

**出处原文（L1）** — OpenAI Cookbook《Using PLANS.md for multi-hour problem solving》（页面自标 archived）：
> "This document describes the requirements for an execution plan ('ExecPlan') … **Treat the reader as a complete beginner to this repository: they have only the current working tree and the single ExecPlan file you provide. There is no memory of prior plans and no external context.**"

另有一份被多个仓库内嵌的 `PLANS.md` 版本写作：
> "**Assume the reader is new to this repository. They only have the current working tree and the ExecPlan file you provide.** There is no memory of earlier plans and no external context."
> （https://github.com/pingcap/tidb/blob/master/PLANS.md ，2026-10-22 抓取）

判定：**思想与原句都在，但顾问的转写是压缩改写**（把 "complete beginner…there is no memory of prior plans and no external context" 压成一句）。引用时必须用原文，否则会被指"编造引句"。

同页还有一条对本包**直接有用**的硬要求：
> "**Every ExecPlan must be fully self-contained**: it includes all context and instructions needed for a novice to succeed."
> "**Every ExecPlan must produce a demonstrably working behavior**, not only source edits."
> "**Do not rely on external blogs or docs; include required knowledge directly in the plan.**"

**顾问引句 2**：「handoff ~500 tokens max，超过就说明塞了下一个 agent 自己能读到的内容」

**查证结果：L3 查不到。** 查了：OpenAI Cookbook PLANS.md 全文（无 token 数）、`pingcap/tidb` 与 `D3Hunter/tidb` 的 PLANS.md 副本（无）、Claude Code / Agent Skills 官方文档（无 handoff token 限制）、定向检索"handoff 500 tokens"。命中的全是非一手材料：

- 社区博客转述 Reddit 用户说法："Each agent 'wave compresses discoveries into ~500 token briefs…'"（https://docs.bswen.com/blog/2026-03-21-agent-task-handoff-coordination/ ，C 级）。
- 第三方 handoff skill（Matt Pocock 上游、`Hiroshi7296/codex-control-tower` 的 Codex 适配版）给出的是**分档压缩目标**而非硬限：
  > "The budget is a **compression target, not a reason to drop a necessary boundary or evidence pointer**: Simple continuation: target **240 tokens** or fewer. Normal engineering handoff: target **400** tokens or fewer. Multiple dependencies, blockers, or evidence: **up to 600** tokens when every line changes a downstream decision."（https://github.com/Hiroshi7296/codex-control-tower/blob/main/skills/handoff/SKILL.md ，C 级）

**关键观察（L1 对撞）**：顾问的两句引文**互相矛盾**。`PLANS.md` 要求"fully self-contained／include required knowledge directly"，而"500 tokens 上限"必然要求把可读可不读的内容推给读者自取。同一份文件不可能同时满足。顾问把两句并置，说明他只做了检索拼接、没做一致性检查。

**对本包的实际影响**

1. `20-handoff.md:20` 的自包含判据（"接收方是新开的空会话，只拿这一份件＋自己读得到的盘，能否完成动作？"）与 `PLANS.md` **同向**，可保留并升级为 L1 引用。
2. **不得**把"500 tokens"写进规格。若要长度约束，用"压缩目标＋可丢弃顺序"（哪些先扔）而不是硬上限——这一点第三方 skill 的措辞可直接借鉴（它明确写了"不是丢掉必要边界的理由"）。
3. `20-handoff.md` 缺一条 `PLANS.md` 已有、本包没有的：**"什么算做完"必须是可观察行为**（"demonstrably working behavior, not only source edits"）。这条恰好补本包"验收"层的空缺。

### A3 门禁是声明式，缺机械钩子 —— **判定：部分成立（hook 存在且可拦；"PostToolUse 兜底"表述不准；"本包无机械钩子"完全成立）**

**核实 1：`PreToolUse` / `PostToolUse` 是否真实存在、语义是否如顾问所述（L1）**

`claude.com/blog/how-to-configure-hooks`（Anthropic 官方博客）：
> "**Matchers** are how you filter which tools can trigger your hook. They only apply to **PreToolUse, PostToolUse, and PermissionRequest** hooks."
> "**Exit code 2 means a blocking error: stderr becomes the error message and the action gets prevented.** Other exit codes indicate non-blocking errors…"
> "Beyond exit codes, hooks can return structured JSON for more control. Fields include: **decision (approve, block, allow, or deny)**, reason, continue, and updatedInput (to modify tool parameters before execution)."
> "Hooks live in JSON settings files at three levels. Project-level hooks go in `.claude/settings.json` … User-level … `~/.claude/settings.json` … Local … `.claude/settings.local.json`."

判定：**PreToolUse 在写入前拦截 = 成立**（matcher 写 `Write` ＋ exit 2，官方语义明确）。

**核实 2：PostToolUse 能不能"兜底"？**（L3，官方 hooks 页直连失败）

- 官方上述博客只说 exit 2 = blocking error，**未按事件区分可阻断性**，也未把 PostToolUse 描述为拦截器（它举的例子是 auto-format／更新 changelog 这类**事后副作用**）。
- 第三方参考页明确：
  > "**PostToolUse can't block — tool already executed. Use PreToolUse to prevent.**"（https://rhombus.so/hooks.html ，C 级）
- 判定：若"兜底"指"事后发现并回灌反馈"→ 成立；若指"事后撤销／拦截"→ **不成立**。规格里不能写成"PostToolUse 兜底拦截"。

### A4 读域隔离靠自觉；权限继承是越权通道 —— **判定：部分成立（现象有更强一手证据；具体链路无官方明文；"自我声明为过渡妥协"一说错位）**

**核实 1：有没有可查来源支持"委派／子 agent 导致越权"（L1，且比顾问强）**

MasDrift（arXiv:2608.07556，2026-08-02，600 任务、8 领域）：
> 摘要："Multi-agent systems (MAS) decompose long-horizon tasks across supervisors and subagents, but **delegated goals do not necessarily carry their original authorization boundaries**."
> "centralized hierarchies achieve **93.9–98.6% task completion versus 85.7–87.0%** for peer networks, while **unauthorized actions occur in 2.7–19.8% of tasks versus 0.6–0.8%**, a gap that **widens with hierarchy depth**."
> 防御对比："**Re-anchoring** every pending call to the original user request **reduces unauthorized actions in every model configuration** … at a cost of **1.6 points** of pooled completion. **Chain propagation blocks required work instead, forfeiting up to 36.3 points.**"
> 实验指导语原文（Appendix，"Peer handoff" 臂）："Every handoff must be a **self-contained branch packet** containing the current subtask, necessary inputs/evidence, relevant completed-step summary, and current-branch tool results. **Never rely on the next peer seeing another branch's transcript.**"

判定：**成立，且强于顾问的表述**——不是"可能发生"，是"实测 2.7–19.8% 的任务发生了"。附带得到一条可落地防御（re-anchor 到原始请求），代价已量化（1.6 个百分点完成率）。

**核实 2：「只读 agent 借子 agent 的手完成真实写入可以在无新授权下发生」——具体链路（L2）**

官方文档可得的两条前件（L1）：
> "Tool definitions (**inherited from parent**, or the subset in `tools`)"（`code.claude.com/docs/en/agent-sdk/subagents`，"What subagents inherit" 表）
> "**As of Claude Code v2.1.172, subagents can spawn their own subagents.** A background subagent five levels below the main agent cannot spawn further subagents; foreground subagents can spawn at any depth. To prevent a subagent from spawning others, omit Agent from its `tools` array or add it to `disallowedTools`."（同页）

缺失的一环：官方**没有**说"子代理的工具池从父代理的池派生"。可查到的只有工具池过滤规则（"If both are set, `disallowedTools` is applied first, then `tools` is resolved against the remaining pool"）与"同一份定义在前台/后台可解析出不同工具集"。

## 二、任务 B：自包含应当按正交分层，还是按长度／引用纪律？

### 2.1 验真记录（逐条·不合并）

| 顾问主张 | 查到的一手材料 | 判定 |
|---|---|---|
| decision-sufficiency，文献《What to Pass and Why》 | **该标题查不到**（检索 + OpenAI/arXiv 侧均无）。但同一问题有更强一手：arXiv:**2608.14528**《Handover of In-Context Learning State Across Session Boundaries》（Kato & Kato, 2026-08-17） | **标题 L3／内容 L1** |
| MasDrift 的 self-contained branch packet 四板块 | **证实**。arXiv:2608.07556 Appendix 原文："Every handoff must be a self-contained branch packet containing the current subtask, necessary inputs/evidence, relevant completed-step summary, and current-branch tool results. | 10–50 倍压缩 | **查不到一手**。该倍数仅见于中文技术博客对"摘要 vs 工具结果裁剪"的压缩比表格（CSDN/掘金），无论文或官方文档支撑 | **L3** |
| A2A 的 Zero Context Pollution | **标签查不到**（非 A2A 规范用语，见中文二手文章）。但**概念 L1**：A2A 规范 §1："…securely exchange information to achieve user goals **without needing access to each other's internal state, memory, or tools**"；§1.2 Guiding Principles："**Opaque Execution:** Agents collaborate based on declared capabilities and exchanged information, **without needing to share their internal thoughts, plans, or tool implementations**." | **标签 L3／概念 L1** |

**2608.14528 的三条可直接用的结论（L1，原文）**

> "The handover record need not reproduce the earlier conversation, but **it must retain the information on which the unfinished task still depends**."
> "Because a prose summary can omit either type of information, **we judge the record by the prediction or action after the handover rather than by its similarity to the earlier wording**."
> "We propose a **three-part record** that stores **decisions and constraints exactly**, uses **task-justified statistics for repeated evidence**, and **retains original observations whose effect is not preserved by those statistics**."

这三句把"自包含"从形容词变成了可测命题：**判质量看交接后的行动，不看像不像原文**；**决策与约束必须逐字**；**重复证据可统计化，独特性证据必须留原样**。

**补充一手（L1）**：arXiv:2606.19795《Agentic Electronic Design Automation: A Handoff Perspective》给出可直接引用的判据句：
> "A handoff is **valid when the transferred object satisfies the consumer's acceptance conditions** and carries **sufficient context, evidence, and provenance** for downstream use."
→ "自包含"的正确落点是**收件人的验收条件**，不是长度上限。这也解释了为什么"500 token"是错的问题提法：长度与验收条件没有决定关系。

### 2.2 结论：分层优先，长度与引用纪律是**派生结果**（L2，推断链已给）

推断链：
1. 交接件质量的判定标准是"收件人能否在自己的层里把事做完"（L1，2608.14528 的 predictive sufficiency ＋ 2606.19795 的 acceptance conditions）。
2. 收件人需要什么，取决于**他在哪一层、要做什么动作**（L1，MasDrift branch packet 只给"current-branch tool results"，明确不看别的分支 transcript）。
3. 因此切分主轴是"层×收件人动作"；长度是"该层所需信息量"的**结果**，引用纪律是"哪些内容可以推给盘面自取"的**结果**（L1，PLANS.md "Do not rely on external blogs or docs; include required knowledge directly" 与 handoff skill "reference existing artifacts rather than retelling" 是同一问题的两侧，取决于收件人能否读到）。
⇒ **正交分层优先成立**。但要加一条顾问没说、本包必须补的（L2）：**长度与引用纪律需要一个"可读性前提"**——只有当收件人**确实能读到**某个盘面件时，"引用代替复述"才成立；否则自包含破裂。`20-handoff.md:20` 的判据已经隐含这点（"只拿这一份件＋**自己读得到的盘**"），但没写出"读得到"要由发件人核验。

**为什么这版不会歧义（逐条对病因）**

1. 三个词**不动用"真源"二字**——歧义的根源是"真源"同时承载三义，去掉它，读者不需要在两义间猜。
2. 三栏**各有一句判定语**（已定／现状·未确认／未定），且**状态词就写在栏名后**：读者不必读完整段就知道哪条能引、哪条不能引。
3. 显式写"这是**来源登记**，不是**背书**"——防最常见的一种误读：把"依据 A 写成"读成"经 A 授权"。
4. **下游引用规则单独成句**，把三栏落成**可执行动作**（可以引用为什么、不可以引用为什么）；只描述状态不给动作的声明，实操中等于没写。
5. 只在本件写**一次**（不复制到副本正文别处），使"改一处即可全改"，避免声明自己变成第二真源。

##### B. 副本侧头部声明（定稿措辞·直接粘贴到部署侧副本正文首块）

```markdown
> **【本件是副本】** 载体真本：`{repo}/deliverables/doc-governance/SKILL.md` @ commit `<40 hex>`
> 同步于 `<YYYY-MM-DD HH:MM +08:00>`；内容依据**不在本件**（见真本「容器非真源」节）；内容定稿权在决策者，本件不参与定稿。
> **改法**：一律改仓内真本 → 回写本副本 → 由执行者更新仓内 `COPY.state`（本副本**无权**登记自己为已同步）。
> **冲突处置**：本件与真本不一致时，以真本为准；本件不声称自己的内容正确。
<!-- copy-guard v1
source=deliverables/doc-governance/SKILL.md
source_commit=<40 hex>
synced_at=<YYYY-MM-DDTHH:MM:SS+08:00>
copy_of_skill=doc-governance
-->
```

**为什么这版不会歧义**：①第一栏只答"谁是载体真本"，**不碰内容**——正是主理人所指"只写'真源在本仓'会让读者把内容层指向搞错"的修法；②第二栏把内容依据**显式推回真本**（"不在本件"），这是关键一句：副本里看到的引用链只是转抄，追溯要走真本；③"本副本无权登记自己为已同步"这一句**预先堵掉了**"副本自证"这条错路（见 D）。

##### C. 放哪儿才可机检（frontmatter？首行块？）

**结论：放正文首块，且"人读块 ＋ 紧邻机检注释"成对出现；不得放 frontmatter。** 三条理由，按硬度排：

1. **frontmatter 会直接违反规范（L1）**：spec 只允许 `name/description/license/compatibility/metadata/allowed-tools` 六个字段；Claude Code 文档明写 "If you include any field the spec doesn't allow, **packaging or upload fails with a hard error**"。副本若加 `copy_of:` 字段，副本与真本 frontmatter 就不一致 → 二者无法逐字 diff，"只差这一处"的前提消失。
2. **正文无格式限制，可自由放机检锚（L1）**：spec 原话 "The Markdown body after the frontmatter contains the skill instructions. **There are no format restrictions.**" ⇒ HTML 注释合法、不渲染、可精确 grep。
3. **块级结构比"首行块"更耐改（L2）**：人读块在前（保读者），机检注释在后（保机器）；两者**相邻且各自闭合**，任何脚本只替换注释块、不动人读块，反之亦然。若把机检信息塞进人读句子，句子一改写，机检就断。

**机检判据（可直接写进脚本·三条）**

| # | 判据 | 检查动作 | 违反判定 |
|---|---|---|---|
| G-1 | 副本存在 guard 块 | `grep -c '^<!-- copy-guard v1$' <copy>` | 0 次＝**裸副本**（见 E） |
| G-2 | guard 块字段齐 | 块内必须恰有 `source=`／`source_commit=`／`synced_at=`／`copy_of_skill=` 四键，`source_commit` 匹配 `^[0-9a-f]{40}$` | 缺键或格式不合＝声明不合格 |
| G-3 | 声明不越权 | 人读块内必须出现"内容依据**不在本件**"与"以真本为准"两串（固定措辞） | 缺＝声明退回重写（防有人用自定义措辞绕过） |

> G-3 用**固定措辞串**是有意的：声明文本若允许自由发挥，"声明是否合规"就变成人判；固定串把它变成机判。代价是措辞改一次要同步改判据（记入维护成本）。

##### D. 同步校验怎么设计：hash 对账 vs `diff -rq` vs README 约定

| 方案 | 怎么跑 | 代价 | 能抓"绕过仓内直接改副本"吗 |
|---|---|---|---|
| **① hash 对账清单（推荐）** | 仓内 `COPY.state` 存**两个** hash：`source_sha256` 与 `copy_sha256_at_sync`；比对时算真源现值与副本现值 | 多一个文件；每次同步要更新两行（漏更即误报）；需 sha256 工具（Git Bash `sha256sum`／Windows `certutil -hashfile`） | **能**，且能判四态（下） |
| ② `diff -q`（单文件）／`diff -rq`（将来拆 references） | 直接比两份文件 | 零状态文件；但**只能告"不同"，不能告"谁改的"**——无法区分"仓内更新了"与"有人偷改副本"；无历史；Windows 依赖 Git Bash | **不能**（只能事后人猜） |
| ③ README／头部约定 | 人读"改完请同步" | 零成本、零强制力 | 不能 |

**为什么必须是双 hash（这是本节的技术核心，L2）**：只记真源 hash，只能判"副本是否陈旧"；要判"有人绕过仓内改了副本"，必须知道**上次同步时副本长什么样**——即 `copy_sha256_at_sync`。单 hash 方案在原理上无法区分"副本旧了"和"副本被偷改过"，这正是现在两个技能静默漂移的风险点。

**四态判定表（执行者照此判，不靠感觉）**

| # | 真源现值 vs `source_sha256` | 副本现值 vs `copy_sha256_at_sync` | 判定 | 动作 |
|---|---|---|---|---|
| 1 | 相同 | 相同 | **一致** | 无 |
| 2 | **不同** | 相同 | **陈旧**（正常） | 提示同步；不算违例 |
| 3 | 相同 | **不同** | **静默漂移（违例）** | 停手：以真源覆盖副本；记违例一次（谁改的／何时，落 `.collab/evidence/`） |
| 4 | 不同 | 不同 | **冲突** | 停手上报，**不得自行合并**（合并＝在副本上造第二真源） |

**结构代价说明（为什么值得／不值得新增结构）**：
- **不新增一级目录**：`COPY.state` 与（将来的）`scripts/` 都落在既有二级目录 `deliverables/doc-governance/` 内。spec 明确允许 skill 目录含任意附加文件——"A skill directory may contain any files and directories beyond the required `SKILL.md`"，故这是**规范内的零结构成本**，不是"为了校验而破一次目录纪律"。
- **部署动作＝复制单文件**：现无 `references/`，同步只搬 `SKILL.md` 一个文件 ⇒ `COPY.state`／`scripts/` **天然不会被带进部署侧**，不需要额外排除规则。**代价触发条件**：一旦按 Q3 结论拆出 `references/`，同步变成搬目录，届时必须加排除清单（`--exclude COPY.state --exclude scripts`），维护成本上升一档——这一点应写进 Q3 的决策输入。
- **不值得新增的部分**：不建 `.copy/`、不建仓根 `tools/`、不建平行"副本台账"目录（三条都会新增一级或准一级结构，且与 `deliverables/README.md` 的索引职责重叠）。

**为什么④⑤两类必须排除在副本制之外（不是"暂时不管"，是概念上不适用）**

- **④ 软链（7 件）**：软链与上游**同一个文件**（改它就是改上游，删它不删上游），不存在"两份内容"这个前提 ⇒ 无漂移、无同步、无 guard 可言。对软链加 `copy-guard` 反而是**错的**：guard 块会写进上游仓库的文件。
  - 但软链并非无治理点：它引入的是**上游变更风险**（上游一改，本地行为即变，无审核）。这一条属 Q9 的"形态选型"输入，不属副本制。
- **⑤ 退役目录（3 件）**：无 `SKILL.md` ⇒ 不会被技能系统加载，不是部署件。它们的正确判据是**"是否还有活指针指向它"**（`50-antipatterns`/索引/他件引用），属 object-audit 的悬空指针测项，不属副本制。
- **③ 类是唯一需要新判据的**：它们既非副本（仓内无对应），也非软链（不指上游）——**上游在不在我完全不知道**。故只能要求**豁免声明**（E-4），不能要求 guard，更不能直接标成"副本"（那会制造假真源）。

**为什么判据取"存在性"而不是"内容正确性"（L2）**：副本制起步时，14 个部署件不可能一次全部纳管；若判据是"内容对不对"，第一批就会卡死。存在性判据的作用是**把不可见状态变成清单**——先数清"哪些纳管了、哪些豁免了、哪些裸着、哪些不适用"，再逐个处理。这与 `20-handoff.md:37`"例外须显式声明（白名单制）"同构，不是我新造的纪律。

**给执行者的最小落地顺序（三步·不依赖任何待拍项）**
1. 仓内入 `deliverables/doc-governance/SKILL.md` 三栏头部（A）＋ `COPY.state`（D）；
2. 部署侧副本加 guard（B），跑一次双 hash 写入 `COPY.state`；**同批把 ① 类现存 3 件纳入**（`multi-collab`／`object-audit` 现状一致，`object-build` 需按真源覆盖一次再记 hash——**这是本次实测发现的唯一现存不一致，建议顺手清账**）；
3. 跑 E-1／E-4 出一张**四列清单**（①已纳管／②待入仓／③待豁免声明／④⑤不适用），随报告呈拍 Q9。
