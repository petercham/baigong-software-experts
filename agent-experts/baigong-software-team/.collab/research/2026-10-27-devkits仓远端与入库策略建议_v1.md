## 2. 逐项判定与判据

### 2.0 判据的总依据（先立尺，再量物）

本仓 `.gitignore` 开篇的治理原则（2026-10-22 皮总拍·按研究裁决执行）已把尺子立好：

> 「是否进 git」由本文件显式声明，**不由目录名前缀表达**（`.` 前缀只影响 ls/rg 可见性，git 不认）。
> **分区键＝性质**：decisions（判词/裁决/呈拍·史实锚）进 git；process/inbox（过程流水）不进。

README「分区判据」一句话版：

> 这份东西是拿来**照着做**的（deliverables/docs，审），还是拿来**查当时发生了什么**的（decisions，记），还是**用完可弃**的（process/inbox，不入库）。

由此可推出三条可操作判据，本文全部判定只用这三条，不凭感觉：

- **判据 A（性质）**：它是不是「判词／裁决／呈拍／判词依据」？是 → 进；是「过程流水／运行时消息／临时产物」→ 不进。
- **判据 B（出处）**：它是**本仓自产**还是**第三方／他仓产物**？第三方产物入我仓＝**真源混淆**＝违「单真源」（MC-SOT-1，且 README 明写本仓与 creative_skyline「不与其互写」的同族纪律），→ 不进。
- **判据 C（冗余）**：它能不能从 git 历史／HEAD／姊妹仓**无损重建**？能 → 属冗余，进仓只增加噪声 → 不进。

> 特别注意：任务背景里点名要排除的那类推理——「`.collab/` 看起来像隐藏目录所以不该入库」——**不成立**，本文未使用。`.collab/research/` 已被 `.gitignore` 用 `!.collab/research/` 显式声明入 git，本仓 HEAD 也已跟踪 30+ 份研究报告，这是**既定事实**，不是待议项。

**（c）价值如何不丢（三件套，这是"忽略"能成立的前提）**

忽略不等于丢弃。可追溯性由下面三件事共同承载，**缺一不可**：

1. **入库一个索引件** `.collab/research/reference-2026-10-24/REFERENCE-SOURCES.md`（新增，**入 git**）。内容须包含：每个素材目录的**来源**（下载 URL／COS 对象键／召唤来源）、**下载时刻**、**文件数/字节数**、**目录级校验**（如 `find <dir> -type f -exec sha256sum {} \; | sort | sha256sum` 的结果）、**它支撑了哪几份判词/报告**（指向已入库的自有 md 与 `#锚`）、以及**实体现在的绝对路径**。
2. **实体移到仓外归档目录** `D:\multi-agent-collab-reference-2026-10-24\`（**保留原目录结构**，整目录 `mv`，不重命名不重排），并在索引件里写明该路径。
3. **可重建性声明**：若素材可从源头重新下载（COS 对象仍在），在索引件里写明「可重建 + 取回方式」；若不可重建（源头已下线），索引件里必须显式标注「不可重建·本机唯一副本」，此时归档目录应按**长期保留**对待，并考虑做一份冷备（D 盘实测仅剩 76G / 95% 满，冷备需另觅盘位——这是皮总拍板项之一）。

### 2.6 三份研究报告的提交组织方式 → **一报告一 commit（3 个）**

**建议：分成 3 个 commit**，外加 1 个治理 commit（`.gitignore` + `REFERENCE-SOURCES.md` + 讨论记录漏件），共 **4 个 commit**。

**理由（按权重排序）：**

1. **可回溯性需要独立 sha。** 本仓治理体系的引用体例就是**引 commit sha**——实测 `verdicts.md` 判词里明写「判词锚 c2d8bf2/5f4ea57」「提交时刻证据 01-12-41（锚 e62fc6a）」。三份报告若合成一个 commit，日后要引用其中一份（例如"席位派发失败根因判别报告"作为某条裁决的依据）时，**给出的 sha 指向的是三份的合集**，锚点不精确。
2. **与既有惯例一致。** `git log` 实测本仓是「一事一 commit」：T2 独立验证报告一个 commit（`3e999ac`）、T3 独立验证报告一个 commit、T4 收口登记一个 commit（`3c62733`）。三份报告是三个**不同议题**（仓拓扑分仓最佳实践／席位派发失败根因／fork-lead 席位 MD 瘦身设计），符合同一体例。
3. **可单独回退。** 若日后发现其中一份需要撤回或勘误，`git revert <sha>` 只动那一份，不牵连另两份。合成一个 commit 则无法做到。

**反方案（合成 1 个 commit）的代价：** 共享 sha → 引用锚点不精确；无法单独 revert；且三份报告议题不同，合成后 commit message 无法用一句话准确概括（要么过长，要么失真）。

**提交顺序建议：** 按**产出时刻**排（瘦身设计 20:40 → 仓拓扑 22:00 → 席位派发根因 22:08），最后放治理 commit。这样 `git log` 的时间线与文件 mtime 一致，便于日后对照。

### 3.3 两条必须知道的技术边界（写给执行者，避免踩坑）

1. **gitignore 的负向规则无法"重新包含"被整目录排除的目录内的文件。** git 官方规则原文：*It is not possible to re-include a file if a parent directory of that file is excluded.* 上面 ④ 排除的是**整个目录**（`video-teams/`），所以 `!.../video-teams/某个.md` 这类写法**无效**。若皮总要求保留素材里的某些 md，必须改写为文件模式：
   ```gitignore
   .collab/research/reference-2026-10-24/video-teams/**
   !.collab/research/reference-2026-10-24/video-teams/**/
   !.collab/research/reference-2026-10-24/video-teams/**/*.md
   ```
   （先排除目录下所有文件、再重新包含所有子目录、再包含 md——顺序不可颠倒）。本文**推荐不这样做**：保留第三方 md 会重新引入真源混淆问题。
2. **新增规则对已跟踪文件无效。** 本文件此次涉及的 10 项**全部未被跟踪**（`git status --porcelain` 全为 `??`），所以规则一改立即生效。但若将来对**已跟踪**文件加忽略规则，必须先 `git rm --cached <path>`，否则规则静默失效。

### 4.3 为什么是这个顺序（逐条给理由）

- **整理 → commit 放在改名之前。** 改名只改变**父目录名**，不动 `.git` 内部、不动工作树相对路径。先 commit 可以**在旧路径下完成全部核验**（`git status` 空、`git add -A -n` 逐行看），出问题只需把目录名改回去即可回滚，回滚成本≈0。反过来（先改名再整理）则每一步核验都在新路径下，一旦要回退就得同时回退"改名"和"整理"两件事。
- **改名放在建仓/首推之前。** 让「本地目录名 == 仓名」这一事实在**首推那一刻**就成立，远端从被创建的瞬间起就与本地终态一致。这正好消掉 `run-gates.sh` 里那段双名探测存在的理由（它现在要兼容旧名，就是因为改名还没做）。
- **建仓放在所有本地整理之后。** 建仓是唯一的**不可逆网络动作**（删仓后 GitHub 会保留该名字一小段时间的占用）。把它放在最后，可以确保"仓建好时，要推什么已经完全确定"，不会出现"仓建好了，又发现要改历史"。
- **首推放在改名之后。** push 的内容与本地目录名无关（push 的是对象和 ref），顺序上这样排是为了保证走到 push 这一步时本地已是终态。

### 4.4 改名的影响面（逐项给结论）

| 对象 | 是否有影响 | 实测依据 |
|---|---|---|
| `.git` 内部 | **零影响** | `.git/config` 实测只含 `repositoryformatversion / filemode / bare / logallrefupdates / symlinks / ignorecase`，**无 `core.worktree`**，不含任何工作树绝对路径 |
| remote URL | **零影响** | remote 是 GitHub URL（`https://github.com/petercham/multi-agent-collab-devkits.git`），与本地目录名无关；且**已经改对为 devkits** |

## 5. devkits 仓的 tag 策略

### 5.1 先把两个仓的性质区别说清楚（这是 tag 策略的分水岭）

| | skills 仓 | **devkits 仓（本仓）** |
|---|---|---|
| 角色 | **组件仓**：被别人按 ref 消费 | **工具包仓**：被**直接 checkout 使用** |
| 消费者 | experts 仓的 `bundle.lock`（锁版本） | 人 + 脚本的 checkout（门禁脚本本体、SOT 对账脚本、deliverables 交付件都住这仓） |
| tag 形式 | `aigc-video-<域>@v1.0.0`（**组件名 + @ + 版本**） | ？ |
| tag 语义 | 「这个组件在这一版的内容被锁死，别人按 sha/ref 去 `git archive`」 | 「这个仓整仓在某时刻的发布快照」 |
| 现状实测 | 5 个不可变 tag：`aigc-video-{content,governance,orchestration,release,visual}@v1.0.0` | 本地有 `refs/tags/v0.1.0`（旧 skillpack 时代遗留） |

**关键区别一句话：** skills 仓的 tag 是**给机器（bundle.lock）读的地址**；devkits 仓没有这样的机器消费者——`bundle.lock` 里不会出现 devkits 的 ref（实测 `find ../multi-agent-collab-experts -name bundle.lock` 未命中该文件，且 devkits 仓内组件按拍板五①「豁免正交切分」，README 明写「本仓＝各维度整合打包的可用开发工具，内部豁免正交切分」）。

### 5.2 建议：**要打，但打仓级版本 tag `v0.2.0`，不打组件 tag**

**形式：`v0.2.0`**（不带组件名、不带 `@`）。

- **依据（历史序列）**：本仓旧远端 `multi-agent-collab-skillpack` 已有 `v0.1.0`（本地 `refs/tags/v0.1.0` 仍在；README 也写「旧远端…保留作归档（tag `v0.1.0`）」）→ 沿用 `vX.Y.Z` **仓级序列**，从 **`v0.2.0`** 起。`v0.1.0`＝拆仓前的 skillpack 时代；`v0.2.0`＝拆仓后升格 devkits 的首个发布态。
- **不打 `xxx@v1.0.0` 的理由**：① 本仓内部豁免正交切分，无对外组件名可挂；② 挂组件式 tag 会与 skills 仓的 5 个组件 tag **语义混淆**，且**无人消费**（bundle.lock 不引它）——造一个没人读的地址＝噪声。
- **命名一致性**：`v0.2.0` 与 README 里的仓名 `multi-agent-collab-devkits` 不冲突；GitHub 上 tag 默认按仓级展示。

**时机：首推成功 + 改名归位 + skills 仓门禁在新名下跑通（GATE PASS exit 0）之后。**

理由：tag ＝ 不可变承诺。打在"尚未验证"的状态上，事后要删 tag 重打——远端删 tag 要 `git push --delete origin v0.2.0`，且**任何已 fetch 过的人本地会残留该 tag**（git 默认不自动剪除），清理成本高于等待成本。把 tag 放在门禁通过之后，等于让 tag 天然带上「这一版是验证过的」语义。

```bash
# 打 tag（在 Step 6 首推成功 + Step 4 门禁通过之后）
git -C /d/multi-agent-collab-devkits tag -a v0.2.0 \
  -m "devkits 仓首个发布态：三仓正交拆仓完成（拍板三/四/五/六）+ 目录改名归位 + SOT 双根对账 GATE PASS"
git -C /d/multi-agent-collab-devkits push origin v0.2.0
git -C /d/multi-agent-collab-devkits ls-remote --tags origin     # 复核
```

### 5.3 三条拍板项（tag 相关）

1. **`v0.1.0` 要不要推到新远端？建议不推。** 推上去会让"旧 skillpack 仓的版本号"出现在 devkits 仓里，语义混乱（读者会以为 devkits 有过一个 v0.1.0）。旧远端 `multi-agent-collab-skillpack` 已保留作归档，`v0.1.0` 在那里可查。
2. **要不要设为"不可变"？** skills 仓那 5 个 tag 是"不可变 tag"。devkits 首推阶段打**普通 tag** 即可（git tag 本身不阻止删除）。若要与 skills 仓同等强度，需在 GitHub 上启用 **tag protection rule**（Settings → Tags → Add rule，模式 `v*`）——这是皮总拍板项。
3. **是否同时给 `master` 加 branch protection？** 本仓纪律是「单写者：所有 git 写操作由唯一执行通道完成」（README 治理约定 1）。若要在远端强制这条，可给 `master` 加保护规则。属于额外加固，不影响首推，可后置。

## 6. 风险与回滚

### 6.1 场景：首推之后才发现某类文件不该入库（以 46M 素材已推上去为例）

四条路径，**按代价从低到高**：

| 路径 | 做法 | 适用条件 | 代价 |
|---|---|---|---|
| **A 接受** | 什么都不做，让 46M 留在远端 | 仓为私有、使用者固定（皮总 + 若干 agent 席位）、46M 不构成硬伤 | 远端永久 46M；每次 clone/pull 都要下。**实测 D 盘仅剩 76G（95% 满），46M 不构成空间问题，主要代价是 clone 速度与仓体洁癖** |
| **C 后续 commit 删除** | `git rm -r <path>` + commit + push | 只想让**当前 checkout 干净** | ⚠️ **对远端体积完全无效**——blob 仍在历史对象里，clone 照样要下。这是最常见的误解，必须点明 |
| **B 历史重写 + 强推** | `git filter-repo --path <dir> --invert-paths` 后 `git push --force --all` | 体积/合规构成**硬伤**时才用 | ⚠️ **代价最重，见下** |
| **D 预防性护栏** | 首推前 dry-run + 首推后体积复核 | 无（**推荐无条件执行**） | 零代价，只是多跑两条命令（见 §6.3） |

### 6.2 路径 B（历史重写）的代价必须讲透

```bash
# 仅在确认必须执行时（未列入推荐流程）
pip install git-filter-repo
git -C /d/multi-agent-collab-devkits filter-repo \
  --path .collab/research/reference-2026-10-24/video-teams --invert-paths
git -C /d/multi-agent-collab-devkits push --force --all origin
```

**代价清单：**

1. **207+ 个 commit 的 sha 全部改变** → 本仓 `.collab/decisions/` 与 `verdicts.md` 里**引用的所有 sha 全部失效**（实测被引 sha 包括 `e62fc6a`、`dadc93f`、`c2d8bf2`、`5f4ea57`、`3c62733` 等）。这是**本项目里最严重的代价**：整套治理体系靠 sha 引判词，sha 一断，史实锚就断了。
2. 任何已 clone 的人必须重新 clone（`git pull` 会因历史分叉失败）。
3. 已打的 tag（`v0.2.0`）指向旧 sha，需重打 + 远端删旧 tag + 通知所有 fetch 过的人清理本地残留 tag。
4. GitHub 侧的悬空对象由后台 gc 回收，时间不确定（必要时需联系 support 触发）。

**结论：只要素材没进任何被判词引用的 commit，且体积不构成硬伤 —— 优先选 A（接受），不要选 B。** 本项目的 sha 引用密度决定了"改历史"的成本远高于"多背 46M"。

### 6.3 预防性护栏（推荐无条件执行，零代价）

```bash
# 护栏①：commit 前 dry-run，逐行看将要提交什么
cd /d/multi-agent-collab-devkits && git add -A -n

# 护栏②：首推后立刻复核远端实际总体积（期望 < 15MB）
git ls-tree -r --long origin/master | awk '{s+=$4} END {printf "%.1f MB\n", s/1048576}'

# 护栏③：首推后确认 46M 素材确实不在远端
git ls-tree -r --name-only origin/master | grep -c 'reference-2026-10-24/video-teams'   # 期望 0
```

若护栏②读数 ≥ 50MB 或护栏③非 0，说明 §4.2 的 Step 2a 漏执行 → **此时仍在首推当天，历史尚未被判词引用，可立即执行路径 B，代价最小**（这是选 B 的唯一黄金窗口）。

### 6.4 其他风险

| 风险 | 概率 | 处置 |
|---|---|---|
| `gh repo create` 报 `CONNECT tunnel failed, response 502` | 中（本机代理已知偶发） | 原命令**原样重试**，不改参数；连续 3 次失败则改用网页建仓（同样：private、不初始化任何文件） |
| 首推报 `non-fast-forward` / `rejected` | 低 | 先 `git ls-remote origin` 确认是空仓（空仓时无输出或无 `refs/heads/master`）。确认空仓后可用 `git push -u --force-with-lease origin master` —— **仅限已确认空仓时使用，否则会覆盖他人提交** |
| 改名被"会话占用"阻挡（此前未执行的原因） | 中 | 关闭所有指向该目录的编辑器/IDE/文件管理器/agent 会话后重试；若仍锁，用 `handle.exe` 或资源监视器查占用句柄 |
| 素材移出仓外后，`REFERENCE-SOURCES.md` 忘了写 | 中 | 该索引件是"忽略"能成立的**前提**（§2.4c）。若未补齐，§3.2 的 ④ 规则应当**暂缓生效**，先把素材留在原位不动 |
| 归档目录 `D:\multi-agent-collab-reference-2026-10-24\` 被误清理 | 低 | 在索引件里标注「不可重建·本机唯一副本」（如确为不可重建），并在 §7 拍板项 1 里决定是否做冷备 |
