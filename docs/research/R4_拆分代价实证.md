# R4 拆分代价实证（拆太细 vs 合太粗）

研究日期 2026-10-22｜只做查证，未改动项目文件｜凡无实测数据者一律标注，不包装成结论。

## 结论（一句话）

两侧都有实测代价，且**方向不对称**：拆太细的代价是**可测、可加总、且大部分不可逆**（常驻 token 线性增长 + 选择准确率下降 + 副本漂移 + 重组困难）；合太粗的代价是**精度衰减但可逆**（删内容即可恢复）。因此业界的收敛建议不是"折中"，而是"**宁可少拆，后补拆**"——因为拆的代价能算，合的代价能改。

## 一、拆太细的代价

| 代价 | 数字 / 原话 | 出处 |
|---|---|---|
| **1. 常驻上下文线性成本**（每轮都付） | 实测：**124 个 skill ≈ 13,800 tokens/轮**（均 ≈111 tokens/个）；其中 84 个从未被调用 ≈8,230 tokens/轮。另一机：**40 个 skill ≈ 3,060 tokens/轮**（≈76/个）。官方口径："Every skill in the skill listing adds to your context on every turn, whether or not Claude ever uses it." | https://dev.classmethod.jp/en/articles/20260905-cc-updates-v2-1-261 ；https://dev.to/rulestack/skill-doctor-40-skills-3060-tokens-a-turn-and-the-wrong-ones-to-cut-3g83 ；https://code.claude.com/docs/en/skills |

## 二、合太粗的代价

| 代价 | 数字 / 原话 | 出处 |
|---|---|---|
| **1. 上下文变长→精度下降（本领域最硬数据）** | Chroma 测 **18 个前沿模型全部退化**；LongMemEval 上**同一答案**：聚焦版 **~300 tokens 胜过 ~113,000 tokens 全史**；退化在"复制重复词"这种零推理任务上也出现 | https://research.trychroma.com/context-rot |
| **2. 官方把上下文定性为有限预算** | "context … must be treated as a **finite resource with diminishing marginal returns**"；"find the **smallest possible set of high-signal tokens**"；官方承认 context rot："as the number of tokens … increases, the model's ability to accurately recall information from that context decreases" | https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents |
| **3. 干扰项比长度更毒** | 单个"相关但不对"的段落就降低准确率，**四个叠加**进一步恶化；且"shuffled haystack 反而比连贯文档得分高"（结构连贯会提供更多似是而非的线索） | https://research.trychroma.com/context-rot |
| **4. 规则堆叠→遵循率跳水（跨域类比）** | GPT-4.1 IFEval **87.4%**（平均仅 **36 词**、单约束），OpenAI 内部 hard 子集 **49.1%**、MultiChallenge **38.3%**；ManyIFEval GPT-4o **0.94 (n=1) → 0.21**；MultiCodeIF 硬满足率 **54.5% (L1) → 18.8% (L4)** | https://codexpedite.com/gpt-4-1-instruction-following-why-87-on-ifeval-still-isnt-enough ；https://www.emergentmind.com/topics/multi-turn-instruction-following-mtif |
| **5. 单体过长→使用者跳过（只有实践共识，无数据）** | "A runbook that's 3,000 words is a runbook the on-call will **skim, miss a step**, and call someone else"；建议 **200–600 词 / 一屏** | https://raccoon.page/blog/how-to-write-a-runbook |
| **6. 长单体的真实收益（用来对照）** | 有 playbook vs 即兴 → MTTR **约 3x**（"roughly a 3x improvement in MTTR as compared to … winging it"）。注意：这是**有/无**的收益，不是**长/短**的收益 | https://sre.google/sre-book/introduction/ |

## 三、不能类比的地方（类比强度衰减，必须写明）

1. **微服务的"延迟/可用性/事务"三条完全不可迁移到 skill 切分。** skill 拆分没有网络跳、没有部署耦合、没有最终一致性——Fowler 列的三大成本里，只有"运维复杂度"（≈ 维护与治理负担）勉强对应。**衰减：3 项中 1 项可借，且只能借方向不能借数字。**
2. **代码克隆漂移的数字只能当"下界参考"，且方向可能相反。** 代码有编译器/测试兜底，副本不一致会编译失败或测试失败；文档/skill 没有编译器，**漂移只会更多不会更少**。给数字时应说"文档漂移不低于代码漂移"，而非"等于"。
3. **SkillRouter 的适用边界很窄，不能当普遍定律。** 条件是：注册表 **~8 万条**、功能**高度重叠**、**75 条**查询、Hit@1 对多技能查询**只要命中任一即算对**。作者自己写"not a universal law about all skill registries"。在 5–30 个技能、描述互不重叠的场景，该效应**未被测量**——不能引用它来论证"任何情况下都该常驻 body"。
4. **三方数字（官方 ~100 / 实测 38–111）不能混用，各自的口径不同。** 官方 "~100 tokens per Skill" 是**规格目标**（无离散度、无 tokenizer 说明）；第三方 38–111 是 **o200k_base 下的实测**（"Claude uses its own tokenizer and its counts differ"），且随 Claude Code 版本变动，小技能可低到 38。**做预算用官方 ~100；做上界论证用实测上界 111。**
5. **指令数↑→遵循率↓的证据来自"单次 prompt 内约束条数"，不是"文档篇幅"。** 用它论证"文档别写太长"是**二次类比**；真正对应"篇幅"的证据是 Context Rot。
6. **runbook 长度建议全部是实践者启发式**（一屏/200–600 词），无对照实验支撑，只有"DORA/事故复盘"式经验。
7. **Context Rot 不为 "5k" 这个数值背书，只支持方向。** 它测的是"同一答案，~300 vs ~113,000 tokens"的一般衰减，**没测过 5k 阈值、也没测过"5k 以内是否安全"**。所以两侧外推距离应分别标：**5k 侧＝规范自己给的数，外推距离近；SkillRouter 侧＝8 万跨到 12，外推距离远**。"夹逼"是**方向上的双侧**，不是**强度上的对等**——写成"两侧都有实测"会被审打回。

## 四、查不到的清单（明说：只有观点，无数据）

- **"每 skill 常驻多少 token"的实测分布**：**有规格值**（规范原文 `~100 tokens` / `< 5000 **recommended**` / `as needed`，本人直连核定，见 §一第 2 行），但**没有**实测分位数、没有最坏值、没有 tokenizer 差异说明（"~"的离散度未知）。第三方实测 38–111 tokens/个。**不要写"官方没有定量口径"（错）；也不要写"官方硬限 5k"（也错，原文是 recommended）。** 正确的缺口是"实测分布与最坏值"。
- **官方或实践者的"渐进披露 A/B 实测"（主文件 vs references 的 token 数 / 命中率）**：**没有**。Anthropic 只有定性句（"the amount of context that can be bundled into a skill is effectively unbounded"），无任何对照数字。唯一实测是 SkillRouter，而它是**路由侧**、不是"主文件 vs references"。
- **"长文档 → 错误率/更新滞后"的直接研究**：**没有**。最接近的是"过期引用率"（篇均 4.7 年），但那是"文档 vs 代码"的偏差，不是"长 vs 短"的偏差。
- **"拆太细 → 缺陷率升高"的对照实验**：**没有**。业界只有具名反模式（Grains of Sand、Nano-services、Distributed Monolith）与判定测试，无缺陷率数字。
- **"You can't have exactly two services"（team-lead 提到的 Nielsen 原话）**：**未找到任何一手出处**，检索到的均为二手转述，无法定位作者/年份。**建议不引用。** 最接近的可验证替身：
  - MeadSteve（2020）"**One less microservice than you need**"——理由是拆分易、重组难的不对称性；
  - Software Architecture Guild："If you **always deploy two services together**, debug them together … you haven't drawn a meaningful boundary — you've just created more moving parts."
- **工具数↑→准确率↓的"统一斜率"**：**不存在**，公开区间极宽（LongFuncEval 报 **7%–85%** 的落差，取决于模型与工具组合，且该数字本人只见到二手引用）。引用时必须带区间与"取决于工具相似度"的前提。

## 五、配置/论文侧的"引用粒度"成本（本轮新核，三条均一手核对）

| 结论 | 原话 | 出处 |
|---|---|---|
| **粗引用=自动吸收上游变更、失控制；细引用=得控制、担维护。成本被还原成"谁吸收变更"** | 粗引用："Referencing a complete category or ruleset means, you'll also get automatically any changes for this ruleset. **If new rules are added, then these are automatically activated for you.** If rules are deprecated, then these rules are automatically deactivated. **This might or not might be, what you want.**" → 细引用："If you want to have complete control over the rules, that you are using, then it is recommended to add each rule separately via a single rule reference." | https://docs.pmd-code.org/latest/pmd_userdocs_making_rulesets.html |
| **拆"对"了也有代价，且代价来自实现方式不是拆分本身**（勿写成"Parnas 说拆错有成本"——第二分解正是他主张的正解） | 摘要："The unconventional decomposition, if implemented with the conventional assumption that a module consists of one or more subroutines, **will be less efficient in most cases**." 正文："If each of the functions is actually implemented as a procedure with an elaborate calling sequence there will be **a great deal of such calling due to the repeated switching between modules**." 解法："we must implement these modules in an unusual way… the routines will be best **inserted into the code by an assembler**" | Parnas 1972, CACM 15(12)；PDF 已本机解压提取核对：https://www.cs.tufts.edu/~nr/cs257/archive/david-parnas/criteria.pdf |
| **成本与收益不在同一账本：成本在"运行态"，收益在"变更/文档/理解态"** | "The systems are **substantially different even if identical in the runnable representation**. This is possible because **the runnable representation need only be used for running; other representations are used for changing, documenting, understanding**, etc." 而一旦内联优化："the separation between modules **may not be clear in the final code**… the several representations of the program … **must be maintained in the machine together with a program performing mapping between them**." | 同上（两处均已本机核对） |
| **"合"要付适配层成本：慢 + 多一层间接** | "These are **generally not recommended**… The downsides of those plugins are: … They are **slower** than running Prettier directly. They're **yet one layer of indirection where things may break**." | https://prettier.io/docs/integrating-with-linters |

**四条各自的迁移边界（务必带上，否则会被读成"拆必亏"）**：
- Parnas 第 3 行：代价是**调用/切换开销**；skill 的 references **不加载就不付费**，没有"每轮切换税"。故**只能迁"边界≠调用边界"这一半**（Parnas 用 assembler 内联化解；skill 用"分件引用、按需读"化解），**不能迁"拆细必然更慢"**。
- Parnas 第 4 行：**这是本报告最可用于设计的一条**，且与 R3 的"主轴+索引表"独立收敛——他用"**mapping program**"把内联后消失的边界找回来，正对应"对象对照/index 表"的角色。但注意：他付的是**两笔账**（内联保性能 + 额外维护表示与映射保可理解），不是"省了切换税就赚了"。
- PMD 的"粗引用自动吸收上游变更"在 skill 侧**无对应物**（skill 不订阅上游版本），只能当**"控制权 vs 维护负担"的一般交换**，属类比而非同构。
- Prettier 的适配层成本是**工程开销**（慢、易断），与本报告 §二 的**精度代价**不是同一维度，不要混算。另：该页还有一句**规范句**"Use Prettier for code formatting concerns, and linters for code-quality concerns"——它支撑"**应当分**"，不支撑"**分更省**"，两者证据力不同，别让一条引文干两件事。

## 六、给设计的直接推论（据上表，非新增事实）

1. 常驻成本**可算**：官方规格 **~100 tokens/skill**（实测 76–111 同量级），N 个模块每轮固定税 ≈ **N×100**。这是唯一能事前定价的一项。
2. 拆分的收益必须**超过**"选择准确率损失 + 漂移维护 + 不可逆风险"三项之和，才值得拆；其中只有第一项有实测斜率。
3. 若拆，**必须同时解决"选择信号不足"**（SkillRouter 证伪了"名字+描述够用"），否则拆得越细、选错越多。
4. 若合，**单文件长度要有硬上限并外置引用**，因为超长本身即降精度（Context Rot），且这个代价**可逆**——这是"宁可先合"的技术依据。（注意分层：规范原文是 `< 5000 tokens **recommended**`，**不是硬限**；把 recommended 收紧成硬限是**设计自加的选择**，别写成"官方规定"。）
5. **本报告的"拆/合二分"是任务给定的框架，不是业界的实际选项集。** 据 R3（res-standard-axis，`R3_标准体系切分维度.md`）：业界公约数是"**一根主轴分卷 + 一张只做导航、不承担判据的对象对照表**"，唯一真做全矩阵的 PMBOK 第 6 版在第 7 版主动撤回（官方 FAQ："The Process Groups and ITTOs are … no longer fully included"）。因此做题时**成本基线应取"主轴+索引表"，而不是"全矩阵 vs 单卷"**——全矩阵的成本里有一项本报告未覆盖：每格必须填满且互不重复，填不满就退化成名单。
6. **漂移是"拆的税"，但税率可由约束降低，不等于"别拆"。** 表一中**「副本漂移（代码侧实测）」「副本漂移（文档侧实测）」两行**的漂移率是**无约束复制**下的观测值；业界对策不是减少副本数，而是"**单一真源 + 指针**"与"**对应关系约束**"（ISO/IEC/IEEE 42010 用 correspondence 保跨视图一致，而非禁止多视图）。故这两行应读作"若不建真源与对应约束，拆的税是这个量级"，不能读作"副本越少越好"——后者会与第 5 条自相矛盾。
7. **拆分的成本由"边界是否等于加载边界"决定，不由"拆成几个"决定。** Parnas 的教训是：拆细贵在**模块间切换**，他的解法是让装配层内联，而不是不拆。skill 侧同理——**skill 边界 = 每轮付费的加载边界（~100 tokens/轮/个）；reference 边界 = 按需付费**。所以"多写分件"便宜、"多开 skill"贵；判据应是"**这个东西需不需要每轮参与选择**"，而不是"内容多不多"。
8. **成本与收益分属两本账，不可放进同一张表比大小。** Parnas：「成本在运行态（调用切换）；收益在变更/文档/理解态」。skill 侧同构：**成本是每轮 token（运行态），收益是可局部修改、可独立评审、可复用（非运行态）**。把"多花 N×100 tokens"和"更好维护"折算成一个分数，是本次最容易犯的错——正确做法是**分别设预算**（token 预算 / 维护预算），不是相互折价。另：一旦为省运行成本而内联，**边界会在成品里消失**（Parnas："the separation between modules may not be clear in the final code"），此时必须额外维护"**多种表示 + 一个映射件**"——这正是 R3 的"主轴 + 对照/index 表"在另一领域的位置。
