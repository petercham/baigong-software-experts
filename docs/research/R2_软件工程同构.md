# R2 软件工程同构先例：「多对象 × 多工序」的规则该按什么组织

> 研究件。只做取证，不改项目文件。取证日 2026-10-22。
> 引文一律原文；凡我没拿到一手原文的地方，标「未取到一手」。

---

## 结论

**业界不按「对象」也不按「工序」拆，按「变更面」拆——而"一个引擎装多条规则"是默认终点，只有当一个对象带独立工具链依赖/独立发布单元时才升级为独立模块。**
（Parnas 1972 原话："it is almost always incorrect to begin the decomposition of a system into modules on the basis of a flowchart … modules **will not correspond to steps in the processing**"）

产业实现的稳定三层是：**引擎 1 个 / 规则 N 条（最小启用与豁免单位）/ 分发容器 M 个（插件·包·规则集，按共同依赖聚合）**。
硬数据：eslint 核心 **294** 条规则放在**同一个包**里；eslint-plugin-vue **257** 条、eslint-plugin-react **103** 条各放**一个插件**里。**不存在"一条规则一个包"的实践**。

**适用条件**：
- 走「一个引擎多规则」——规则之间只**读同一份中间产物**（AST/IR），增删单条不扰动他条，用户需要按强度或维度**组合启用**。
- 走「一对象一模块」——该对象有**自己的运行时/解析器/外部工具**、**自己的版本号与发版节奏**、能被单独卸载（eslint-plugin-prettier 这种 adapter），或**共享同一份昂贵中间产物会付出不可接受的代价**。

## 案例

### 1. ESLint：规则是单元，插件是分发容器

- **结构证据**：核心规则"Each core rule in ESLint has **three files** named with its identifier"——`lib/rules/x.js`、`tests/lib/rules/x.js`、`docs/src/rules/x.md`。一个插件导出 `{ meta, configs, rules, processors }`，`rules` 是**字典**。
- **为什么这样组织**（原话）：插件只是"encapsulate the additional functionality you want to share across multiple projects"；`peerDependencies` 要求 eslint ">=10.0.0" + npm keywords → **插件边界 = npm 分发边界**，不是对象边界。
- **官方有没有给插件粒度建议？没有。** Create Plugins 页通篇无 "granularity/one rule per plugin" 字样（我逐节读过，确认缺失）。唯一相关的是运维性建议："To make your plugin as easy to maintain as possible"。
- **唯一被明文承认的拆分理由（单条规则的独立生命周期）**："When rules are feature complete, they are marked as frozen … considered feature complete when the intended purpose of the rule has been fully implemented such that it catches 80% or more of expected violations"——**规则可以单条冻结**，所以规则必须是可独立处置的最小单位。
- **反例（一规则一插件）存在，但理由是外部工具依赖**：eslint-plugin-prettier = 1 条规则 1 个插件，自述 "Runs Prettier as an ESLint rule"。而 Prettier 官方明确**不推荐**这种融合："**Use Prettier for code formatting concerns, and linters for code-quality concerns**"；桥接插件 downsides 是 "They're yet one layer of indirection where things may break"、"They are slower"、"generally not recommended"。
- URL：https://eslint.org/docs/latest/extend/plugins ｜ https://eslint.org/docs/latest/contribute/core-rules ｜ https://prettier.io/docs/integrating-with-linters
- 数量：GitHub API 列 `lib/rules` → eslint 294 / eslint-plugin-vue 257 / eslint-plugin-react 103。

### 2. Checkstyle：**一条引擎按 token 分发给所有 check**（与我们的问题最同构）

- **结构证据**：配置是一棵树，根 `Checker` → 子模块 `TreeWalker` → 各 check。全部 ~200 条 check 是**同一个 XML 里的并列条目**，不是并列程序。
- **原话（这是本节的关键）**："The `TreeWalker` module creates a syntax tree for a Java source file and invokes its submodules, called *Checks*, during a walk … Every node of the syntax tree has a token. **A visit to a node during the traversal triggers all Checks that are configured for its token.**"
  → **"这个节点是什么类型"不是模块边界，而是规则的触发条件（token）**。同一 check 还能对多 token 重复挂载："To apply particular properties to different subsets of tokens for a Check, **repeat the Check**"。
- **为什么合在一个引擎**（原话）："properties are inherited in the module hierarchy. These features make it easy to define one property value that applies to many modules."
- URL：https://checkstyle.org/config.html ｜ https://checkstyle.org/checks.html（导航"organized by functionality"、索引按字母）

### 2b. PMD：按**八类工序**组织，语言是第二维；并有一条明确的"粗/细引用"判据

- **结构证据**：`category/<语言>/<类别>.xml/<规则名>`，例 `<rule ref="category/java/errorprone.xml/EmptyCatchBlock" />`；八类 Best Practices / Code Style / Design / Documentation / Error Prone / Multithreading / Performance / Security，且"**consistent across languages**"。
  → 主组织轴是**质量面/工序**，语言（对象域）只是路径的一段。
- **明确判据（原话）**："Referencing a complete category or ruleset means, you'll also get automatically any changes for this ruleset. If new rules are added, then these are automatically activated for you. If rules are deprecated, then these rules are automatically deactivated. **This might or not might be, what you want.** … **If you want to have complete control over the rules that you are using, then it is recommended to add each rule separately**"。
  → 拆到多细 = **谁吸收上游变更**（粗引用省维护、失控制；细引用得控制、担维护）。
- URL：https://docs.pmd-code.org/latest/pmd_userdocs_making_rulesets.html

### 2c. SonarQube：质量维度是**标签**不是分区

- **原话**："In Multi-Quality Rule (MQR) mode, rules are categorized by software qualities: security, reliability, and maintainability. **A rule may impact more than one software quality.**"
- **结构证据**：`Repository`（= "the engine/analyzer that contributes rules"）是最接近"模块"的轴；`Quality profile` 是命名选择束。规则另带 Language / Severity / Tag / Coding attribute / Status(Beta·Deprecated·Ready) / Available since 共 10 个可筛面。
  → **一条规则横跨多个维度 → 维度不能当模块边界**；模块边界落在"插件/分析器"（即运行时单元）。
- URL：https://docs.sonarsource.com/sonarqube-server/latest/user-guide/rules/overview/

### 3. LLVM：pass 是最小单元，按**作用域契约**归类，按 pipeline 排序

- **结构证据**："All LLVM passes are subclasses of the Pass class"；可选基类只有 `ModulePass` / `CallGraphSCCPass` / `FunctionPass` / `LoopPass` / `MachineFunctionPass`——**按 IR 的"作用域单位"分类，不按 IR 节点类型分类**。
- **明确判据（原话）**："you should choose the **most specific** class possible, while still being able to meet the requirements listed. This gives the LLVM Pass Infrastructure information necessary to optimize how passes are run, so that the resultant compiler isn't unnecessarily slow."；pass 分类的实质是"gives the system more information about **what your pass does, and how it can be combined with other passes**"。
- **为什么不是"每个 IR 节点类型一个编译器"**：pass "are, above all, **a structuring technique for compiler code**"；`PassManager` 负责"Share analysis results"（不重复算分析）与"Pipeline the execution of passes"（"It reduces the memory consumption of compiler, because, for example, only one DominatorSet needs to be calculated at a time"）。→ **共享重计算 + 缓存局部性**是合引擎的硬理由。
- **新 PM 的注册方式**：`PassRegistry.def` 列出每个 pass 及其 "IR unit (module, CGSCC, function, loop)"；嵌套 `module → cgscc → function → loop`；外部注入走 `registerPipelineStartEPCallback` 这类**命名扩展点**，而非新造编译器。
- URL：https://llvm.org/docs/WritingAnLLVMPass.html ｜ https://llvm.org/docs/NewPassManager.html

### 4. Schema/API 校验器：规则按**语义面（purpose）**分组成 vocabulary，keyword 不是声明单位

- **JSON Schema 2020-12（最锋利的一条）**："A vocabulary is generally organized around **a particular purpose**."；"**Vocabularies are the primary unit of re-use** in JSON Schema"；"**While keywords can be supported outside of any vocabulary, there is no analogous mechanism to indicate individual keyword usage.**"
  → **keyword（= 具体校验规则）被显式拒绝作为组织单位**；组织单位是 purpose 面。`$vocabulary` 按三档强度分层（硬语义**只到模块层**）：vocabulary 标必需 → "**MUST refuse to process**"；标可选 → "**SHOULD** proceed"；落到单条 keyword → "Implementations **SHOULD** treat keywords they do not support as annotations"（**软的，无硬拒绝**）。→ 结论：**能力边界只有划在"模块/用途"粒度上，才配拥有硬语义**。另有一处硬约束：`$vocabulary` "**MUST NOT appear in subschemas**"、"MUST be ignored in schema documents that are not being processed as a meta-schema" → **必需性声明只能写在元层，不许散落在实例里**。
  URL：https://json-schema.org/draft/2020-12/json-schema-core
- **buf lint（工序内按严格度累进分组）**：`MINIMAL ⊂ BASIC ⊂ STANDARD`（"Anything passing `STANDARD` also passes `BASIC` and `MINIMAL`"），另有两个正交类别 `COMMENTS`、`UNARY_RPC`。"**Rules are grouped into categories so you can opt in to a strictness level rather than enabling rules one at a time.**"
  → 规则名**绝大多数按对象起**（ENUM_*/FIELD_*/MESSAGE_*/ONEOF_*/RPC_*/SERVICE_*/PACKAGE_*/IMPORT_*/FILE_*/COMMENT_*/DIRECTORY_*/SYNTAX_*），**但组织轴是严格度**，交付是一个二进制。这是"按对象命名、不按对象分模块"的**正面**反例。
  **例外两条必须留档**（否则"按对象命名"会被原文直接反驳）：`PROTOVALIDATE` 不守前缀；`STABLE_PACKAGE_NO_IMPORT_UNSTABLE` "Categories: none"、须显式启用。→ **连命名惯例本身都不是铁的**，工具作者照样允许例外。
  URL：https://buf.build/docs/lint/rules/

## 判据汇总

### A. 业界**明确表述**过的拆分判据（有原话）

| # | 判据 | 出处原话 |
|---|---|---|
| A1 | **不按流程图/工序拆**，按"易变的设计决策"拆 | Parnas 1972 p.1058："it is almost always incorrect to begin the decomposition of a system into modules on the basis of a flowchart. We propose instead that one begins with a list of difficult design decisions or design decisions which are likely to change. Each module is then designed to hide such a decision from the others … modules will not correspond to steps in the processing." |
| A2 | 模块是**责任分配**，不是子程序/不是部署单元 | Parnas p.1053："'module' is considered to be a **responsibility assignment rather than a subprogram**" |
| A3 | 拆分好坏要用**变更落点**验收 | Parnas p.1055：同一张变更清单下，"For the first decomposition the second change **would result in changes in every module!**"；第二分解里"Any change in the manner of storage can be **confined to that module**"；且效益三条 = managerial / product flexibility / comprehensibility |
| A4 | 细引用 vs 粗引用 = **谁吸收上游变更** | PMD："This might or not might be, what you want … If you want to have complete control … add each rule separately" |
| A5 | 单条规则若能有**独立生命周期**，就必须是独立处置单位 | ESLint Frozen Rules：逐条判定 feature complete（"catches 80% or more of expected violations"）、逐条冻结、逐条建议 fork |
| A6 | 分组要服务**启用粒度**，不是服务实现 | buf："grouped into categories so you can opt in to a strictness level rather than enabling rules one at a time" |
| A7 | 组织单位是**语义面（purpose）**，细到 keyword 就失去可声明性 | JSON Schema："there is no analogous mechanism to indicate individual keyword usage" |
| A8 | 合引擎的正当理由是**共享配置/共享重计算** | Checkstyle："easy to define one property value that applies to many modules"；LLVM PM："Share analysis results" / "reduces the memory consumption" |
| A9 | 选最窄的作用域契约，为的是**可组合性与调度** | LLVM："choose the most specific class possible … how it can be combined with other passes" |
| A10 | 关注点不同就不该包 adapter，**应各自成工具** | Prettier："Use Prettier for code formatting concerns, and linters for code-quality concerns"；桥接 "generally not recommended"、"yet one layer of indirection where things may break" |
| A11 | **按变更面拆（第二分解）也有代价，但代价成立的条件是"仍按子程序实现"**；代价来源是**模块间切换**，不是"模块多"。且**成本只记运行态、收益记非运行态，两本账不可折价** | Parnas §Efficiency and Implementation **p.1056**：**"If we are not careful the second decomposition will prove to be much less efficient than the first. If each of the functions is actually implemented as a procedure with an elaborate calling sequence there will be a great deal of such calling due to the repeated switching between modules. The first decomposition will not suffer from this problem because there is relatively infrequent transfer of control between modules."** 解法不是不拆，而是换实现："the routines will be best **inserted into the code by an assembler**"；且承认"the separation between modules may not be clear in the final code"，故须"maintain … several representations of the program … together with a program performing mapping between them"。**分账依据（p.1054）**："The systems are **substantially different even if identical in the runnable representation** … the runnable representation need only be used for running; **other representations are used for changing, documenting, understanding**, etc." → **性能与可维护性不是同一张表上的两个分项，须各设预算、禁止相互折价** |
| A12 | **按实体/数据模型切组件是具名反模式（entity trap）**，判据是"围绕存储而非行为"——与 A1/A3 同轴（都是"变更/行为面"而非"对象清单"） | Richards & Ford《Fundamentals of Software Architecture》Ch.8："This isn't an architecture; it's a component-relational mapping of a framework to a database."；"the components end up **organized around storage rather than behavior**"。**⚠ 此条由队友 res-standard-axis / res-split-cost 核过，非我取证**；属教材/命名范式级，未核原书页码 |

> ⚠ **成本主体不同，禁止并算**：A4（PMD）= **维护者**承担上游变更；A11（Parnas）= **运行时**承担调用开销；A10（Prettier）= **集成层**承担多一跳。三者不是同一主体的成本，并成"拆分总成本"会塌陷（res-split-cost 交叉提醒，我已自核 A11 原文）。

### B. 我**从结构推断**的判据（无原话背书，标注为推断）

| # | 推断 | 依据的结构 |
|---|---|---|
| B1 | **按"对象域"分模块的实际载体是语言/框架/外部工具，不是"被检节点类型"** | eslint-plugin-react / -vue / -import、stylelint、sonar 的 Repository——插件名对应框架或分析器，无一是"某个语法节点一个插件" |
| B2 | **部署单元 = 版本单元 + 依赖单元**决定插件边界 | ESLint 插件必须声明 `peerDependencies` 与 npm keywords；Sonar 插件即 analyzer |
| B3 | **规则命名按对象 ≠ 模块按对象**，前者是命名空间便利 | buf 的 ENUM_/FIELD_/RPC_ 前缀全在一个二进制里 |
| B4 | **"触发条件"是对象类型在体系里的正确落位**（token / given / keyword），不是模块划分依据 | Checkstyle token 分发、JSON Schema keyword、Spectral `given` |
| B5 | 一个插件/包的规则数落在 **10² 量级**（~100–300），说明聚合上限由**人类可维护面**而非对象数决定 | 294/257/103 |

## 查不到的清单（明说）

1. **ESLint 官方从未表述过插件粒度建议**。Create Plugins 与 Custom Rules 两页均无 "granularity" / "one rule per plugin" / "rule is the unit" 字样。"一规则一文件"只在 Contribute Core Rules 里以 **"Each core rule … has three files"** 的形式出现（是**文件**粒度，不是**包**粒度）。
2. **"一个对象一个包/模块"没有任何权威文本支持**——反向证据强（buf/Checkstyle/eslint 均一容器多规则），正向证据为**零**。**唯一沾边的是 A12 entity trap，但它反对的是"按实体切组件"（架构组件层），不是"一对象一发布包"；且我未自核原文，不并入本报告证据链。**
   另需防一处混引：**entity trap（过粗/抄数据模型）与 grains of sand（过细/一 class 一服务）在粒度轴上相反**，不可并列成"两种切法都被否"；后者的 ACID/编排自检也**不可迁移**到无网络跳的 skill 场景。本条由队友交叉提醒，我未自核，不引用。
3. **Parnas 1972 的"按责任分配"如何映射到"skill/module"无原始出处**——1972 年不存在 skill 概念；这条迁移是本次推断，不可当引文用。
4. **LLVM 没有一句话解释"为什么不为每种 IR 节点建一个编译器"**。我给的解释（共享分析、缓存局部性、内存）来自 PassManager 的**功能描述**，属于结构推断（已归入 A8 的边角，主论断按推断看待）。
5. **buf 未在同一页明文说"lint 与 breaking 是两个命令"**——该页只覆盖 `buf lint`；工序级分离未取到原话。
6. **PMD 八类为何是这八类，无设计理由文档**；只查到"Since PMD 6.0.0 … sorted in one of eight categories, which are consistent across languages"，属既成事实陈述。
7. **一手渠道限制**：Parnas PDF 经 Tufts 镜像（`cs.tufts.edu/~nr/cs257/archive/david-parnas/criteria.pdf`）取得全文，ACM DL 与 win.tue.nl 均 403/503；页码引自已取全文内的 1053–1058 页标。
