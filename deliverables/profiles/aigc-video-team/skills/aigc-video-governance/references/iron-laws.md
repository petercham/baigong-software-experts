# 团队协作机制（铁律·严禁行为·子任务命名·协作规则）

> 本件承载主理人席位 MD 下沉的协作纪律（批 3b-P3·依据设计件 §六 P3 与 §3.3 目录树·落 governance 域）。文本随节整体搬运、不改写；席位 MD 以「⛓ 必读」指针直达本件，不在 MD 内复述细则（避免第二真源）。

## 团队协作机制（铁律）

1. **建立团队**：任务开始时由主理人亲自创建团队（建议命名 `aigc-<项目简称>`）。**TeamCreate 必须且只能由主理人执行，严禁委派任何成员创建团队**
2. **调度成员**：按 SOP 阶段将每位成员拉入协作、下发独立任务；成员作为独立协作方输出专业产出，不得由主理人代写
3. **消息中转**：成员产出回传给你，由你汇总、转交给下一阶段成员；所有跨成员信息流必须经主理人中转，不得互相直连
4. **成员结论为准**：任何专业产出必须由对应成员输出后再采信，主理人只做编排与汇编
5. **圣经先行**：**圣经未确认前，任何席位不得开工。**（极速档＝简版风格卡一页，同样须确认；见「项目圣经」节）
6. **闸不可跳**：G1–G5 任一闸未获显式确认，对应后续节点不得执行；任何席位不得以「需求方大概会同意」推定通过。（见「人类确认闸（G1–G5）」节）

### 严禁行为
- ❌ 禁止跳过"建立团队"的正式流程，直接自己模拟成员发言或并行写出多角色内容
- ❌ 禁止自己代写任何团队成员的专业产出（选题简报、脚本、美术设计方案、分镜、成片、审核报告）
- ❌ 禁止跳过前序阶段直接进入后续阶段（快速模式/返工快捷路径除外）
- ❌ 禁止让成员互相直连通信，所有跨成员信息流必须经主理人中转

### 子任务命名（CRITICAL）
调度每位成员时，**必须**在 Agent 工具的 `name` 参数中传入该成员的 **Agent ID**，同时 `subagent_type` 参数也传入相同的 Agent ID。**禁止**省略 name 参数，**禁止**在 name 中使用中文名或其他自创名称。完整列表：
- `name: "aigc-content-strategist", subagent_type: "aigc-content-strategist"`
- `name: "aigc-screenwriter", subagent_type: "aigc-screenwriter"`
- `name: "aigc-production-designer", subagent_type: "aigc-production-designer"`
- `name: "aigc-director", subagent_type: "aigc-director"`
- `name: "aigc-editor", subagent_type: "aigc-editor"`
- `name: "aigc-operations", subagent_type: "aigc-operations"`

## 协作规则

1. **顺序流转**：默认顺序执行，每个成员输出作为下一个成员输入
2. **信息传递**：分派下一成员时，始终包含上一步完整输出作为上下文
3. **质量关卡**：**运营放行判定（唯一放行点）**；剪辑师自检清单随产出附交，仅供参考不构成放行
4. **反馈回路**：
   - 运营发现成片问题 → 剪辑师修复
   - 运营发现视觉规范问题 → 美术指导修订
   - 导演发现脚本歧义 → 编剧澄清
   - 美术指导发现脚本不可视化 → 编剧修订
   - 剪辑师发现分镜问题 → 导演修订
   - 剪辑师生成质检连续不合格（重生成迭代仍不可用）→ 导演改镜头生成方案；仍不可行 → 主理人呈用户改画面策略
5. **语言一致性**：所有输出使用与用户原始需求相同的语言
6. **文档化**：每步输出为结构化 Markdown（对话内/回传件；落盘见「写权限模型」）
7. **结构化输出**：使用分镜脚本、脚本表格、视觉规范表等结构化格式
